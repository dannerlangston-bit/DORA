## 1. Purpose, guarantees and how it works end to end

### 1.1 The problem, in the author's terms

A change to one feature breaks another. A developer changes Flexible Grid so chart cells carry less chrome. The Active Trader ladder, which can also live in a Flexible Grid cell, now draws over its own order controls whenever the cell is short. User testing of Flexible Grid does not catch it, because nobody testing Flexible Grid puts an Active Trader panel in a small cell. The developer hand-screenshots the chart grid to prove the change works, which proves nothing about the surfaces the change did not mean to touch.

Sentinel drives the whole product like a user, compares every screen of the build after the change against the build before it, reports the intended change as evidence and anything else that moved as a suspected regression, and does so for every change, every time, without a human remembering to look.

Three facts shape everything else in this spec:

1. Attribution comes from the build pair, not from a model. Candidate and base are installed from pipeline artifacts on identically fingerprinted rigs and driven through identical checkpoints in the same data window (3.1 Build pair rules). What differs, differs because of the change set, or because of an environment fault that has its own outcome name.
2. The system does not need to know what a screen should look like. It needs to know that the candidate should look like the base, and that every layout obeys invariants that hold everywhere (2.7 Layout invariants, INV-01 to INV-15): no two siblings overlap, nothing extends outside its parent, no text is clipped, required labels are present, no placeholder text at capture.
3. The intended change is declared up front in a change manifest (4.3 Change manifest). The manifest, not the reviewer's judgement, decides which diffs may be called `intended`. A diff on a surface the manifest does not declare is `collateral`, the highest-priority finding the system produces.

### 1.3 Goals and non-goals

Goals:

1. Every PR that touches UI code gets, within 45 minutes of its branch build, a comment separating the intended change (evidence) from everything else that moved (suspected regressions), ranked by tier, with one-click actions (9.2 PR comment template).
2. Every merge to main is compared with the previous main build across the full Surface Registry in the tier A workspaces plus every tier-1 flow within 3 hours.
3. Every release candidate is compared with the last released build across everything, including tier B and migration workspaces, size sweeps, soak and the Explorer, and is signed off N business days before GA (10.9 Release-day timeline).
4. Layout defects are found on the first run of any new layout, with no baseline.
5. Numbers on money surfaces are checked against an oracle, not only against pixels.
6. The system proves nightly that it still sees the defect classes it exists for, and the morning report says so when it does not.
7. Nothing the system does can send an order, except through the identity-gated `paper_send_ok` flow class, OPEN pending the risk owner (6.7 Send policy: both branches).

Non-goals:

- macOS and Linux in phases 1 to 3. Registry, flows, invariants and taxonomy are platform-neutral; only Rig Manager, Capture, Executor and the JAB rung are Windows-specific. Every report header names the platform (2.13, item B07).
- Live accounts, real routing, any customer account.
- Backend correctness beyond what the client displays.
- Load or latency testing beyond RC soak budgets.
- Accessibility conformance; keyboard-only flow variants are flow content.
- Replacing exploratory QA; the Explorer is bounded and runs last in RC runs only.
- Deciding what a screen should look like; baseline approval is human-only.

The full list of what the model cannot detect, each with an id and the label every merge and RC report prints for it, is 2.13 What this model cannot detect and how it is labeled.

### 1.5 Success criteria and kill criteria

Metrics are computed from run one, exclude synthetic items, and are printed in every report header with the harness commit, config commit, model id and prompt hash range (9.11 Metrics dashboard and kill criteria repeats this table and owns the dashboard). Targets are provisional until two release cycles have produced data; kill criteria are not.

| Metric | Formula | Target (Phase 1 exit / Phase 2 exit) | Kill or fix criterion |
|---|---|---|---|
| False-positive rate | Findings dispositioned noise or expected over all findings shown to a human, per run and rolling 30 days; mutants and suppressed findings excluded. | Under 35 / under 20 percent | Above 50 percent after three releases: PR comments stop, fix, re-enter pilot. |
| Flake rate | Checkpoints whose verdict flips between runs of one build or between a run and its targeted re-run, over checkpoints run; the per-checkpoint flake score drives quarantine at 0.10 over the last 5 observations of the same build (10.5 Flake tracking, targeted re-runs and quarantine). | Under 5 / under 2 percent | Above 10 percent for two consecutive releases after a fix list: no new flows until under target. |
| Quarantine share | Tier-1 checkpoints currently `not_run (reason: quarantine)` over registered tier-1 checkpoints. | Under 2 percent at every RC cut | Above 2 percent: run health red and the RC gate blocks until flow owners clear rows. |
| Time to triage | Human minutes from report publish to every Unexpected finding dispositioned (capped at 10 minutes per finding); p90 latency to first decision shown beside it. | PR under 15 / 10 minutes; merge under 30 / 20 per morning; RC under 2 hours | Above 2x target for two releases: cut tier-3 scope. |
| Escape rate | Production bugs on a registered surface that a checkpoint existed for and did not flag, per release; each is a root-caused incident classed covered-missed, not run, not registered or not detectable. | Measured / zero on tier 1 | Two consecutive releases with a covered tier-1 escape: system owner review of whether to continue. |
| Coverage per tier | Covered cells over registered cells per tier (2.12 Coverage accounting and the matrix); `not_run` never counts as covered. | Tier 1 100 and tier 2 70 percent / tier 1 100, tier 2 90, tier 3 60 percent | Tier 1 below 100 percent in a merge run blocks that release's RC gate. |
| Canary pass rate | Detected over injected mutants, per class, nightly. | Money-cell 100 percent, others measured / money-cell 100, others at least 95 percent rolling | Any money-cell miss: canary state `detector_blind`, P1 page and the banner on every report; no verdict is trusted until the next green canary. This is whole-pipeline detection (diff, invariants, Oracle, Reviewer), distinct from the Reviewer's own eval gate in the Reviewer quality row. |
| A/A noise floor | Pixels over tolerance and diff components between two captures of one build (3.9 A/A calibration and threshold derivation). | Zero on frozen checkpoints; masked_live per-region floors recorded | A non-zero frozen floor is a flow or environment bug with a fix list, never a raised threshold; unfixed after 5 business days it quarantines the checkpoint. |
| Reviewer quality | Precision and recall per category on the labeled eval set (300 to 500 items, 3.14 Eval set, metrics and gates) per model and prompt version; calibration error; human-overturn rate. | Not required (zero model calls) / `intended` precision at least 0.95, `does_not_match_manifest` recall at least 0.98 on tier-1 eval-set mutants and at least 0.95 overall, per model and prompt version (3.14); this eval gate measures the Reviewer alone and is distinct from the Canary pass rate row, where the whole pipeline must detect 100 percent of money-cell mutants or the detector is blind | `intended` precision below 0.85: `intended` disabled, declared-surface diffs go to `needs_human (reason: reviewer_unavailable)` until a new eval passes. |
| Harness health | `aborted_harness` and `aborted_budget` share of runs; `env_error` share of checkpoints; `passed_via_agent_fallback` steps over steps; cost per run (rig minutes plus model dollars). | Under 10 percent of runs and 3 percent of checkpoints / under 5 and 1 percent | Every `aborted_harness` and every `aborted_safety` pages harness on-call immediately (P1); two `aborted_harness` in a week freeze harness changes until root-caused. |

Pilot exit (end of Phase 2): two release cycles; false-positive rate under 20 percent; at least one real pre-release catch on an undeclared registered surface; triage within budget; canaries at target every night of the last cycle. The Phase 1 exit test is the worked example in 1.11 run as 10.10 End-to-end acceptance test: the Flexible Grid change, injected as a mutant and as a real branch, caught in a PR run and reported as `collateral` with the primitive FlexibleGrid named.

RC respin and pre-emption. A new RC build supersedes the running RC run: the running run schedules no new flow, stops at the next flow boundary with run outcome `aborted_budget (reason: superseded)`, its unreached checkpoints are `not_run (reason: budget)`, teardown and the post-run proof run as usual, and the new RC run starts at once with the rig reservation transferred. RC runs pre-empt the Nightly run; a skipped Nightly run is alerted, and its canaries run at the next free window before any further PR comment is trusted (until then every report carries a stale-canary banner). The RC start deadline is 8 hours before the release gate (sign-off N business days before GA, section 11); an RC run that cannot start by it goes to the release manager to decide (9.12).

All run types share the Orchestrator state machine (provisioned -> launched -> authenticated -> paper_mode_asserted -> settings_attested -> workspace_loaded -> fixture_verified -> canary_flow_passed -> running -> teardown -> reported; gate table in 5.2 Orchestrator), the Input Gateway, the data-mode policy and the outcome taxonomy. Runs happen in the operating day, 06:00 to 22:00 America/New_York; safety depends on the gateway and the account identity, never on the clock.

Base and candidate are scheduled by data mode (11.3 Sharding and parallelism). Frozen checkpoints run both builds on the same rig, back to back, and a base capture is reused when it was taken under the identical fingerprint and fixture epoch (a PR run's base is the merge-base main build, already captured by its merge run). `masked_live` checkpoints run on two identically fingerprinted rigs in lockstep, the same checkpoint within 60 seconds on both, with fingerprint equality asserted before capture; a slip over 60 seconds re-queues the pair once at the end of the shard, and a second slip is `not_run (reason: budget)`, counted as `lockstep_slip` in run health, a counter and never a finding (3.1). If only one rig is free, `masked_live` checkpoints are `not_run (reason: budget)` rather than captured minutes apart.

### 1.10 Outcome taxonomy (authoritative)

This is the authoritative copy; 12.2 Outcome taxonomy carries it verbatim together with the reason table that lists every reason code used in this spec, and every section uses these names and no others. The sets are closed: 15 per checkpoint, 5 per step, 5 per run, enforced by SQLite CHECK constraints and the `outcome_reasons` lookup table generated from `taxonomy.yaml` (8.3 Schema). A reason is written as `outcome (reason: code)`, a gate as `env_error (gate: name)`; reasons refine an outcome and never add to the set.

Precedence. A checkpoint can produce several results (an invariant fires and the pixel diff is also above threshold). It ends in exactly one outcome, the first that applies in this order: `env_error`, app failure (`assertion_failed (assertion: app_alive)`), `harness_error`, `not_run`, `not_comparable`, `not_settled`, `landmark_missing`, `invariant_violation`, `assertion_failed` (every other assertion), `needs_baseline`, `collateral`, `needs_human`, `intended`, `noise`, `identical`. Environment outranks the app and the harness because a hang during a network drop is an environment fact, and an app failure outranks the harness because an exception raised while handling an app failure is evidence of that failure, not a harness fault (10.1). Lower results that also applied stay on the finding record as evidence (a `collateral` classification on an `invariant_violation` finding) but are not outcomes. `unregistered_surface` is a checkpoint of its own created by registry validation and never competes. The rule list in 3.11 Classification decision table implements this order. One refinement inside that list: a region with no calibrated floor cannot be said to be above a threshold, so `needs_human (reason: uncalibrated)` is decided before `collateral` (3.11 row 15) and is ranked with `collateral` in the report.
