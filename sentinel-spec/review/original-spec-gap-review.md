# Spec review: AI visual regression and exploratory tester for thinkorswim

This review covers the spec as pasted, which was cut off after the Reporter row. 76 gaps survived adversarial review by two independent skeptics; each appears exactly once in sections 2 to 5 with its id so you can trace it. Section 8 lists the gaps that your cut-off sections (flow list, phases, risks, metrics) may already cover, so you can check rather than be told you forgot. Section 9 separates what the reviewers verified about thinkorswim, paperMoney and the tooling from what remains unverified.

## 1. Executive summary

1. The first question decides whether this is a release gate or a post-mortem tool: which build does the system test, and when? If the machine only ever runs what the launcher downloads tonight, it sees version N the night after every user did, and "little to no issues once released" is unachievable by construction (G12, G13). Make build identity an explicit run input with two written modes: internal (RC artifact or pipeline trigger, triage complete and signed off N business days before GA) and external (no RC access; reframe to "detect within the first closed-market window after release", pin builds only through VM snapshots because the installer cannot pin a version).
2. Four statements in the spec contradict each other or the goal and must be resolved before any component is designed. "Keep everything on the machine" versus an AI reviewer and a Claude computer-use agent that upload full-window screenshots of account numbers, balances and an unreleased build to an external API (G07). "Never send a real order" enforced by a button-label rule while Auto Send, Shift+click send, the confirmation-off setting and Enter on the confirm dialog bypass it, and "it cancels" leaves the entire post-order lifecycle (Working to Filled, cancel/replace, brackets, buying-power recalculation) untested (G01, G04). "Same window size, font size, workspace layout every time" versus an Explorer that resizes windows and changes settings on the same login, where most of that state is server-side and survives a VM revert (G47, G46, G58). "Run only while the market is closed" versus a platform where 24/5 equities, Globex futures, forex and now 24/7 crypto futures almost never close, and a goal of catching wrong numbers on a streaming product that the tester only ever sees static (G22, G23).
3. There is no oracle and no intent input. Every component compares pixels to yesterday's pixels or asks a vision model to read 9 to 11 px fonts after downscaling; nothing reads a number off the screen and checks it against an independent source or the other numbers it must agree with (G28); flow files describe screens but carry no assertions (G29); and the reviewer must label diffs "expected UI change" with no release notes, tickets or mocks anywhere in the design (G30). The second half of your goal, cross-checking changes against the intended outcome, has no input to cross-check against.
4. Order safety needs an input gateway, not a prompt instruction: keystroke-level denial of Enter, Space and order hotkeys while a ticket or confirm dialog is up, run-start attestation of the settings that disable confirmation, a runtime assertion that the login landed in paperMoney (the Live/paperMoney switch is one toggle on the same Schwab credential), a kill switch followed by a verified Cancel All and a post-run proof that nothing was sent, and a hard deny list for the Explorer, which today can post in Chat Rooms, share to public tos.mx links, page the account owner by alert, open Application Settings and disable the confirmation dialog for every later run (G01, G02, G03, G05, G06).
5. Noise will kill the tool before a missed bug does. No A/A calibration of the noise floor, one global threshold, masks that are unanchored rectangles, no settle rule before capture, no popup catalog, account state and server-side profile drifting between runs, and verdicts that are never persisted mean the same 40 diffs come back every morning; within three weeks nobody opens the report and the one real bug ships (G26, G25, G18, G17, G44, G46, G34).
6. Scripted mode as written cannot exist. thinkorswim is Swing with a custom look and feel; pywinauto and UIA see a single opaque SunAwtFrame, so "fixed clicks" means absolute screen coordinates that every release moves, and the fast, stable tier collapses into slow, nondeterministic agent mode (G09, C07, G38).
7. Trust, not detection, decides adoption: a human-only baseline approval with lineage, a labeled eval set and recall metric for the reviewer, nightly synthetic-fault canaries that prove the detector still sees a missing Send button, and metrics with kill criteria (G32, G36, C02, G66).
8. Before writing code: name the accountable owner and get written authorization (G08); get a data-path ruling on which model endpoint and retention terms may receive screenshots (G07); and run a week-1 spike on the target machine covering Java Access Bridge exposure, OnDemand availability under the paperMoney login, the A/A noise floor, and the one-session-per-login rule (G09, G23, G26, G50).

## 2. Contradictions in the spec to resolve first

Each item below quotes the spec text that conflicts, states the question only you can answer, and gives the decision.

### Order safety and account identity

**Never-send guard is a button-label rule; keyboard, hotkeys, Auto Send, no-confirm paths and agent mode bypass it (G01)**
What conflicts: the only enforcement is "it must never click 'Send,' 'Confirm and Send' or anything like them" plus "if the confirm dialog's Send button is under the cursor, stop the run", while the same section says "it can build, stage and review orders, then it cancels." A click rule does not cover Enter or Space on the focused Order Confirmation dialog, Active Trader ladder clicks with Auto send on, Shift+click send, the Application Settings option that disables the confirmation dialog, user-bound order hotkeys, pywinauto `type_keys` or the computer-use model emitting Enter by habit; in agent mode the rule is a prompt instruction, not a hard stop. The spec never says where the "hard-coded rule" lives, and pywinauto cannot see Swing controls, so the executor never knows which control it is about to click (Delete and Edit sit beside Send in the confirm dialog, so a layout nudge turns the cancel click into a send). On paperMoney a stray fill corrupts the positions every later run depends on; the day the harness lands on an internal account with real routing, or the login lands on Live, it is a real order and a compliance incident. The Explorer's "rapid clicking" is specifically likely to hit a ladder cell.
Question: Is the executor's input gateway the only path to the OS, or do flows and the computer-use loop call pyautogui/pywinauto directly? Which order paths bypass the confirmation dialog on this account's current settings? Is "never press Send" a compliance requirement imposed on you, or your own guardrail?
Do: Build one input gateway and split it into a slow half and a fast half. All OCR, template and JAB resolution runs inside the gateway before any event is emitted; the low-level hook callback consults only in-memory arm/deny state (expected click coordinates plus a one-shot token, a "ticket or dialog visible" flag, a blocked key set), because Windows silently unhooks a callback that exceeds the low-level hook timeout. The hook drops injected Enter, Space and Ctrl+Enter whenever the ticket/dialog flag is set, and any click without a matching token. A run-start attestation flow screenshots and OCRs Application Settings (confirmation on, Shift+click send off, Active Trader hot keys disabled, no order hot keys bound) and the Auto send checkbox on every Active Trader panel in the workspace, since it is per panel. As an independent paperMoney-only layer, use Adjust Account to hold cash at a small fixed amount so an accidental send larger than the fixture size is rejected for buying power (skip if G04 sends are enabled). Nightly fire drill: attempt Enter on an open confirm dialog, an Auto send ladder click, a bound hot key and Shift+click; pass only if the gateway blocks each and Monitor > Activity and Positions shows no new row.

**Live vs paperMoney is one login toggle; nothing asserts paper mode at runtime (G02)**
What conflicts: "Never point it at a live account" names no mechanism. The thinkorswim login dialog has a Live Trading / paperMoney switch on the same Schwab credential; it can be flipped by an agent, a human, a profile reset or a layout shift in a new build, and the scripted login has no positive check of which mode it landed in, no re-check after a mid-run re-login, and no record of the account used. One misclick at login puts the whole run, Explorer included, on a real brokerage account with real routing, with the cursor-over-Send screenshot check as the only remaining guard.
Question: Can the platform team issue a paper-only or test-backend credential whose live side has no trading entitlement? What does the login screen default to on that machine today?
Do: Assert mode from the account selector text (OCR, `D-` prefix plus a hard-coded allowlist) immediately after login, before every flow, and after any re-login or session-expired dialog; kill the process tree on mismatch. Write `account_id` and mode into the run manifest and every checkpoint record. On identity: inside Schwab, get a test-backend credential. Outside, the only paper-only credential is a thinkorswim Guest Pass (demo-only, 30 days, not extendable, separate from any brokerage login), so plan a 30-day rotation; or use an unfunded Schwab brokerage account (stays open at $0, permanent paperMoney) and treat its Live mode as present, asserting against it every time. Whether the login dialog remembers the last mode is unverified; the account-dropdown prefix is the reliable signal, not a title-bar badge.

**Banning Send even in paperMoney leaves the post-order lifecycle untested (G04)**
What conflicts: "Never send a real order" and "it can build, stage and review orders, then it cancels" stop before the part of the product where the costliest bugs live: Working Orders rows, Working to Filled/Partial/Rejected/Canceled transitions, cancel/replace, OCO and bracket children, fill notifications, position creation, P/L Open, buying-power recalculation, Account Statement rows and Strategy Roller. The Confirm and Send dialog's numbers are screenshotted but never verified, and Cancel itself is never verified: no assertion that Working Orders has no new row, that the ticket cleared, or that balances are identical before and after. A regression where a filled bracket's stop leg stays Working, where Cancel silently leaves an order working, or where a staged order is submitted on dialog close is invisible because nothing ever fills.
Question: Is "never send a real order" meant to forbid simulated paperMoney fills too? Is the risk owner willing to permit tiny, allowlisted, far-from-market paper sends under a positive-identification gate?
Do: Keep identity-gated `paper_send_ok` flows (1 share or 1 contract, far-from-market limit, allowlisted `D-` account, fresh frame), a start/end state snapshot with end equal to start for every non-send flow, and OCR assertions on the Confirm dialog arithmetic. Do not plan fills inside OnDemand: OnDemand is launched from Live Trading mode, not paperMoney, so that path would require a Live login and contradict G02. Instead: (a) Working to Cancel flows using far-from-market DAY limits, which work after hours; (b) for fills while equities are closed, a 1-contract micro futures order such as `/MES` in paperMoney during the overnight Globex session, after verifying by hand that paperMoney simulates overnight futures fills on its delayed feed; (c) if the risk owner refuses any send, print "fills/rejects/replaces untested" in every report. Add an end-of-run Cancel All and a positions-flat check before the next run. paperMoney quotes are delayed 20 minutes by default and fills simulate off that tape, so equity orders cannot fill in the spec's closed-market window at all.

**"Keep everything on the machine" contradicts sending screenshots to a cloud model (G07)**
What conflicts: "Screenshots stay local or in approved internal storage" versus "Agent mode: a computer-use AI model (Claude computer use) that reads the screen" and "AI reviewer: gets the baseline, the new screenshot and the heatmap." Both upload full-window screenshots, every screen in agent mode, to an external API: account holder name, account numbers in the Account Info gadget and order ticket, email, balances, positions, the username at the login checkpoint, and identifiers of an unreleased build. No endpoint, retention terms, data-classification ruling, InfoSec approver, redaction step or local-model fallback is named; the HTML report and SQLite store are also undescribed distribution channels. At a broker-dealer this is stopped at security review or runs for months before someone notices, and a late redaction bolt-on changes every stored baseline's pixels.
Question: Which model endpoint and retention terms has security/compliance approved for screenshots of the platform (even paperMoney), and what must be redacted before an image leaves the machine?
Do: Decide the data path before Phase 1, in this order. (1) Which model tier is zero-data-retention eligible under the firm's agreement: per Anthropic's docs as of November 2026 the newest models require 30-day retention by default and are excluded from ZDR unless expressly authorized, with a reported later exception for Fable 5.1 that is unconfirmed, so verify the current eligibility table with the account team. (2) Whether computer use, a beta feature, is covered at all under that agreement; if not, agent mode needs a cloud-provider endpoint (Bedrock or Vertex) or is dropped. (3) A local vision model for the reviewer as the fallback. Add the redaction stage in the capture module with masks anchored to locators, OCR-regex redaction of account patterns and the test user's name, store only redacted artifacts and diff on redacted copies. Keep a per-run egress log and a data-flow diagram.

### Executor and capture

**Scripted mode has no locators: thinkorswim is Swing, pywinauto sees one opaque window (G09)**
What conflicts: "Scripted mode: fixed clicks and keystrokes (pyautogui or pywinauto) for stable flows that run fast" assumes a Windows control tree. thinkorswim is Swing with a custom look and feel: UIA and MSAA see a single SunAwtFrame HWND with no children, so "fixed clicks" means absolute screen coordinates and every assertion, value read and the Send-button guard rely on pixels. Java Access Bridge is the only accessibility route; it needs a Python client (pyjab) with a WindowsAccessBridge DLL of matching bitness, and custom-painted panels (charts, option chain grid, Active Trader ladder) may appear as opaque containers. Nobody has verified what thinkorswim exposes. Coordinate scripts break on every layout change, which is exactly what a release does, so flows fail for the wrong reasons and cascade into agent mode; the fast, stable tier never exists.
Question: Has anyone run an accessibility inspector against thinkorswim with Java Access Bridge enabled to see what the tree exposes, panel by panel (order ticket, option chain, Monitor grid, Active Trader)?
Do: A week-1 spike. (1) Inspect the bundled runtime under the thinkorswim install folder and run its `java --list-modules` to see whether `jdk.accessibility` is present; if the bundled image is jlinked without it, JAB cannot be enabled at all and the options are launching on a full Zulu JDK 21 (unverified that the launcher allows this) or accepting template/OCR/coordinate rungs for everything. (2) Install a full Zulu JDK 21 on the box for `jabswitch`, `jaccessinspector` and the client-side `WindowsAccessBridge-64.dll`, and run `jabswitch -enable`, which writes `%USERPROFILE%\.accessibility.properties` (this survives a JRE replacement, so the updater does not drop it). (3) Dump the tree per panel and record names, roles, values and bounds. (4) Define a locator ladder in the flow schema (JAB, then template anchor, then OCR, then coordinates), log the rung used per step, and re-run the tree dump as part of each new-build intake. Prefer keyboard navigation and the symbol box where possible.

**Drag, wheel, right-click and splitter interactions are outside the executor's vocabulary (C04)**
What conflicts: the executor is limited to "fixed clicks and keystrokes." A large share of thinkorswim usage is press-move-release and wheel: panning and wheel-zooming a chart, drawing a trendline, dragging a working-order or alert price line, dragging the Active Trader ladder, dragging a tab out to detach it, dragging column headers and splitters, dropping a watchlist symbol onto a chart, right-click context menus, double-click to open, Ctrl/Shift multi-select. `pyautogui.dragTo` at the default `duration=0` never starts a Swing drag; computer-use `left_click_drag` is coarse. Nothing releases stuck modifier keys when the harness dies between keyDown and keyUp, and a stuck Shift turns the next "cancel" click into a Shift+click, which with the opt-in "Auto Send with Shift Click" setting can mean send-without-confirm. Detach, resize and drag paths are where layout bugs live, so "emulates how any and all users would use it" is false for the most common chart and workspace interactions.
Question: Does any flow drag anything? How do you get a trendline drawn, a tab detached or a column resized?
Do: Extend the flow step schema with `drag(from, to, steps>=10, hold_ms)`, `wheel(delta, at)`, `rclick`, `dblclick`, `key_chord` and a mandatory `reset_input_state` step (keyUp Shift/Ctrl/Alt/Win, mouseUp, Escape) at flow start, flow teardown, every exception handler and crash recovery. Implement drags with `pywinauto.mouse.press/move/release` or `pyautogui.dragTo(duration>0)`; pydirectinput is unnecessary for Swing. Add drag, wheel and right-click flows to the coverage matrix: detach and reattach a tab, resize a splitter, reorder and resize a column, draw and delete a trendline, drag an alert line, drop a watchlist symbol onto a chart, wheel-zoom a chart, context menus on chart, watchlist and positions. For order-bearing drags (chart order bubble, Active Trader ladder) rely on the G01 attestation that Auto Send and "Auto Send with Shift Click" are off and the confirmation dialog is on: official Active Trader documentation says dragging an order bubble opens another confirmation dialog unless Auto Send is enabled, so the never-send rule applies to the dialog the drag produces. Alert lines and drawings are safe to drag freely.

**Detached windows, owned dialogs and modals break "full-window" capture; multi-monitor layouts are never seen (G16)**
What conflicts: "Takes a full-window screenshot at each checkpoint, plus close-up crops of key panels" means one HWND. thinkorswim lets any tab or gadget detach into its own top-level window; order confirmation, Setup, the studies editor, alerts and chart settings are owned dialogs; modals disable the main frame. A detached window partly off-screen, a dialog overlapping the frame, a modal hidden behind the main window, or a dialog left open by a failed step is invisible while the flow keeps clicking a disabled frame. Power users spread detached windows over four monitors and run Flexible Grid. The confirm dialog, the one screen the spec most wants to check, may never be captured, and a leftover modal pollutes every later diff.
Question: Do you have data on how many users run detached windows or more than one monitor?
Do: Enumerate top-level windows of the thinkorswim process tree by PID (`EnumWindows` plus `GetWindowThreadProcessId`, class names `SunAwt*`; the process image is the install4j launcher, not `javaw.exe`, so filter by PID). Capture each via a virtual-screen grab (mss) cropped to `DWMWA_EXTENDED_FRAME_BOUNDS`, and save a composite virtual-screen image for the report. Let each checkpoint name its target window; key checkpoints by window title plus flow plus step; store title, rect and z-order with an invariant that every rect intersects the virtual screen. Before every input check `IsWindowEnabled(main_hwnd)`; false means a modal is up, so assert it is the expected dialog by title or template, else route to the popup sentinel (G17). Pin the main frame with `SetWindowPos` at run start. Add a workspace corpus (DEFAULT, CANONICAL, FLEXGRID, MULTIMON on virtual displays, two community tos.mx workspaces) and a mismatch flow that loads MULTIMON on one display; flows that detach end with a restore and a window-count assertion.

**Retries and the scripted-to-agent fallback hide the regressions they recover from; repairs are never written back (G38)**
What conflicts: agent mode "is used when scripted clicks fail, when layouts change" is described as resilience, while the stated purpose is catching "missing buttons, broken layouts ... regressions between releases." A scripted click failing because a button moved is the regression signal; the agent finding it anyway turns that into a green pass, leaves the screen in a different state (scroll, tooltip, sub-tab) so the checkpoint is not comparable, and nothing writes the repair into the YAML flow. Flake and regression become indistinguishable, the pass rate stays green while layouts drift, and within a few releases most flows run in agent mode and the run time balloons past the window.
Question: When a scripted step fails, is that a bug report, a self-heal, or both, and which screenshots after recovery count as comparable?
Do: Record retry and fallback as first-class events (step id, attempt, mode, reason, pre-attempt screenshot hash) and report step status as `passed`, `passed_after_retry`, `passed_via_agent_fallback` or `failed`, with a fallback shown beside the checkpoint diff as "scripted locator broke at step X" plus the agent's action trace. Cap retries at one per step, never retry across a capture, keep the first attempt's screenshot, and run a declared normalize routine before any post-recovery capture, which is tagged `rescued` and routed to needs-a-human. On agent success, save the final click target (native coordinates) and anchor crop and open a proposed flow patch PR; two consecutive fallbacks on the same version auto-open an "update scripted flow" ticket. Track flows-in-fallback and 30-day flake rate with a quarantine threshold, and budget maintenance hours per release with a named owner.

### Scheduling, market data and masks

**"Market closed" is undefined and nearly never true: 24/5 equities, futures, forex, crypto, maintenance, holidays, DST (G22)**
What conflicts: "Run only while the market is closed. The scheduler won't start a run during regular market hours" treats market closed as one quiet state and never says why it matters (noise, load, compliance or order safety). Verified: Schwab retail clients can trade 1,100+ securities 24/5 from 8 pm ET Sunday to 8 pm ET Friday; CME crypto futures now trade 24/7 with a Saturday 2:00 to 4:00 am CT maintenance break; CME Globex runs Sunday 6 pm to Friday 5 pm ET with a daily 5 to 6 pm break; forex runs 24/5; Schwab's extended-hours order sessions are 7:00 to 9:25 am and 4:05 to 8:00 pm ET; NYSE holidays, 1 pm early closes and DST weekends differ from CME. Prices propagate beyond quote cells into P&L, buying power, Greeks, chart candles and ladders, which no region mask covers. Nothing defines what a run does when it overruns into 09:30 with orders staged, and the rule provides zero order safety for `/ES` or EUR/USD. If the test symbols are SPY, AAPL, `/ES` or anything on the 24/5 list, every weeknight run sees moving prices everywhere.
Question: What harm does running during market hours cause, what exact ET window counts as "market closed" for you, and which exact symbols are on the test list (are any in Schwab's 24/5 overnight list or crypto futures)?
Do: Define windows explicitly in config with an exchange-calendar library and tz-aware America/New_York datetimes: `all_quiet` = Friday 20:00 ET to Sunday 17:00 ET (forex opens 17:00, Globex 18:00, 24/5 equities 20:00 Sunday), used for canonical baselines and pixel-diff runs; `equities_quiet` = weeknights 20:00 to 07:00 ET only for symbols confirmed absent from the thinkorswim "Public > 24 Hour Trading" watchlist, which you export each run with the date. Exclude crypto futures from pixel-diffed checkpoints or give them an always-live profile. Each flow declares `requires_window`; the scheduler refuses runs that cannot finish before the boundary (durations from the run DB) and a hard deadline cancels staged tickets before 09:25 ET. Read the status-bar connection indicator and any delayed-data banner at every checkpoint, store them in metadata, and downgrade differences captured in a degraded state to "environment". Keep order safety entirely in the no-Send rule plus post-run Cancel All, never in the schedule. Verify the hours against Schwab's current page before coding windows; the Saturday-night maintenance window is anecdotal, not published.

**Streaming behavior is never tested; OnDemand replay can make it deterministic and the spec never uses it (G23)**
What conflicts: "Run only while the market is closed" versus the goal of catching "wrong numbers" and "functional problems" on a streaming-data platform. Users live on the platform during market hours; the tester only sees a static one. Never exercised: ticking quotes and cell flashes, Level II and Time & Sales churn, the Active Trader ladder re-centering, live chart bars, alerts firing, Working to Filled transitions, frozen-quote failures. Capture is stills only, so there is no temporal signal, and the regions that do stream after hours (futures, forex) are masked, which blinds the futures persona entirely. A Level II panel that freezes after 90 s, a quote column that stops updating, a chart that stops appending bars, all among the most-reported release-day issues, are invisible here.
Question: Does the test login have OnDemand, which features does the current build disable inside it, and is a pinned OnDemand timestamp acceptable as the data source for chart and quote checkpoints? Is "market closed" a safety constraint or a noise-reduction constraint?
Do: Spike OnDemand first on the target machine under the test login: confirm it is available at all (forum claims say a funded live account is required and that OnDemand launches from Live Trading mode, so this may conflict with G02), measure buffering time and failure rate over 20 launches, and enumerate which gadgets replay. If it passes, run Tier A as: open OnDemand, set the checked-in timestamp, press Go, wait for buffering (hard timeout classified as environment), immediately Pause, then capture; byte-identical data holds only when paused at the pinned timestamp. Store the timestamp with each baseline and give OnDemand account panels their own baselines since it swaps to its own virtual account. If the spike fails, drop Tier A and rely on frozen fixtures (G24) plus OCR rules. For Tier B streaming checks, use the futures session (Sunday 18:00 to Friday 17:00 ET) so it stays inside the spec's constraint: record 10 to 20 s at 10 to 15 fps at streaming checkpoints, compute per-region frame-difference energy (zero where the region must tick means frozen; sustained alternation means flicker), OCR the quote timestamp and require it to advance, and check bid <= ask and last within [low, high].

**Baselines go stale on date-driven content; the dynamic-content list misses most of what changes while closed (G24)**
What conflicts: "compares it with the same screen from the last approved version" and masks for "clocks, futures and forex quotes, news, extended-hours prices." Not covered: option expirations roll weekly and DTE counts down daily; the chain centers on the ATM strike so the visible strike set shifts; earnings and dividend icons; corporate actions creating adjusted series; front-month futures roll (`/ESZ25` to `/ESH26`); daily charts gain a bar and autoscale; previous close, net change and volume roll over; paperMoney delayed/stale badges (data is 20-minute delayed by default); "as of" labels; net liq and P/L drifting with marks; Message Center unread counts; and the data epoch of a baseline is never recorded. Each unlisted item is a false positive every run; masking them as they appear erodes the chain, chart and account summary until the tool stops checking the panels where wrong numbers appear, and the first run after every Friday expiration or quarterly roll shows every chain checkpoint as changed.
Question: Which test symbols are planned, and are their charts and option chains frozen or live during the run?
Do: Keep a per-checkpoint registry where every region is `freeze`, `data-rule` or `mask`. Freeze: fixed chart date range, fixed Strikes count, expirations chosen by relative rule ("2nd monthly out"), continuous futures symbols (the roll date is still part of the epoch), no positions in the visual-suite account, news, ticker and Schwab Network gadgets removed. A global "flash off" setting could not be confirmed, so defeat flashes mechanically: capture 3 to 5 frames over 1 to 2 s and take the per-pixel median before diffing. Data regions go to OCR plus format rules (G28); masks only for true noise (clock, connection indicator). Tag every baseline with a data epoch (window date, OnDemand timestamp if any, front-month contract, nearest expiration, delayed/real-time state) and keep a churn calendar (expirations, rolls, holidays, earnings, ex-div) so an epoch change triggers re-approval instead of scored diffs. Add `symbol_fixture.yaml` with a pre-run existence/split/expiration-shape check via the Schwab market-data API and abort into "fixture maintenance needed". Alert when a checkpoint's masked share grows.

**Masks are unanchored rectangles that drift, and masked regions are never checked at all (G25)**
What conflicts: "It applies masks to areas that are allowed to change" says nothing about how masks are authored, stored, versioned or kept aligned. As absolute pixel rectangles, a new toolbar button or a wider sidebar shifts content so the mask hides live content while the dynamic content slides out from under it, on every checkpoint at once; fixed-coordinate close-up crops have the same problem. And "allowed to change" is treated as "allowed to be anything": a quote that stops updating, shows 0.00, N/A or yesterday's price, flips sign or loses a decimal is inside a mask and never seen. Layout shifts are the normal case for a release, so the first real release under test is the one where every mask is wrong, and stale or malformed market data, a top-severity bug on a trading platform, is exactly what masks hide.
Question: Who draws the masks, where do they live, what happens to them when a panel moves 8 px to the right, and what still gets checked inside them?
Do: Store each mask and close-up crop as an offset from a named landmark (panel header text or icon template); locate it each run by template match with a confidence floor and emit a "panel moved/missing" finding when not found instead of diffing blind. Version masks with the baseline and flow, with an owner and reason, and add a CI check that masks are in bounds and under a coverage budget per checkpoint. Make masks typed: `{price: decimals, min/max, must_change_within during venue hours, must_not_change when closed}`, `{time: must_advance}`, `{text: min_rows}`; run those checks on the OCR extraction inside the region and report masked-region failures as their own class. Treat Java Access Bridge bounds as an optional spike and fall back to template landmarks if exposure is poor. Auto-propose masks from A/A runs (G26) and surface a mask editor in the report.

### Oracle, assertions and intent

**No ground-truth oracle for the numbers on screen: no OCR/JAB extraction, no API cross-check, no arithmetic or Greeks invariants (G28)**
What conflicts: the goal is "wrong numbers" and "values that don't add up", but every component compares pixels to a baseline or asks a vision model to read 9 to 11 px fonts after the API downscales the image. If the baseline already shows a wrong Mark, P/L, cost basis or DTE, the new build matches it and passes; if the value changes legitimately it is masked or called noise; a one-digit change is below any pixel threshold. A release that renders pixel-perfect while showing a stale quote, an un-adjusted cost basis after a 4:1 split (P/L Open at -75%, labeled "expected after market data update" and promoted to baseline), a wrong Buying Power Effect on the confirm dialog, or a mis-scaled option price passes with zero diffs. This is the single biggest blind spot and the class with the highest business cost.
Question: Which numbers on which screens does the team consider "must be exactly right"? Do you have Schwab Trader API or internal feed credentials for the test environment, and is the paperMoney account reachable through any API or only through the GUI?
Do: Add an Oracle layer before the AI reviewer. (1) Extract: OCR (Tesseract or PaddleOCR on an inverted, 2x-upscaled crop at the pinned, enlarged font size) into typed fields per checkpoint, validated each run against a calibration panel; spike JAB on the bundled runtime and use it only where it exposes values. Store extractions in SQLite next to the image so the baseline is also numeric and rules can be re-run offline. (2) Diff extractions: label and button sets exact, box geometry within tolerance, numeric cells by rule. (3) Evaluate `invariants.py` per checkpoint with per-instrument multipliers (equity options 100, `/ES` 50, `/NQ` 20, SPX 100), including no NaN, `--`, N/A or ellipsis, and number-format rules; use put-call parity as an equality only for European options such as SPX and as inequality bounds for American equity options on dividend payers. (4) Cross-check market data against the Schwab market-data API with the paperMoney delay modelled: compare to the API quote as of capture time minus 20 minutes unless the account is confirmed real-time, and require exact equality only for symbols whose last session closed more than 20 minutes earlier and that are not on the 24/5 list. Trader API access requires a registered developer app and OAuth against a live Schwab brokerage account. (5) Keep a corporate-action calendar for the test symbols and assert adjusted basis and multiplier across one upcoming split or dividend. (6) Require oracle-pass before any screenshot can be approved as baseline, and pass mismatches to the vision reviewer as text evidence (field, expected, got) with native-pixel crops.

**Flow files describe screens but carry no assertions, and the reviewer never sees the flow's expected state (G29)**
What conflicts: "Each one lists its steps, what the screen should look like, and the named checkpoints" has no assertion schema: nothing lets a flow state "after step 4 the ticket shows BUY +10 AAPL LMT 150.00 DAY, Buying Power Effect = -1,500.00" and fail otherwise, and the reviewer gets only baseline, new and heatmap, so it does not know which step was just performed, which panels and values must exist, or how critical the checkpoint is. A bug present in both baseline and new is invisible; a ticket that defaults to SELL, drops a digit from qty, rounds a 4-decimal price, resets TIF or accepts `-5` is "a small diff in a text region" the reviewer can call noise. "Odd states", "anything that looks broken" and "key screens" are undefined, so report ordering is arbitrary.
Question: For each step of each flow, what value or behavior proves it worked, and how is that read off the screen?
Do: Extend the flow schema with an `expect:` block per step and per checkpoint evaluated from the Oracle extraction: `{region, equals | matches | within tol | present | absent | changed_since_previous_step}`, with regions as named rectangles anchored to landmarks (G25) defined once per workspace. An assertion failure is a hard FAIL independent of the pixel score, and the report shows expected versus extracted versus native crop. Minimum coverage: symbol, side, qty, order type, price, TIF, routing, the confirm dialog's cost, buying-power effect and max loss, the absence of the Send button under the cursor, and an empty ticket after Cancel. Add a criticality tier per checkpoint (tier 1: order ticket, Confirm and Send, positions, balances). Pass the last few actions, the expectations, the tier and the mask list to the reviewer as text and require structured output answering two questions separately: does the candidate satisfy the expectations (absolute), and how does it differ from baseline (relative). Replace "key screens" with an explicit list and the reason each is key.

**The reviewer has no source of intended changes, so "expected UI change" is a guess (G30)**
What conflicts: "It sorts each difference into bug, expected UI change, noise or needs-a-human" with inputs limited to the baseline, the new screenshot and the heatmap. Nothing ingests release notes (published per build at toslc.thinkorswim.com/center/release, pages of the form `rel-MM-DD-YYYY`), Jira tickets with fixVersion equal to this build, design mocks, feature-flag diffs or a touched-screen list, and nothing maps them to checkpoints. The reviewer will classify by plausibility, cannot tell a half-implemented intended change from a finished one, and the newest code, where release bugs cluster, has no flow at all. Without evidence it either flags every intended change (unreadable report) or rationalizes real bugs as intended (a Buying Power Effect line moved out of the confirm dialog labeled "dialog restyle" at 0.9 and then baselined). Public notes are coarse and published at release time, so an outside team may not have them before testing.
Question: For each build, where will the list of intended changes come from (ticket export, release-notes draft, feature-flag diff), can you get it before the build is tested, and who owns mapping each change to the screens and checkpoints it touches?
Do: Make a per-build change manifest a required run input (YAML next to the flows): `{id, source: ticket key or release-note line, summary, affected panels or checkpoint IDs, expected_visual text and/or mock image, feature_flag}`. Build it from the internal ticket export when available and from the public release-notes page otherwise, with an LLM proposing the entry-to-checkpoint mapping and a human approving it. At review time inject only entries whose panels intersect the checkpoint, with mock images as extra image blocks. Enforce via structured output: "expected" requires a non-null `manifest_ref`; a diff with no entry can only be bug, noise or needs-a-human; a diff on a panel the notes do not mention gets a higher bug prior. For each manifest entry with no covering flow, draft a flow stub via agent mode and queue it for approval before the baseline is captured. When no manifest exists for a build, disable "expected" entirely and route everything through needs-a-human until the notes are ingested.

### Version, state and configuration determinism

**Launcher auto-updates every start; version under test is unpinned, unread and can change mid-run (G13)**
What conflicts: "The approved 'known good' screenshot for every checkpoint, saved per app version" assumes the version is known and stable. Schwab's own install guide says thinkorswim checks for updates every time it starts; no documented pin or rollback exists; the updater shows What's New, agreement and restart dialogs on first launch. The spec never says how the version is read, what happens the first night after an update (no baseline for the new version), what the diff engine does when the version changed overnight or between parallel workers, or that server-side changes alter the UI with no client version change. A run that silently updated diffs a new build against an old baseline and floods the report; a run that silently tested yesterday's build gives a false "release is clean"; an approved baseline is unreproducible the moment the machine updates.
Question: Can you install a pinned build, or do you only ever get whatever the launcher downloads tonight, and is there a sanctioned way to stop the launcher from updating the baseline machine?
Do: Read the build from the main window title (`GetWindowText`) at launch, after every relaunch and before each flow, with OCR of Help > About only as fallback. Record build, JRE version (from the `release` file in the bundled jre folder), sha256 of `thinkorswim.vmoptions` and of the jar listing into the run row; abort with `env_error` "version changed mid-run" on any change. Keep `run_type` regression versus candidate: candidate is the first run after a build change; it dismisses first-launch dialogs, diffs against the last approved baseline in "intended change" mode, groups by widget, emits a promotion proposal instead of bug alerts, and alerts that a new build landed. Pin the baseline as a VM snapshot (the installer cannot pin a build). Use the documented second-instance install only with separate logins. For external installs do not block the update host; snapshot and let a canary update. Re-apply vmoptions after updates and confirm with the hash (updater overwriting vmoptions is unverified). Schedule a 24 h confirmation run.

**paperMoney account state drifts between runs: no dedicated account, no reset, no fixture, no owner (G44)**
What conflicts: "It can build, stage and review orders, then it cancels" and "Repeatable runs. Use the same ... test symbols every time." Each run adds rows to Activity and order history; account values drift with marks even with no fills; expirations, assignments, dividends and splits change positions; a human using the same login changes everything; options on futures may be rejected in paperMoney; nobody owns the accounts. No expected account state at checkpoint time and no reset is defined, although paperMoney's Account Adjustments offers "Reset All Balances and Positions" and "Set Account Cash to". Monitor, Position Statement, Account Statement and account-info panels differ every run for reasons unrelated to the build, so the team masks the whole Monitor tab or lives with permanent false positives, and a real wrong-sign P/L is indistinguishable from leftover state.
Question: Is the paperMoney account dedicated to the tester, does Adjust Account reset clear positions and working orders or only cash, and can the test account get real-time data and options on futures?
Do: Dedicated login per worker with a named owner. Pin the fixture account's `D-` number in config and assert the Account dropdown shows it at run start (each login has two paper accounts, margin and IRA, so the selector is a drift source). `verify_account_fixture` at run start compares Positions and Working Orders against `account_fixture.yaml`; on mismatch run Reset All Balances and Positions, Set Account Cash, and delete saved orders. Re-seeding positions requires sending paperMoney orders during market hours, which the executor must never do: make seeding a human step or a separately gated seed tool on a different machine and profile, run once and on a calendar. Any working order found at run start is a `send_guard_breach` at top priority (an unsent staged order is not persisted and cannot fill; only a sent order can). Treat Monitor rows as data regions, OCR account-value cells with drift tolerance since marks move daily even on a closed market, and confirm empirically whether the reset clears working orders and alerts. Ask support to enable options on futures for the test login if those flows are needed; mark them unsupported until then. Do not rely on Guest Pass logins for this.

**"Same workspace every time" has no restore mechanism; most state lives server-side on the login and drifts (G46)**
What conflicts: "Repeatable runs. Use the same screen resolution, DPI, theme, font size, workspace layout, window size and test symbols every time" lists what must stay fixed but gives no restore step, verification, hash, or protection from a human or crashed run changing it. thinkorswim keeps custom studies, scans, watchlists, chart settings and drawings, alerts, saved orders, most Application Settings, order defaults and Favorites on the account (persisted at change time, not on exit), plus a local usergui folder with window geometry, column widths, cache and launcher properties; saved workspaces are stored locally (which is why tos.mx sharing exists) and a workspace file does not carry studies or scans. A single flow that adds a drawing, resizes a column or detaches a panel permanently shifts every later checkpoint, and a fresh VM image with the same login still inherits the previous run's server-side state.
Question: Which parts of thinkorswim state live on the server for the login versus on disk, and which of them does a VM snapshot revert not touch?
Do: Split the state model. Local, restored by a VM snapshot revert: the saved workspace file (`workspace.<name>` in the install folder next to usergui), the usergui folder and `thinkorswim.vmoptions`. Server-side on the login, not restored by a revert: studies, scans, watchlists, chart settings and drawings, alerts, saved orders, Application Settings, order defaults, Favorites. So: check the workspace file, vmoptions, study and scan exports and the tos.mx link into the repo; before launch, copy the checked-in workspace file into the install folder and hash it (more deterministic than loading by name through the UI); after login run a scripted server-side reset (re-apply Application Settings from a checked-in profile, delete non-fixture watchlists, clear drawings on fixture symbols, delete alerts and saved orders, re-import studies and scans); screenshot the Setup dialogs and take a tight-threshold `profile_clean` checkpoint. Killing the process at run end prevents only local workspace autosave, which the revert already handles; the explicit server-side teardown is what matters.

**Explorer shares login and profile with scripted flows and its mutations persist into every later run (G47)**
What conflicts: "A free-roam agent that tries edge cases: odd inputs, rapid clicking, resized windows" versus "Use the same ... theme, font size, workspace layout, window size ... every time." The Explorer mutates layout, columns, font size, theme, settings including safety-relevant ones, watchlists, alerts and drawings. Layout is local and a snapshot revert removes it; settings, watchlists, alerts, drawings and studies persist to the login immediately, so a forced process kill does not undo them. One Explorer session that changes the font size moves every pixel of the next scripted run, the diffs get promoted as a new baseline, a real column-width regression two weeks later is absorbed, and the layers the never-send rule depends on can be silently removed.
Question: none beyond G05 and G46; the decision is structural.
Do: Run the Explorer under its own login (its own paperMoney accounts) and its own VM snapshot, scheduled last and never in the same session as scripted flows. Run the server-side teardown from the Explorer's mutation ledger after every session. Add a hard deny list that goes beyond Send: never open Application Settings > Order defaults or confirmation options, never toggle Active Trader auto-send or one-click ordering, never change the account selector. Assert at the start of every scripted run that the confirmation dialog is still required (a flow that builds an order and checks the confirm dialog appears before cancelling). Combine with the G05 deny list.

**One canonical display configuration means theme, DPI, font size, window size and multi-monitor are never tested (G58)**
What conflicts: the "Repeatable runs" constraint fixes one resolution, DPI, theme, font size and window size and never says a second tier exists. Light theme, Windows scaling at 125/150/200% (the laptop default), the app's own font-size setting, restored or snapped windows, 1366x768 laptops, 4K monitors and mixed-DPI dual monitors are never rendered. HiDPI is where Swing tends to clip text, truncate headers and produce dialogs taller than the screen (a general Swing pattern, not a documented thinkorswim defect, so a reason to test rather than evidence of a bug). Regressions that appear only in Light theme or at 125 to 150% ship with a green report, and single-config green is read as universal.
Question: Which scaling, theme and resolution combinations do your users actually run (from telemetry or support tickets), so Tier B is weighted rather than exhaustive?
Do: Tier A stays the pinned canonical config. Tier B per release candidate on 15 to 20 smoke flows across a short list: 1920x1080 at 100% light, 1920x1080 at 125% dark, 2560x1440 at 150%, 1366x768 restored window, app font size large. Defer mixed-DPI dual-monitor to a physical machine (not dependable inside VMs) and drop Windows High Contrast (it does not restyle thinkorswim's custom Swing look and feel). Tier B checks, in order of reliability: window and dialog rectangles fully inside the virtual screen (pywinauto rect), expected controls present by template match at the config's scale, no horizontal clipping of a fixed list of header labels (OCR of named labels, not generic word boxes), and a VLM "same content, different rendering" comparison against the Tier A shot. Key baselines by `(checkpoint_id, config_hash)` so a cell can graduate to pixel diffing once stable. Relaunch the app after any scaling change. Note that an off-screen Send button cannot be mouse-clicked, so off-screen dialogs do not defeat the cursor guard; keyboard activation does (G01).

**macOS and Linux thinkorswim users are silently out of scope (G59)**
What conflicts: "This is an automated testing system for a Windows desktop trading app" scopes to Windows without saying so as a non-goal. thinkorswim officially supports macOS 14+ and Linux (Zulu OpenJDK 21) from the same Java codebase with a different JVM, the macOS menu bar, Cmd-versus-Ctrl hotkeys, Retina 2x scaling, Apple Silicon, macOS permission prompts (Screen Recording, Accessibility) and macOS point releases that can break Java rendering. The system would report "no issues" with zero Mac coverage.
Question: What share of your users run macOS? Above roughly 10% the Mac runner is not optional.
Do: Phase 1: write "Windows only" as an explicit non-goal and record the macOS/Linux user share. Phase 2 only if that share is material: one Mac mini on a pinned macOS version (Tart on Apple Silicon can give VM-style snapshots), Screen Recording and Accessibility pre-granted, Retina plus one 1x external display. Only pyautogui/mss image-based steps port as-is; pywinauto and Java Access Bridge do not exist on macOS, so accessibility steps need a separate implementation (Java's NSAccessibility bridge via pyobjc/atomacos). Window enumeration via Quartz; Cmd-versus-Ctrl mapped per OS in the flow runner; a separate baseline namespace per OS. Smoke set: install and launcher update (thinkorswim on Mac updates through its own launcher, not a dmg), login, workspace load, Charts, option chain, Confirm and Send then cancel, detach and reattach, Cmd hotkeys. Skip Linux unless users exist there.

### Vendor dependency

**Model API outage, throttling or deprecation leaves no degraded mode (C01)**
What conflicts: agent mode is the fallback for scripted failures, but it depends on the same external API as the reviewer, so the fallback is unavailable exactly when the vendor is. The spec never says what a run does when the API is down, returns 429s or is slow during the 2 to 6 am window; reviewer calls appear to run synchronously inside the run; there is no pinned model ID in config and no watch on the deprecation calendar (Anthropic's published policy is at least 60 days' notice before retiring a public model, and the computer-use tool schema has changed across four tool-type versions, with hard 400s on the older type for current models). One API outage the night before a release means no report at all and nobody is told why; an agent fallback that loses the API mid-flow leaves a half-built ticket on screen with no one driving.
Question: If the model API is unreachable at 3 am the night before release, what does the morning report say and who finds out?
Do: (1) Make review asynchronous and idempotent: a run must reach "captured+diffed" and publish a report in state `unreviewed` with zero model calls; a separate reviewer job consumes a queue keyed by `(run_id, checkpoint_id, diff_hash)` and can be re-run hours later. (2) Submit reviewer work through the Message Batches API (one batch per run, `custom_id` = checkpoint id, results keyed by `custom_id`, resubmit on `expired`); batch turnaround is "within 24 hours", so keep a synchronous path for the smoke tier and a deadline fallback. (3) Pin full model IDs and the computer-use tool type per component in config and stamp them on every verdict; preflight calls `GET /v1/models/{id}` and a 1-token message before the run, and a failure flips agent fallback OFF so scripted failures are reported as "scripted-failed, not recovered" instead of hanging. (4) Subscribe to deprecation announcements, open a migration ticket on notice, and re-run the G36 eval on the replacement model before switching. (5) For the agent path keep a small concurrency semaphore with exponential backoff on 429; the SDK already retries 429/5xx twice by default.

## 3. Gaps that would make the system miss bugs

Ordered critical, high, medium; no low-severity gap falls in this section.

### Critical

**No access to pre-release builds or build-pipeline trigger; "no issues once released" is unachievable post-release (G12)**
The spec never says which build gets tested or when. For a retail install the app on the machine is the version already shipped to every user; there is no statement that the team receives release candidates, no trigger from the build system, no release train the run must fit, and no public beta channel was found (Guest Pass is a 30-day trial, not a beta). If the first time this system sees version N is the night after N shipped, it is a post-mortem tool, and the project's value gets argued down the first time a real regression is found a day after users hit it.
Do: Make the build identity an explicit run input (RC build number or installer drop path, or "whatever the launcher pulled tonight") and write both modes into the spec. Internal: trigger from the build pipeline or an RC-artifact watcher; the gate is "run complete and triaged N business days before GA with a named sign-off". External: say so plainly, reframe the goal to "detect within the first closed-market window after release", pin the team's own desks at the last-passed build via a VM or install-folder snapshot, and run a canary machine that updates first. Ask thinkorswim support whether any early-access program exists rather than assuming one does.

### High

**Upgrade-in-place over real user profiles and fresh install are never exercised (G14)**
"Same config every time" implies a pristine canonical profile, so the tester never sees an old-version usergui folder (settings, saved workspaces, custom thinkScript studies, hotkeys, detached-window geometry, order templates, watchlist columns) loaded by the new build on first launch, a fresh install from the public installer, or the workspace-conversion warnings and re-accepted agreements on that path. "My layout/studies/hotkeys are gone" and "app won't start after the update" exist only on the migration path, so a clean-profile tester is structurally blind to them (how large that complaint class is remains unverified).
Do: Maintain VM snapshots at N-1 and N-2 (installers cannot pin a version; the snapshot is the pin), each with a profile library dropped into the install's usergui folder (canonical; default; power-user with many workspaces, detached windows, a full hotkey map, custom order templates and watchlist columns) and a matching account-side fixture on the login (studies, watchlists, alerts; these are reported to be server-side, so split local usergui diffs from account state). On release night, for each snapshot: boot, capture every workspace pre-update, launch and let the updater run with a hard timeout, screenshot every first-start dialog, reload the same workspaces, diff pre versus post as a cross-version diff, and diff the usergui files for dropped keys. Add a fresh-install flow from the public installer on a clean snapshot and treat installer, updater and first launch as its own flow with checkpoints. Snapshot after each update so the build under test stays pinned.

**App logs and Java exception dialogs are not an input to the reviewer (G41)**
thinkorswim writes its own client logs, but the spec never tails them, never attaches the slice between checkpoint timestamps to the checkpoint record, never feeds them to the reviewer, and never treats a Java exception dialog as a terminal state. A NullPointerException thrown while building an order ticket can leave the screen looking fine with one field silently defaulted; a stack trace pinpoints a regression where the screenshot is a blank panel the reviewer must guess about.
Do: Locate the log directory once on the reference image and pin it in config (community reports disagree between `C:\Users\<user>\thinkorswim\logs`, the Program Files install folder and `%LOCALAPPDATA%\thinkorswim`; confirm on the actual build). Tail with a file watcher, stamp lines with run, flow and step, store the slice per checkpoint in SQLite. Build exception signatures from normalized stack traces (exception class plus top 3 app frames, line numbers stripped) and diff per version; a new signature is needs-human, with an allowlist for known noise. Capture JVM crash files (`hs_err_pid*.log` lands in the JVM working directory unless `thinkorswim.vmoptions` sets `-XX:ErrorFile`) and enable Windows Error Reporting LocalDumps for the launcher so native crashes leave a `.dmp`. Template-match the exception dialog and mark the flow `crash` with the log excerpt, separate from visual diffs. Do not key "environment invalid" on a Delayed indicator: paperMoney is 20-minute delayed by default, so that is the normal state; key it on Disconnected or reconnect loops, auth/token failures and OutOfMemoryError, and treat delayed/real-time as a pinned fixture value. Expect log format drift between versions; version the parser and fail soft.

**Network degradation, disconnect/reconnect and backend maintenance are not modeled or detected (G43)**
Nothing exercises slow links, packet loss, a disconnect mid-flow, reconnect, session expiry, or distinguishes "the backend is down" from "the app is broken". Disconnect handling (stale data shown as live, working orders not reloaded, a ticket silently failing) is a classic regression that appears only under bad network, and a single run inside a maintenance window floods the report with environment false positives (maintenance is reported on Saturday nights, not every after-hours window; no published schedule exists).
Do: Preflight gate: login OK, pinned quote fresh relative to the login's data entitlement, no Disconnected indicator; otherwise mark the run environment-invalid and reschedule. For the chaos suite, clumsy filters at the WinDivert layer work by IP and port, not process, so either run the harness controller inside the VM and shape all outbound 443 traffic, or exclude the harness and RDP control channel by address; use a Windows Firewall outbound block rule on the thinkorswim executable for the hard disconnect. Do not assert "cancel a staged order during disconnect": a staged order exists only client-side and was never sent. Assert instead that the status-bar indicator changes, quotes and chains are flagged stale rather than silently frozen, symbol change and chain load during disconnect show a clear error state, and after reconnect quotes resume and Monitor and Working Orders reload without duplicate rows. Keep a maintenance calendar seeded from community-reported windows and refined from your own preflight failures. paperMoney uses production servers, so expect "no" to the staging-backend question but ask it.

**"Odd inputs" have no corpus, no seed and no expected-response rule (G56)**
"Odd inputs" and "unusual option strikes" are left to the agent's imagination with no corpus, no seed, and no statement that a validation message after bad input is the correct outcome; as written, errors are logged as broken. Every "Invalid symbol" dialog becomes a reported bug while real failures (bad input accepted silently, NaN rendered, a field reverting to a third value, `150,50` parsed as 15050) go unflagged, and the agent picks the same handful of inputs every night.
Do: A versioned corpus with a pass/fail rule, each entry scoped to a pre-Send surface and what is observable there: symbol box (nonexistent, delisted, Unicode, 200 chars, format strings, BRK/B, a symbol with no options), order-entry fields (`0`, `-1`, `0.5` shares, `1e9`, `150,50`, `$1.00`, scientific notation) checked by the field's rendered value, the Confirm and Send dialog's displayed quantity, price and Buying Power Effect, Analyze tab price and date inputs, and study parameters including a thinkScript compile error. Pass = visible rejection or a clamped value shown; fail = crash, freeze, silent acceptance, NaN/Infinity/null, or a field showing a third value. Because Send is never clicked, server-side rejections (buying power, price far from market, exchange quantity rules) cannot be exercised; phrase the rules against client-side validation only. Schwab does not take fractional-share orders on the desktop platform, so `0.5` shares is a rejected expectation, not an edge case. Drop "a halted stock" from the nightly set or source it from the day's halt list. Sample with a logged seed so each night covers new items.

**No coverage matrix of surfaces, no persona-shaped flows, no usage- or ticket-weighted ordering, no coverage measurement (G57)**
"A set list of workflows" never enumerates thinkorswim's surfaces, how flows are chosen or ordered, or how coverage is measured. Flows mirror the author's own habits; free roam revisits Trade and Charts and never opens Scan > Stock Hacker, Risk Profile, the thinkScript editor or right-click menus; "any and all users" cannot be claimed without knowing what percentage of tabs, dialogs and controls were exercised.
Do: Add a surface x persona matrix (tab x sub-tab x asset class x order type x strategy; personas: options, futures, forex, swing, beginner, power user, each with its own symbol zoo) as an appendix, make persona and surface required fields on every flow, and report pass rate and NOT COVERED cells per persona. Weight rows by ticket volume if internal; if external, by release-note mentions and a short list of highest-traffic surfaces (Trade order entry, option chain, Charts, Monitor Activity and Positions, Analyze). For coverage measurement do not depend on a JAB crawl (exposure is unverified): build the control inventory as a curated list per surface (tabs, sub-tabs, right-click menus, dialogs) and mark each item visited when a checkpoint or agent action lands on it, identified by template match or OCR of the active tab label. Print "changed per release notes but no flow covers it" as a red row and gate the release on critical-area coverage.

**One test account means one entitlement profile; paperMoney cannot represent account types and is not the live product (G60)**
paperMoney gives a simulated margin account and IRA with every strategy, futures and forex enabled. It never produces option approval tiers and "not approved" dialogs, cash-account unsettled-funds warnings, the pattern-day-trade counter, Reg-T versus portfolio-margin buying power, Trade-tab states when futures or forex are not enabled, or multi-account households. A panel the account lacks shows a placeholder that gets baselined as correct. The order ticket, Confirm dialog, buying-power fields and Monitor branch on entitlements, which is where wrong numbers live.
Do: Add an entitlement matrix and tag every flow with `requires: [margin, options_L2, futures, forex, ira, portfolio_margin, multi_account]`; the Reporter prints a coverage-by-entitlement table with NOT RUN cells, never "passed", for profiles the available login cannot reach. If internal, request fixed-entitlement test logins and rotate the suite across them. If external, run on both paperMoney accounts (the IRA exercises the no-short, no-margin branch), verify in-platform whether paperMoney reflects the live login's option level and PDT counter after the Schwab migration (unverified), and publish a paperMoney-versus-live known-gaps list in every report (20-minute delayed data by default, simulated fills, no real rejections). Add paperMoney-specific flows: the paperMoney badge, Adjust Account and reset, switching between the two accounts.

**Order ticket defaults are overwritten before the screenshot is taken (G64)**
Flows type qty, price and TIF into the ticket and then checkpoint, so the ticket's initial state from each entry point (default quantity, order type, price basis, TIF, routing, Setup > Order defaults, the Active Trader tab's own default quantity) is never captured or asserted, and one pinned workspace means one of many default profiles. A release that reset the option-order default quantity from 1 to 10 when opened from the chain would pass because the checkpoint was taken after the flow typed `1`.
Do: For every ticket entry point add a pre-input checkpoint immediately after the ticket appears: OCR qty, order type, price, TIF, routing and link fields from fixed crops (upscale 3x, threshold; verify the OCR once per build against a known ticket) or read them via JAB, and assert against expected values declared in the flow YAML. Run the set under three Order Defaults profiles applied by scripted steps in Setup > Application Settings > Order Defaults at run start (fresh-install defaults; power-user with custom quantities per asset class, TIF and order type; and the Active Trader default quantity, which is a separate setting), capturing the settings dialog as its own checkpoint. Order Defaults are per asset class (stocks, options, futures, futures options, forex), not per symbol, and there is no export, so profiles are applied through the UI or by copying the user settings directory. Treat Position Statement > Create closing order as its own flow asserting full position quantity on the opposite side. Assert the ticket after a cancelled order to catch sticky last-used behaviour (unverified whether it exists), and include "clear order details after sending" and "Shift+click to send" in the pinned profile.

**Charts and studies (including custom thinkScript) are diffed on data that changes nightly and never asserted numerically (G65)**
Chart and study checkpoints differ every run because a new session was appended, so they get masked or classed as noise; there is no fixed-data mode and no assertion on study output, including custom thinkScript, a major reason people use the platform. A data-format change that made volume-based studies read volume as zero while the chart still drew a plausible line would sit under "noise" for weeks.
Do: Run charts in two modes. (a) Frozen: enter OnDemand at a fixed historical timestamp with playback paused, mouse parked off-chart, fixed symbol, aggregation and lookback, and pixel-diff the chart with no mask; choose symbols without splits or dividend adjustments in the window, and re-baseline deliberately when the data vendor issues corrections. OnDemand uses its own demo account, is memory intensive, can stall in prebuffering, and scans do not work in it, so budget extra launcher memory and give it its own timeout and retry. (b) Live-data after the close: daily aggregation with a fixed lookback, mask nothing, assert numerically. In both modes add a verification study that `AddLabel`s close, volume, SMA(20), RSI(14) and VWAP at the last bar plus the Data Box, OCR the labels, and compare against an independent oracle: the Schwab Trader API price-history endpoint (independent of the client's chart pipeline, so a client-side volume=0 bug is caught) or, failing API access, raw close and volume labels of the last N bars recomputed offline for self-consistency. Keep a corpus of custom thinkScript studies covering `fold`, secondary aggregation periods, cross-symbol references, `GetValue` and option functions, plus one with an intentional compile error, with expected label values pinned per OnDemand timestamp. There is no direct chart-data export; intraday history is capped at roughly 30 to 45 days of 1-minute bars.

**No synthetic-fault canaries prove the detector still sees a missing button (C02)**
Nothing continuously demonstrates that the diff engine, masks and reviewer together can still detect the defect classes the spec exists for. G36's eval set tests the reviewer offline and G66's backtest is one-time; neither is a nightly, end-to-end, known-answer check. Detectors degrade silently: masks grow, thresholds get raised after a noisy week, a mask drifts over the Send button, a DPI or JRE change alters the downscaled image the reviewer sees, a prompt edit makes it more forgiving, a vendor model update changes behaviour. A green report from a blind detector is worse than no tool because people act on it.
Do: Keep a 20 to 30 item mutant catalog bound to critical checkpoints (order ticket, Confirm and Send dialog, Position Statement, option chain, Account Info), generated deterministically from the approved baseline with a fixed seed: erase a button, substitute one digit in a P/L or Buying Power Effect cell, flip a green value to red, shift a panel 2 px, truncate a column header, swap the BUY/SELL label. Inject them as extra candidate images through the normal diff, mask and reviewer path, flagged `synthetic=true` in SQLite so they never promote a baseline and never count in G66 metrics. Score recall per defect class; a miss in a critical class sets run status `detector-degraded` and alerts; a miss elsewhere lowers a printed recall figure in the report header. Add two behavioural mutants that exercise the real app (type the wrong quantity; leave a field blank) so capture is covered too. Re-run the catalog as a gate whenever masks, thresholds, the prompt or the pinned model ID change.

### Medium

**Full-window pixel/SSIM scores rank the bugs you care about backwards (G27)**
The spec does not say how a difference is segmented or whether pass/fail is per window, region or element. A missing 20x20 px button is 0.011% of a 1440p capture; a wrong digit is a 5x7 px change; meanwhile a one-pixel layout shift, a chart repaint or a grid scrolled one row dominates any whole-window score. Window-averaged scores are tuned by big legitimate changes and blind to the small, high-value ones section 1 lists as the point of the project.
Do: Score at three levels and gate on the strictest: full window only for translation and layout-shift detection; named regions (order ticket, chain header, account summary, each toolbar) with their own thresholds and A/A floors; and connected components (pixelmatch-style binarization with anti-aliasing tolerance, dilate, label, record bounding box, area and owning region). Any component the size of a text run, icon or button fails the checkpoint regardless of the global score. Estimate pure translation first and report "layout shift dx,dy" as its own finding rather than a pixel storm. Compute per-channel or CIEDE2000 difference so colour-semantic flips register (thinkorswim's green and red differ in luma, so grayscale SSIM does see them; dilution by averaging is the real failure). Add template-presence checks for must-exist controls (Send, Cancel, tab names). Hand the reviewer native-resolution crops per component with the region name, never the downscaled full window.

**Announced changes that never appear go unnoticed (no reverse reconciliation) (G31)**
The reviewer only examines diffs that occurred. If release notes say "Position Statement adds a Day P/L column" and no checkpoint changes, there is no signal that the feature failed to ship, is behind a flag, or sits on a screen the flow library never visits. The report says "no issues" for the wrong reason.
Do: Tag every checkpoint with the panels and gadgets it shows (a short list in the flow YAML). For each manifest entry (G30), require at least one checkpoint tag that should reveal it; if none exists, emit "no covering checkpoint" as a flow-authoring task. For entries with a covering checkpoint, send the entry text plus that checkpoint's baseline/new pair to the AI reviewer with a narrow question ("is this described change visible: yes/no/unsure, where?") rather than an OCR assertion language; route "no" and "unsure" to a human and the feature owner. Print manifest coverage (entries verified over total) in the report. Add OCR assertions only for the few numeric or text checks that recur every release (column headers, balance labels), using 3x upscaled crops, since OCR on thinkorswim's small default fonts is unreliable otherwise.

**No performance budgets, no long-session soak; leaks and 6-hour failures are never seen (G42)**
Nothing measures login-to-workspace time, chart load, SPX chain load with All strikes, tab switching, idle CPU, process memory, thread count or GDI/USER object counts, and every flow is a short path from a fresh launch. Java desktop regressions are often performance regressions, and some become visual only after exhaustion: a GDI leak hitting the 10,000-object quota after hours renders blank panels, while a 45-minute run never gets close; a 2x slower chart load ships because the orchestrator's timeout is generous.
Do: Keep an OS-level sampler (psutil private bytes, working set, threads, CPU; `GetGuiResources` GDI/USER) and a per-version "time to stable screen" metric, computed on the masked image (futures, forex and clock regions tick around the clock, so an unmasked hash never settles). Treat `jcmd` as optional: thinkorswim ships its own runtime (reports say Java 17/21), so you need a matching-major JDK on the VM and attach must not be disabled in `thinkorswim.vmoptions`; if attach works, use `jstat -gc` or `jcmd GC.heap_info` without `GC.run` during timing flows, and `GC.run` only at soak checkpoints. Schedule the soak Friday after close into Saturday rather than the whole weekend, since community reports place maintenance on Saturday nights, and tag any disconnect during a known window as expected. The soak runs against a closed market, so quote-update load is absent; it still catches UI-driven leaks (chart open and close, tab switches), the dominant GDI case. Use a linear-fit slope with a minimum duration, not single-sample thresholds. An inactivity auto-logout is unverified; let the soak discover it and then pin it as an expectation.

**An empty paper account hides populated-state bugs; no golden portfolio (G45)**
Real accounts carry 50 to 300 positions, multi-leg option positions, expired and assigned contracts, dozens of watchlists, hundreds of alerts and custom studies. The Explorer covers empty states; nothing defines a populated state, so seven-digit P/L overflow, negative-number formatting, row virtualization and scrolling, group-by headers, Account Statement pagination and slow rendering with 300 rows are invisible.
Do: Use the two paper accounts every login already has: margin = GOLDEN (populated), IRA = EMPTY (visual suite); fall back to a second login only if IRA restrictions (no futures, forex or margin buying power) get in the way of empty-state flows. Seed the golden portfolio by a named human during market hours from a checked-in list (equities spanning sub-$1 and $1000+, multi-leg option positions, a LEAPS, futures, forex), and schedule re-seeding on an expiration calendar with expiration day itself as a checkpoint; paperMoney orders fill only when the market is open, so seeding cannot be part of the after-hours run. Drop "years of Account Statement" and "adjusted options after a split" from the fixture: you cannot manufacture history in paperMoney and its corporate-action handling is unverified; let history accumulate and treat the Account Statement as a date-range data region rather than a pixel baseline. For the 300-row scaling case, a populated watchlist (server-side state, seedable without any order) covers row virtualization and scrolling.

**No path from a confirmed Explorer finding to a permanent scripted regression flow (G54)**
The flow library and the Explorer have no arrow between them; nothing turns a confirmed exploratory finding into a scripted flow with a checkpoint and baseline, so the same bug is re-found by chance or missed next version and the Explorer's cost is paid every night for one-shot value.
Do: On a confirmed finding, auto-emit `flows/quarantine/<finding-id>.yaml` directly from the action trace since the last named stable state, each step anchored by the click-point crop (template match) with window-relative coordinates as fallback, a checkpoint at the failing screen and the violated invariant as the expected result. Replay it once end-to-end to confirm it reproduces. Do not run delta debugging by default: each probe is a multi-minute relaunch against a nondeterministic session, so allow only an optional bounded mode (at most 8 replays) for long traces. A human trims and promotes; the first baseline is captured on the next good build. Dedup by `(panel, invariant, element-or-crop-hash)`.

**Keyboard-only paths, hotkeys, tab order and accessibility have no path through the tester (G61)**
Scripted mode sends clicks and keystrokes, but there are no keyboard-only variants and no focus assertions: default and user-assigned hotkeys, Tab order inside the ticket and confirm dialog, Enter/Escape semantics, arrow-key quantity increments, and the accessible tree are not in the flow model. A tab-order change is invisible in a screenshot; a release that reordered focus so Tab from Quantity landed on Order Type would make keyboard users type their limit price into the wrong field while every screenshot was pixel-identical.
Do: (1) Extend the never-send gate to the keystroke layer: while the order-confirmation dialog is the foreground window (detect by top-level window title), the key sender drops Enter, Space and any order shortcut and logs the attempt; also turn on "Shift+click to send orders" on the rig so a plain click or Enter cannot send. (2) For each ticket flow add one keyboard-only variant (Tab, Shift+Tab, arrows, Enter, Escape) that asserts the focus owner after each key: via JAB if the bundled runtime ships `jdk.accessibility` (enable with `jabswitch -enable` or `JAVA_TOOL_OPTIONS=-Djavax.accessibility.assistive_technologies=com.sun.java.accessibility.AccessBridge`), else a before/after Tab screenshot diff located against the declared control rectangle. (3) Build the hotkey inventory by hand from Setup > Application Settings > Hot Keys (screenshot and OCR it once per build; no export exists), fire each default hotkey and assert the expected panel or dialog; re-OCR per build to catch default-binding changes. (4) Test that Escape closes every modal under the gate. (5) Replace Windows High Contrast (ignored by the custom look and feel) with the app's own Look and feel options, Light, Dark and the "high contrast colors" toggle, as Tier B cells. (6) If JAB works, store the accessible tree per checkpoint and diff it build to build (names lost, roles changed, tab-order sequence changed). Whether Enter on the confirm dialog activates Send is unverified; treat it as if it does.

**Locale, time zone, number format and DST are pinned to the author's values and never varied (G62)**
The rig is implicitly en-US in Eastern time. The app's time-zone setting versus the OS zone, Pacific, Hawaii, Arizona and Asia-Pacific users, DST transition weekends, non-English UI, decimal and thousands separators, date formats and 12/24-hour clocks are not a test dimension. Session shading, pre/post-market boundaries, "today" P/L rollover and alert timestamps are locale-dependent, and a DST weekend can put a wall-clock-scheduled Monday run inside the open.
Do: Pin the canonical rig to America/New_York at both OS and app level and schedule runs with an exchange calendar library (`exchange_calendars` or `pandas_market_calendars`) rather than wall-clock cron, with a pre-run market-open check. Add exactly one Tier B time-zone cell (app time zone = Pacific, OS tz switched with `tzutil /s`) running the chart time-axis, session-shading, Position Statement "today" P/L and alert-timestamp flows with OCR assertions that displayed times equal the expected conversion, with its own small baseline set. Use OnDemand at the most recent DST-change Friday close and the following Monday open to assert chart shading boundaries in both zones (OnDemand replays market data only; it does not change the client clock or the scheduler). Add OS-locale cells (de-DE comma decimals, en-GB day-first dates) only if the organisation has non-en-US users, limited to the ticket and confirm dialog with an OCR check that the staged value equals the typed value; whether the app honours the OS number locale at all is unverified. The exact location of the app's time-zone setting is unverified (charts have a separate time zone in chart settings).

**Hardware and graphics-stack personas (D3D vs software pipeline, low memory) are never varied (G63)**
thinkorswim renders through Java2D, whose Direct3D, OpenGL and software pipelines behave differently per GPU driver; the community fix for garbled graphics is disabling D3D. Users run old laptops with integrated GPUs and 8 GB RAM, 4K displays, RDP/Citrix sessions and the app's own memory setting; the canonical baseline may be rendered on a stack no user has, and the pipeline may be auto-selected differently under RDP or a VM.
Do: Day one, pin the rendering pipeline on the canonical rig by writing the Java 2D flags (`-Dsun.java2d.d3d=false` or `=true`, plus `-Dsun.java2d.noddraw` as needed; Oracle documents these as implementation-specific and subject to removal) into `thinkorswim.vmoptions`, record the active pipeline per run (`-Dsun.java2d.trace=log` or a startup screenshot of Help > System), and refuse to diff against a baseline captured with a different pipeline; prefer a GPU-backed physical box or a VM with a real display adapter. Tier B: one cell with the opposite pipeline, its own baselines, weekly rather than nightly. Low-memory cell: set the launcher memory to its minimum (the memory setting lives in the login-screen Setup button and in vmoptions `-Xms/-Xmx`, not Application Settings), load the Flexible Grid chart workspace, add `-Xlog:gc`, and record time to first quote (OCR poll of a quote cell), steady-state RSS via psutil, GC pause totals, and UI freezes detected by screenshot staleness (a ticking clock region stops changing) rather than `IsHungAppWindow`, since a blocked Swing EDT does not reliably mark the AWT window as hung.

**Noise verdicts ratchet masks toward blindness; no masked-area budget or expiry (C03)**
The feedback path from a verdict ("noise", "expected") to the masks and thresholds the next run uses is undefined, and however it is built, nothing bounds it: no cap on how much of a checkpoint or a critical panel may be masked, no per-checkpoint effective-sensitivity number, no expiry, no owner or reason, no report of mask growth. Masks are the one knob that makes a noisy night quiet, so they ratchet in one direction; after three months a large share of the Trade tab is masked and nobody notices the suite has gone blind until a user does.
Do: Store masks as versioned records (anchor per G25, owner, reason, `created_by human|ai`, `created_run`, `expires_at` default +30 days). Compute masked-area percent per checkpoint and per named critical panel every run and fail the run with "mask budget exceeded" above a configured ceiling (for example 10% of Confirm and Send, 0% over Qty, Price, Buying Power Effect, account number). AI verdicts may only propose a mask; a human approves it in the report. Expired masks are re-evaluated against the A/A noise floor (G26) and re-approved or dropped. Emit a weekly mask-growth line in the report. Where a mask would cover a numeric cell, prefer a numeric assertion with tolerance from the CSV/clipboard oracle (C05) or OCR (G28) so the value is still checked. Pair with the C02 mutants so a mask that swallows a critical cell is caught the same night.

**CSV exports, clipboard and saved files are an unused deterministic oracle (C05)**
thinkorswim produces text artifacts that are not pixels: Export to File from the Account Statement (confirmed), copies from grids to the clipboard, Save Workspace As, thinkScript export. The spec captures only screenshots and the Explorer treats Export only as a hazard. Exports are a real escape class on their own (users reconcile P/L and taxes from them), and they hand the harness exact numbers the pixel path cannot read, so flows can assert arithmetic (sum of P/L Open equals the screen's Net P/L; Net Liq equals cash plus long market value minus short) and diff text against a baseline byte-for-byte at zero model cost.
Do: Add step types `export_csv(grid, path)` and `copy_grid(grid)` that write into the run folder with a content hash and redact account identifiers before storage (G07). Add a text-diff engine beside the image diff: strict equality on column set, row count and static columns; numeric tolerance on columns declared live. Let flow assertions reference CSV columns and cross-check CSV totals against the on-screen total read by the Oracle. Baseline exports per app version alongside PNG baselines so lineage is shared (G32). Hand CSV deltas to the reviewer as text context. Prefer the clipboard path for grids where Copy works and the file path for Account Statement. A "Copy All" command on grids, an export on the option chain and scan results, the saved workspace format and a chart "save image" command are unverified; confirm each on the rig. Treat workspace and thinkScript exports as hash-compare checks until their formats are confirmed.

**thinkorswim Web shares account state; unused as DOM oracle and sync check (C06)**
The spec is desktop-only and never mentions thinkorswim Web or mobile, which log in with the same account and share state through the backend (Schwab describes desktop, web and mobile as synced; the exact object list is unverified). Two consequences: a desktop release that writes malformed shared state (a watchlist, alert or saved order the web client cannot parse) breaks users who never open the desktop screen that changed, with no desktop-visible symptom; and thinkorswim Web renders the same balances, positions, working orders and quotes in a real DOM that Playwright can read in milliseconds, the independent numeric oracle G28 asks for that an outsider can actually reach.
Do: Add a small weekly cross-client sync flow: on desktop create a watchlist, alert, drawing and saved order with known names, read them back through a logged-in thinkorswim Web session (Playwright, read-only, same paperMoney login) and assert presence and content; run the reverse direction once. Before building, verify on the rig (a) whether a web login ends the desktop session (sources conflict), (b) which object types actually sync, (c) whether the web login can be automated under the G08 authorization. Use the web DOM as a numeric oracle only if (c) is cleared; otherwise use C05's CSV export as the primary oracle and keep the web check to the sync flow. Keep all web actions read-only outside the sync flow and route the web credential through the C09 secret path.

## 4. Gaps that would make people stop trusting or using it

False positives, flakiness, maintenance burden, triage and reporting. Ordered critical, high, medium, low.

### Critical

**Reviewer verdicts have no consequences, no owner, no persistence and no feedback; the same diff returns every night (G34)**
The Reporter produces a page; nothing says what a "bug" at 60% does (block, ticket, sit in HTML), who receives needs-a-human and by when, what blocks a release, how identical diffs across hundreds of checkpoints and across nights are collapsed, where a human override is stored, whether the next run honors it, how a fix is verified once a ticket is closed, or how harness failures are separated from app findings. If accepting a change does not update the baseline and marking noise does not suppress it, the same 40 diffs appear every morning; within three weeks nobody opens the report, the one real bug ships, and reviewer quality never improves because corrections are lost.
Do: Persist a per-diff state machine in SQLite keyed by a fingerprint of `(checkpoint id, mask-region or coarse grid cell, pHash of the anchored diff crop with a Hamming tolerance, category)`. On the next run matching diffs inherit the prior decision and appear under "suppressed by decision #id"; cluster identical signatures across checkpoints into one item with counts; rank by tier x confidence x novelty and cap the top section. Route by confidence but auto-file tickets only for human-confirmed bugs, or into the harness team's own queue until the reviewer's precision on the G36 eval set justifies auto-filing; when a ticket is marked fixed-in-build X the next run asserts the fingerprint is gone and reopens if not. Name a triage rotation, a one-business-day time box and a written release gate. Serve the report from a small local web app so approve, reject, noise and known-issue controls write back to SQLite. Weekly, turn overrides into eval-set entries, few-shot examples and mask proposals; track override rate per category.

### High

**No catalog or policy for the popups and interstitials thinkorswim throws on its own (G17)**
thinkorswim opens windows unprompted: Message Center, What's New after updates, price and study alerts with sound, paperMoney notices, "session expired", "already logged in from another location", MFA and device prompts, agreements that reappear after updates, surveys, delayed-data banners, Java exception dialogs. The spec never says how a flow notices one, which are dismissed silently, which abort, or that an unknown popup is itself a finding. Every popup shifts pixels (false bugs), steals keystrokes (a typed symbol lands in a dialog), and a modal left open stalls the whole night; a blocking modal on release day is also the most visible user failure.
Do: A sentinel: before every step and capture, enumerate the thinkorswim process's top-level windows, match title regex plus a small template against a versioned catalog (title regex, template, action dismiss-key/click/abort, severity), log each hit with a screenshot, and hand unmatched windows to the agent with a strict "dismiss or abort, never confirm" instruction reported as "blocked by unknown dialog". Seed the catalog from a soak run on the test account; pre-empt what you can in the golden profile (alert sounds off, Message Center detached or pinned so alerts do not pop over tabs, What's New pre-acknowledged after each candidate run). Do not add a scheduled paperMoney reset entry; no such reset is documented (reset is manual). Count popups per run and treat a spike after a release as a regression signal. "Message Center at login" and Trade Flash under Schwab are unverified; alert pop-ups as a blue box are user-reported.

**No settle/readiness rule before a screenshot; timing noise and slow loads look like diffs or flakes (G18)**
Swing exposes no "loaded" signal; charts, chains, Level II and Monitor populate asynchronously, show "Loading..." and spinners, and flash cells for seconds after data arrives. The spec takes the screenshot "at each checkpoint" with no definition of settled, so capture timing is whatever the last sleep happened to be, and a retry after a timeout silently re-runs until it passes. Half-loaded panels diff as missing widgets, the reviewer calls a spinner a bug, and a release that makes the option chain take 10 s instead of 2 is recorded as flakiness and never reported.
Do: Capture only when N consecutive frames (3 at 250 ms) are identical outside masks, must-see anchors (panel title, chain expiry header) are present by template or OCR, and anti-anchors ("Loading", "Reconnecting", spinner, empty-grid placeholder) are absent, with a per-checkpoint max wait; make any CPU threshold optional. A timeout yields "did not settle" with the last frame, never a diff and never a silent retry. Log time-to-settle per checkpoint and alert above 2x baseline p50. Turn off cell flashing and animations in the pinned workspace (the exact setting name is unverified; the behavior exists), reset scroll positions explicitly before chain and watchlist checkpoints, and auto-quarantine a checkpoint that flips three times without a version change.

**No noise floor: thresholds are never calibrated with same-build (A/A) runs (G26)**
The diff engine "outputs a score", but the spec never says what score passes, where the number comes from, or how inherent noise is measured; thresholds appear to be one global constant. A single hand-picked threshold either floods the reviewer and human with hundreds of noise diffs nightly (the team learns in week one that red means nothing) or is high enough that a missing button slips under it.
Do: A Phase 0 calibration: run the full flow library 5x on the same build inside the same quiet window, back-to-back and on a second night, and diff A against B. Store per-checkpoint and per-region statistics (pixels over a YIQ/pixelmatch tolerance, SSIM, count and largest bounding box of diff components) in SQLite. Expect a near-zero floor from a Swing app with a pinned environment: Java2D anti-aliasing is deterministic for a fixed build, font, DPI and ClearType configuration, so the real A/A noise sources are state and timing (caret, hover, tooltips, flashes, scroll and sort position, live data). Treat any checkpoint with a non-trivial A/A floor as a defect in the flow and fix the cause before considering a threshold or mask. Only then set per-checkpoint thresholds from the residual distribution plus a margin, auto-propose masks from the dilated union of A/A-changing pixels for human acceptance, and quarantine checkpoints over budget. Re-run A/A whenever a flow, mask, crop or environment fingerprint changes, keep a weekly A/A pair, and publish the A/A false-positive rate as a first-class metric.

**No baseline approval workflow or lineage; flows, masks and baselines are not versioned together (G32)**
"Approved known good" has no approver, tool, granularity (per checkpoint, flow or run), release-channel lineage, audit trail, rule for whether the AI's "expected" or "noise" verdict promotes the new image, way to revert an approval, or CI on flow and mask edits; a run cannot name the flow and mask revision it used. If a bug is approved as baseline, by a tired human bulk-approving or by the AI verdict, that bug becomes the standard and is invisible in every later release; baseline poisoning fails the project silently.
Do: Baseline lifecycle candidate, approved, retired, with approval a human-only action recorded in SQLite (approver, timestamp, checkpoint id, app version, channel, reason, ticket ref). The AI verdict may order and pre-fill the approval queue but never promotes. Approve per checkpoint or per diff-signature cluster within a flow; never "approve run". Never delete a baseline: keep every image content-addressed with a pointer to the current one, so revert is a pointer change and a run can be re-diffed against N-1 or N-2. Keep separate lineages per release channel. Version `flows/` and `masks/` in git, store baseline images in LFS or an object store with `baselines/<version>/manifest.json` in git, and record harness SHA plus manifest SHA on every run. CI on flow and mask PRs does schema validation, mask-bounds and mask-coverage-budget checks only; the smoke run of touched flows goes into the next closed-market window as a pre-merge lane, not into daytime CI, because of the market-closed constraint.

**No labeled eval set, recall metric, confidence calibration or model/prompt change control for the reviewer (G36)**
The reviewer emits a category and confidence, but there is no labeled diff set, no precision or recall per category, no calibration check, no gate that prompt or model changes must pass, no record of model ID and prompt hash per verdict, and no audit of the noise bucket. A reviewer that calls most real bugs noise produces a short, clean-looking report, the worst failure mode for this system; a model update that flips 20% of labels looks like a quieter app; a verdict cannot be reproduced when the app team disputes it.
Do: Build the eval set before tuning: an OpenCV mutation script over real captures (shift 2 to 6 px, erase a button, change a digit, clip or overlap labels, swap red and green, swap headers), A/A pairs labeled noise, and real release diffs labeled by two humans; target 300 to 500 items with tier-1 screens over-represented. Report per-category precision and recall, tier-1 recall separately, and a reliability diagram or ECE; choose routing thresholds from the curves. Gate every prompt, model, few-shot, mask or redaction change on this harness and block on a tier-1 recall drop. Run a 30-item canary at the start of each nightly run. Record model id (from the response), prompt hash, few-shot version, mask and redaction version with each verdict; pin model ids per release cycle; at borderline confidence sample three verdicts and take the majority; audit a random 5% of the noise bucket weekly. Create app-level seeded defects through the thinkorswim UI (a saved workspace with a column removed, a hotkey unassigned) rather than by editing files whose format is undocumented.

**No "not comparable" outcome and no separation of harness, environment and app failures (G37)**
The four reviewer categories assume both screenshots show the same screen in a settled state, and the orchestrator "handles retries" without classifying a run that fails before or between checkpoints: What's New, Message Center, a spinner, a tooltip, a different scroll or tab, a detached window, agent mode reaching the checkpoint by another path, login MFA, maintenance banners, black frames. Each becomes a confident "bug: panel missing" or a silently empty run. Ops spends every morning separating "the harness broke" from "thinkorswim broke", and the first developer who checks a harness artifact filed as an app bug stops trusting the rest.
Do: Give the orchestrator a gated state machine (launched, authenticated, workspace_loaded, canary_flow_passed, flows), each gate verified by an anchor-crop check; a gate failure yields `env_error` with the gate name and last screenshot, never enters the diff engine, and goes to the ops channel. In capture, add a comparability gate: window title via `GetWindowText` (no OCR needed), active tab and panel headers via template match or OCR against the checkpoint's expected screen id, a stability check, modal and popup detection against the catalog, and executor mode plus action path recorded per checkpoint. A failed gate yields the fifth outcome `not comparable` with a reason, excluded from app-bug counts. Run outcomes: `env_error`, `harness_error`, `app_crash`, `completed`; only completed runs feed regression metrics. A second login kicks the old session rather than blocking, so a crashed session does not block the next login.

**Computer-use agent cannot read thinkorswim at native resolution, and agent, explorer and reviewer have no step, time or dollar budgets (G39)**
Computer-use models work best on screenshots around 1280x720 and return coordinates in that space; thinkorswim at 1920x1080+ uses 9 to 11 px fonts in dense grids that become unreadable when downscaled, so the agent misreads strikes and misclicks by the scale factor unless coordinates are mapped back. Each step costs a screenshot plus accumulated context and a multi-second round trip (so "rapid clicking" by a model loop is not rapid), yet there is no cap on steps, minutes or dollars per flow, per explorer session or per run, no stop rule when nothing new happens, and no cost accounting per component. One bad night (a rescue cascade after a layout change) consumes the window and a large bill while producing nothing, and a surprise invoice or a run still going at the open gets the system switched off by someone outside the team.
Do: Run the VM at the fixed native resolution the diff engine needs (1920x1080 at 100% DPI), send the agent screenshots downscaled to about 1280x720 with aspect ratio preserved, and map returned coordinates back through an explicit scale factor verified by a calibration click at run start; the current toolset no longer takes display dimensions, so the harness owns the screenshot size and the scaling. Use the toolset's built-in zoom action (enabled by default in `computer_toolset_20260801`; `enable_zoom` on `computer_20251124`) and implement its handler to crop at native resolution; keep an OCR grid overlay only if zoom proves insufficient for strike columns. Put hard budgets in config enforced by the orchestrator: max agent steps per flow, max rescued steps per run (abort with "layout changed, library needs repair"), explorer action and wall-clock caps with early stop after N actions that produce no new screenshot hash, reviewer items per run, dollar caps per run and per week, and a run deadline relative to the next market-open boundary; scripted flows run first and the explorer gets the remainder. Prompt-cache the system prompt and tool definitions, drop old screenshots from context, record the usage block of every response per component, alert on a 2x week-over-week change, and print cost, duration and actions-per-finding in Run health.

**No action-level audit trail; exploration is unreproducible and findings cannot be replayed (G53)**
Capture stores screenshots at named checkpoints only, which the Explorer does not have. Nothing records the click and keystroke stream, the gateway's allow/deny decisions, the agent's per-action rationale, model ID, prompt hash or seed, or a continuous recording between checkpoints, which is where an incident would happen. If a working order shows up in the post-run check there is no way to tell which flow, mode or action produced it, so the guard cannot be fixed; and a finding that cannot be replayed is a Slack message, not a bug report.
Do: Log per action: step index, wall and monotonic time, mode, target as the model or script stated it, screen and window-relative coordinates, keys, gate decision, pre and post screenshot hashes, model ID, prompt hash, and a 96x96 crop around the click point captured at action time. Add the JAB accessible path only if the one-day spike shows the bundled Zulu runtime exposes usable names; click-point image anchors are the baseline mechanism. Record the whole run at 2 to 5 fps. `replay <run> --from --to` drives the trace in scripted mode: match the stored click crop by template (`cv2.matchTemplate`) first, fall back to coordinates (safe because the display config is pinned), and report reproduce or not-reproduce.

### Medium

**Mouse hover, caret blink, tooltips and keyboard focus make captures nondeterministic (G19)**
GDI screenshots omit the cursor but not what it causes: row highlight under the pointer, the chart crosshair and its price readout, tooltips after roughly 700 ms, hover states on buttons; the Swing caret blinks in a focused field (a look-and-feel property, so Windows' blink-rate setting does not fix it). The spec leaves the mouse and focus wherever the last step left them, so the same checkpoint produces different pixels depending on where the previous step clicked, especially on charts where the crosshair readout prints prices.
Do: Before every capture move the mouse to a declared parking coordinate in a dead area outside any gadget, drop field focus by clicking a declared neutral control rather than pressing Esc (Esc can close the order-entry panel in thinkorswim), wait past the tooltip delay, then run the settle check. Record the parking coordinate in capture metadata and mask a small region around it; exclude the cursor from captures; mask the caret region in any checkpoint that must keep a focused field.

**No triage stage before the reviewer: identical images, sub-noise changes and duplicate clusters all go to the model (G35)**
There is no perceptual-hash gate under the checkpoint's A/A floor, no grouping of the same change across many checkpoints (one toolbar icon visible on 40 screens becomes 40 findings), and no cost or item cap per run. Asked what changed between two near-identical images, a vision model invents differences, which are pure false positives; cost scales with checkpoint count rather than real change; 40 duplicate findings hide the one unrelated finding.
Do: Define a per-checkpoint A/A noise floor from repeated captures of the same build and treat anything under it as no difference. Stage: exact hash equal, pass; below A/A floor, noise; signature in the noise library, auto-noise; else pixel/SSIM with connected-component extraction. Cluster components across checkpoints by signature and send one representative per cluster with member count. Cache verdicts by `(baseline hash, candidate hash, mask version, prompt hash)`. Send native-resolution crops with a little context rather than full windows. Submit through Message Batches with a 1-hour cache TTL on the shared system prompt and few-shots, started as soon as captures land, with a synchronous fallback for anything not back by the report deadline (cache hits are best-effort and batch results can take up to 24 hours; the 50% batch discount stacks with cache pricing). Record tokens and cost per checkpoint and cap items per run.

**No process-level watchdog for a hung or crashed Java process, no freeze definition, no crash artifacts, nothing watching the orchestrator (G40)**
"Handles retries and timeouts" lives inside the orchestrator and nothing sits outside it. Long sessions hit heap pressure and the frame goes Not Responding, but a hung app still screenshots fine so step timeouts never notice; "frozen screen" has no definition; JVM crash files, heap dumps, WER dumps and Application Event Log entries are never gathered; the harness itself can deadlock; and no resume semantics exist, so a crash at flow 30 of 40 loses the run. One hang at 1 am yields a night of nothing with no alert until morning, and the one file that would explain a crash is lost.
Do: Run a separate watchdog (scheduled task or service under the same Windows user) that reads a heartbeat file the orchestrator touches on every step and samples every 2 s: find the app PID from the main window (`Main@thinkorswim` title, SunAwtFrame class) via `GetWindowThreadProcessId` and track its process tree with psutil (verify the process model first: the install4j launcher may host the JVM in-process rather than spawn a `javaw` child, so locate the JVM by command line or loaded `jvm.dll`); check the working-set ceiling; keep `IsHungAppWindow`/`SendMessageTimeout` only as a cheap JVM-wide stall detector, since AWT pumps native messages on its own thread and a blocked Swing EDT is not detected that way. Primary freeze definition: screenshot hash unchanged N s after an input that should change the screen, with no spinner template present. On hang, crash or N minutes of heartbeat silence: screenshot the desktop, attempt a thread dump with `jcmd` from a JDK matching the bundled runtime's major version (best effort), collect app logs, `hs_err_pid*.log` and process metrics, kill the process tree, record `app_crash` or `harness_error` with the last step id, relaunch, log in, reload the workspace and resume at the next flow boundary; abort after K restarts with an alert. Set `-XX:ErrorFile`, `-XX:+HeapDumpOnOutOfMemoryError` and `-XX:+CreateCoredumpOnCrash` in `thinkorswim.vmoptions` (verify flags against the bundled JDK version; the login-screen Setup may rewrite the file) and re-apply after updates; add WER LocalDumps for the launcher as a fallback; query Application log Event IDs 1000/1002 after each run; any crash artifact fails the run with the file attached and bypasses the reviewer. Relaunch proactively every N flows; tag captures with process uptime and restart count. Implement stress bursts as scripted macros the agent invokes as one tool call with the freeze detector running. A 30 s screen-video ring buffer (ffmpeg gdigrab) is optional.

**No cadence, runtime budget, sharding plan or flake quarantine; parallel workers collide on one login (G50)**
Flows run "in order" on one implicit machine with no run-duration budget, no cadence (per RC, nightly, weekly explorer) and no quarantine process beyond retries. Regular hours are 9:30 to 16:00 ET, so wall-clock is not the binding constraint; the one-session-per-login rule and flake handling are. Naive parallelism on one login logs workers out mid-flow, and flaky checkpoints poison the verdict.
Do: Parallelism equals the number of distinct test logins, justified by account and profile isolation; still test the session rule empirically (community reports conflict: a second login from another location logs the first out with a message citing data-entitlement rules, multiple instances on one machine reportedly coexist, and thinkorswim officially documents installing a second instance in a separate folder). Shard by stable hash of `flow_id`, because baselines containing account numbers, positions and server-side profile are per login; bind baselines to `(flow_id, login)` and mask the account number in checkpoints. Per-flow time budgets, a global deadline, longest-first ordering, `timed_out` distinct from `failed`, a smoke subset per RC under 30 minutes, the nightly full suite, the weekly explorer on its own worker and login, and a quarantine list with owners for checkpoints that flip twice on the same build. Publish p50/p95 durations.

**Data store: SQLite on a shared path under parallel writers, no baseline backup, no retention or storage plan (G51)**
"SQLite to start" with no statement of who writes; two workers on one DB file on a network share hit SQLite's documented unsafe locking on SMB/NFS. The baseline store is the irreplaceable asset yet has no backup or restore drill. Full-window PNGs at 1440p run 2 to 4 MB; with roughly 150 checkpoints plus crops, heatmaps and thousands of agent-step frames per night the store grows by tens of GB a month. A full disk kills a nightly run mid-flow.
Do: One writer: the orchestrator owns a local-disk SQLite in WAL mode; workers return results in-process or over a tiny HTTP or queue hop, never by opening the DB file over a share. Blobs are files, not rows: content-addressed (sha256) under `runs/<run_id>/` and `baselines/<app_version>/`, with a `manifest.json` in git per baseline set. Expect little cross-run dedup from hashing (quotes, clocks and anti-aliasing change bytes even in masked regions), so size the store on raw growth; hashing is for integrity and linking. Retention: baselines and images attached to open findings kept indefinitely; full checkpoint sets for the last N green runs per version; passing images 7 to 14 days; agent frames downsampled (JPEG q80 at 0.5x) and dropped after 14 days unless referenced by a finding. Nightly rsync of baselines plus the DB to a second internal location, a quarterly restore drill, and a preflight that fails the run as `env_error` below a free-space threshold.

**No alerting model and no harness observability (G52)**
The only output is an HTML report. Nothing says how anyone learns that a run never started, stalled, ended in `env_error` or found a high-confidence bug, who owns each outcome, or how the harness itself is observed. A nightly system that only writes a report gets checked less every week, and when verdicts shift or flows slow nobody can tell app change from harness change from model change.
Do: Minimum viable: (1) a dead-man alert if no run-completed event by T+deadline; (2) `env_error`/`harness_error` to the on-call channel with gate name and last screenshot; (3) new high-confidence bug verdicts to QA, deduplicated by `checkpoint_id` plus diff signature against open tickets; (4) a daily needs-a-human count. Log one JSON line per step (`run_id, flow_id, step_id, attempt, mode, duration_ms, verdict`) and chart p50/p95 step time, scripted-to-agent fallback rate, `env_error` rate, verdict mix, human-overturn rate and model cost per run. Stamp every run with harness commit, flow-manifest hash, VM image ID, app build, model IDs and prompt hashes so a shift in verdicts can be attributed.

**Explorer findings have no schema, dedup or disposition loop, and app bugs cannot be told from agent misclicks (G55)**
The reviewer is defined for baseline diffs; Explorer findings have no baseline, no record format, no merging of duplicates across nights, no disposition that changes future behavior, and no agent-error class. Computer-use models misclick on dense Swing UIs; a misclick that opens the wrong tab is reported as "navigation broken". Developer trust is gone the first week if half the findings are the agent's own mistakes.
Do: A finding record (signature, severity, confidence, invariant and raw values, trace ref, screenshots and video, app build, first and last seen). Before each agent action require a stated target and expected outcome; after it, verify the post-action state by the cheapest available means (JAB focused element if it works, else a VLM yes/no on "did <expected> happen" against the post screenshot) and log mismatches as `agent_error`. Run the Explorer at a resolution the model handles accurately (around 1280x800 to 1920x1080, with the canonical config reserved for pixel diffs) and verify every agent click with a template match of the intended control before acting. Replay every candidate finding once in scripted mode; hold non-reproducing findings as flaky/agent. Add "agent mistake" and "expected behavior" dispositions, retrieve past dispositions by signature as reviewer context, and report Explorer precision and agent-error ratio per run.

**No success metrics, definition of done, backtest or pilot exit criteria (G66)**
Nothing says what "a report a person can act on" means or how the system is judged: escape rate, false-positive rate, flake rate, time to detect, coverage, triage minutes and cost per run are neither defined nor instrumented; no targets or kill criteria exist; there is no plan to prove the tool would have caught real escaped bugs before people are asked to trust or fund it. Without a noise target the project dies as "too noisy" with nobody able to say whether it was improving.
Do: Add a human disposition column (bug, expected, noise, unknown) to every finding and store it in SQLite; from run one print FP rate (noise plus expected over all findings), flake rate (verdict flips between two runs of the same build, or between a run and a targeted re-run of its diffs), time to detect, triage minutes and cost per run (model tokens plus machine hours) in the report header. Set provisional targets (FP under 20%, flake under 2%, triage under 20 minutes, full scripted run under 3 h) and a kill-or-fix criterion (FP above 50% after three releases). Escape rate: tag each production bug with the flow that should have caught it and report covered versus uncovered. Backtest only if prior builds are obtainable (internal artifacts or a pinned update channel, since the launcher auto-updates and no official older-build install exists); otherwise a seeded-fault backtest (perturb baselines and masks, or point the explorer at known historic bug areas) with the limitation stated. Pilot exit: two release cycles, FP under target, one real pre-release catch, triage under budget.

**Only one comparison axis: product change cannot be separated from flakiness (G67)**
Each new screenshot is compared only with the last approved baseline, so for a new release that diff contains every intentional change plus every flaky difference with no way to tell them apart; there is no comparison with the previous run of the same build or with older approved versions. Flaky diffs get classified as product changes and product changes as noise, and a regression wrongly approved in version N is never seen again in N+1.
Do: Keep the baseline comparison as the primary axis. For instability, re-run only the checkpoints whose diff exceeded threshold (a targeted re-run of the same flow steps, not a full second run) and classify: differs from baseline but identical across re-runs, product change for the reviewer; differs between re-runs, instability routed to the flow owner with the two images and never shown as a product finding. Maintain a per-checkpoint flake score in SQLite and auto-widen masks or quarantine above a threshold. If prior builds are obtainable, run the previous approved build sequentially on the same night with the same login, or concurrently only with a second paperMoney login (concurrent instances on one login are reported to disconnect the earlier session), so closed-market data matches. Add a weekly re-diff of the current run against the N-2 approved baselines to catch drift and mistaken approvals. The second-machine axis is optional once the rendering pipeline is pinned (G63).

**Flow authoring and upkeep have no recorder, anchored locators, owner or budget (C07)**
The spec says flows are YAML or JSON but not how a person writes one against a Swing window with no control tree, how a flow is validated before it runs at night, what it costs to keep 100+ flows alive when each release moves a toolbar, or who owns each flow. Maintenance, not detection, is what kills visual-regression suites: with absolute coordinates a single toolbar redesign breaks dozens of flows at once, the agent fallback quietly takes over, and within two releases the suite is mostly agent-driven. (The "one engineer per 100 to 200 UI flows" rule of thumb is unsourced; do not plan on it.)
Do: Build a recorder (global mouse and keyboard hook plus a screenshot per action) that emits YAML steps whose targets are image anchors: a small template (stable icon or label, about 40x20 px) plus an offset, stored next to the flow and versioned with it. Anchors are per display tier, not multi-scale. Add a "flow lint" job before each nightly run that matches every anchor against the latest approved baseline and the previous night's candidate; a broken anchor is reported as "flow maintenance needed", not as an app bug. Give every flow `owner`, `last_repaired` and `agent_fallback_rate` fields; when agent fallback succeeds, emit a proposed anchor patch for the owner to accept. Track `flows_repaired_per_release` and `fallback_rate_per_flow` as health metrics and set a weekly maintenance budget from the first two releases' measurements. The recorder must honour C09's secret steps (hook paused) and be declared in C11's prerequisites. Note `pyautogui.locateOnScreen` supports confidence thresholds only with opencv-python installed.

### Low

**Keyboard layout, toggle keys, symbol autocomplete and symbol linking are not controlled (G21)**
pyautogui types by virtual key codes, so a non-US layout or Caps Lock changes characters (NumLock affects only the `num0`..`num9` key names, not ordinary digits); thinkorswim symbol boxes open an autocomplete list (Enter semantics unverified); futures and options rely on `/` and `.` prefixes. Flows pass on a developer's machine and fail on the runner with the wrong symbol in the wrong panel.
Do: At run start record `GetKeyboardLayout` (assert `0x0409` en-US) and `GetKeyState` for VK_CAPITAL, VK_NUMLOCK and VK_SCROLL into the environment fingerprint, normalize them, and fail fast on mismatch. Prefer pywinauto `send_keys` (SendInput) over pyautogui for text; keep clipboard paste only as a fallback for unmappable characters, because the computer-use agent, screenshot tooling and clipboard managers share the one clipboard. Do not try to read the dropdown: after committing a symbol, OCR the gadget header (symbol plus company or contract description) and assert the exact symbol. Always type the fully qualified symbol (`/ESZ25`, `.AAPL250117C150`). Link-group colors are already deterministic once the workspace is pinned; add a per-flow `changes_gadgets` list so the diff engine expects linked panels to change.

**Checkpoint identity is tied to flow steps, so edits orphan baselines (G33)**
The spec's "named checkpoints" partly answers this, but nothing says what makes an ID stable or what a checkpoint with no baseline does. If the ID derives from flow name plus step index, inserting a step orphans every baseline after it; if "no baseline" silently passes, a whole flow can go untested after a refactor, and if it fails loudly every edit creates a wave of fake failures.
Do: Make the checkpoint id a stable slug naming the screen and state (`trade.order-ticket.single-leg.review`), unique across the library, validated in CI. Require a rename map in any PR that removes or renames an id; CI fails the PR, not the nightly run. A checkpoint with no approved baseline gets its own outcome `needs baseline`, excluded from app-bug counts but blocking the run from being reported as clean; offer the closest existing baseline by perceptual hash in the approval queue. Tombstone retired checkpoints with the version they were retired in, and report orphaned baselines in Run health.

## 5. Gaps in safety, compliance and environment

Order safety, explorer blast radius, credentials, data egress, environment determinism, logins, authorization. Ordered critical, high, medium, low.

### Critical

**Explorer has no boundary: it can post in chat, share publicly, page humans, reset the account (G05)**
Free roam is unbounded. From a click the agent reaches Chat Rooms (public posts) and Live Support (a real Schwab employee), Share buttons that publish charts, grids and workspaces to public tos.mx links, MarketWatch Alerts that email or SMS the account owner, Help feedback (verified for the mobile app; desktop path unverified), links that open the system browser with SSO, Export and Print, paperMoney reset and adjust-cash that wipe fixtures, Setup and Application Settings (where it can disable the confirmation dialog or enable Auto Send), Logout and account switch. Its odd inputs typed into a chat room are public posts. Each has an effect outside the machine: real people receive messages, internal screenshots of a pre-release build become public, the owner's phone is spammed at 2 am, fixtures are destroyed mid-suite, or a later run's safety layers are silently disarmed.
Do: Prefer cheap identity-level controls first: never verify an email or phone number in Notifications on the test identity (then alerts cannot page anyone), keep chat, support and Share behind the gateway deny list, and deny Setup, Adjust Account, Logout and account switch outright. Replace the default browser with a logging stub and disable printing. Do not rely on restricting outbound network to Schwab hosts: thinkorswim talks to thinkorswim.com, tos.mx, mediaserver.thinkorswim.com and CDN hosts, and chat, share and alerts all run over Schwab hosts, so a host allowlist adds breakage without closing the real exits. Give the Explorer its own saved workspace containing only allowlisted tabs, and run a per-release denied-action test.

### High

**No kill switch, no definition of "stop", no post-run proof that nothing was sent (G03)**
"Stop the run" is undefined. Stopping the executor leaves thinkorswim logged in with a ticket open; if the agent loop is wedged it cannot stop itself; nobody is alerted; nothing after the run checks whether an order was in fact placed; and a guard that trips does not disable the flow or open an incident. A guard that detects danger and then does nothing decisive is theater, and without end-of-run verification you cannot tell the person who authorized this that no orders were sent.
Do: Layered: the gateway's deny is the first stop; the hard stop kills the process tree. Two corrections to the obvious design. (1) A dead process cannot send going forward, but it does not cancel an order already accepted by the server: working orders survive the client, so the hard stop must be followed by a verified Cancel All from a fresh scripted login (or a human) and a diff of Working and Filled against the start snapshot. (2) Do not lock the machine as part of the trip; G10 needs an unlocked console for the next run. Instead mark the run RED, alert, and revert the VM from the golden image. Keep the post-run read of Working, Filled, Canceled and Position Statement plus Net Liq and buying power as the end-of-run proof, stored in the run DB.

**Computer-use agent reads untrusted screen text and improvises at the worst moment (G06)**
Agent mode is invoked when scripted clicks fail, which means the screen is in an unexpected state, often with a half-built order ticket. Its only input is the screen, which carries news headlines, chat text, symbol notes and tooltips that can read like instructions, and a model told to "review the order" will improvise toward completion. The reviewer's output has no fixed schema, so screen text can leak into report fields. The fallback fires precisely when the guard's assumptions about the screen are broken; an improvising model with raw keyboard access is the most likely path to an order being sent.
Do: Implement the agent's tool set as the gateway itself: `click_named(target)` resolved by the locator ladder, `type_fixture(id)` from a fixture list, `press(tab|escape|pgup|pgdn|arrows)` only; no raw coordinate click or free text. Abort agent mode (Escape via the gateway, mark the step failed) whenever the ticket/dialog detector fires. Cap at about 15 actions and log each action's rationale. Reviewer and agent prompts state that screen content is data; reviewer output is schema-validated before it reaches the report. Computer use is a beta feature of the Claude API, which bears on retention eligibility (G07).

**No named authorization; automated client use can breach terms and trigger surveillance (G08)**
"paperMoney or internal test account" straddles two situations. A retail paperMoney login is the same credential as a real brokerage account; brokerage terms commonly prohibit automated access and credential sharing (Schwab's prohibited-use clause could not be retrieved, so treat it as unverified but likely), and sanctioned automation goes through the Trader API, not the UI. Abuse detection on logins and session behavior can lock or restrict the account (trade surveillance does not see paperMoney orders, so the risk is from automated-access detection, not simulated order activity). If internal, the platform owner, security and compliance must sign off. The spec names no accountable owner or incident contact. Without authorization the most likely outcome is a restricted account and a project shut down after the first incident; with an internal owner, every other mitigation becomes a requirement that person will ask for.
Do: Before code: name the accountable owner and incident contact in the spec, and get written authorization (platform owner plus legal and compliance if internal; Schwab's written permission if external). If external and permission is not forthcoming, use a Guest Pass (paper-only, separate credential, 30-day rotation) rather than a personal brokerage login, and keep login, symbol and order-staging rate caps. Record the authorization reference and `account_id` in every run manifest and log every staged and cancelled order with timestamps.

**Runner needs an unlocked interactive console session on a hardened, isolated box (G10)**
The spec has a scheduler but never says which Windows session the run executes in. A Task Scheduler job set to "run whether user is logged on or not" is non-interactive: SendInput goes nowhere and screenshots come back black. An RDP session that disconnects locks the console and renegotiates resolution; lock screen, screensaver, display sleep and Windows Update reboots do the same. Nothing says what else runs on the box (Teams, Outlook, Defender toasts). This is the most common way desktop GUI automation dies in month one: a night of black or shifted frames diffed against baselines and reported as high-confidence "entire screen missing" bugs.
Do: A dedicated VM with console autologon, lock and screensaver disabled, Focus Assist on, Windows Update active hours set, and `tscon` to console on any RDP disconnect (G20 lists the rest). Run-start checks pin DPI scaling, ClearType state and the Java2D pipeline (log the rendering lines from the client log) so the same bytes render the same way; use the hypervisor's basic console (not Hyper-V Enhanced Session or any RDP-backed console) for operator access. Because the launcher auto-updates at start, either bake each release into a fresh golden image (so reverting does not re-download the build every run) or allow the update and record the resulting build in the run manifest. Classify any self-check failure as `env_error` and never as a visual diff. A VM without a GPU forces the Java2D software pipeline no user has; this does not cause false positives (baselines come from the same box) but limits representativeness (G63).

**Rendering drift (JRE, GPU driver, ClearType, OS patch) is unguarded and a global shift is not handled as one event (G15)**
Pixel and SSIM baselines assume identical rasterization, but Java2D picks a pipeline per machine, anti-aliasing follows the JRE version and font flags, and ClearType, GPU driver and Windows font updates move glyph edges; a bundled-JRE bump (user reports show the auto-updater has moved from Zulu 11 to 17) changes every text pixel. No environment fingerprint is stored with images, and there is no run-level view, so a global shift arrives as 150 individual "noise" diffs. The team either re-baselines blindly, burying the real regressions in that same release, or turns the tool off.
Do: Compute an `env_fingerprint` from live reads at run start (jre `release` file, vmoptions hash, Windows build, display settings, theme, workspace hash) rather than from the snapshot name, and store it with every image. Run global-shift detection as a cheap pre-pass before any reviewer call: the fraction of checkpoints with diff above epsilon, and whether diff pixels sit on text edges via an edge-density measure; a global shift becomes one run-level event, not 150 findings. Use SSIM with a Gaussian window plus a 1-px-dilation-tolerant pixel diff as the default metric so sub-pixel anti-aliasing changes do not trip. Keep an A/A pair (two captures of the same build in the same session) to calibrate per-checkpoint epsilon. Store the Help > About render as the rendering-fingerprint checkpoint.

**No per-flow preconditions or teardown; a failed flow dirties the next (G48)**
Flows run "in order" with retries, but nothing restores UI state between them: open tickets, modal dialogs, a changed symbol in a linked group, scrolled lists, detached gadgets, switched tabs, zoomed charts. A retry starts from wherever the failure left the screen, so checkpoint N+1 contains flow N's leftovers, the diff is real but not a bug, and each retry produces a different screenshot so baselines never stabilize.
Do: A precondition block per flow (canonical workspace name in the Setup menu, exactly one top-level SunAwtFrame for the process, main window rect equals fixture, fixture symbol in the linked group, no modal). `reset_ui` between flows: Esc x3, close every non-main top-level window via pywinauto win32 enumeration by process id, re-enter the fixture symbol, park the mouse in a dead zone. Reload the canonical workspace only when the `pre_flow` checkpoint fails, since a workspace load costs tens of seconds and doing it before every flow blows the runtime budget. On precondition failure after one reload, run `reset_profile` (G46) and retry once, otherwise mark the rest "blocked by environment". Store attempt numbers and keep the first attempt's screenshot.

**Unattended login reality: MFA, device trust, lockouts, single session per login, credential rotation (G49)**
"Launches and logs into the app" hides the most release-fragile sequence: launcher update progress, Schwab 2-step verification, expired-password and terms re-acceptance pages, exchange-data agreements, the failed-login lockout combined with a retry loop, the one-active-session rule, session expiry mid-run, the remember-password checkbox, and rotation of the Schwab password and the vault token. Each turns into a locked account, a run that fails every night at step one with zero signal, or the first rotation producing a night of login failures reported as app bugs.
Do: A dedicated LOGIN flow with a checkpoint on every screen from launcher to loaded workspace. Schwab's 2-step verification offers Symantec VIP (app or hardware token) and SMS codes, with modes "always at login" or "only on untrusted devices"; there is no push-approval or generic TOTP option. Two workable paths: (a) trusted-device mode: trust the VM, take the golden snapshot after the trust is established, and verify empirically that the trust survives a revert (if Schwab rotates the device token per login, the reverted token is stale and you are back to prompts); (b) a Symantec VIP credential provisioned with the open-source `python-vipaccess` tool, whose OATH secret the orchestrator holds in the vault to generate the 6-digit code; this is a software reimplementation of VIP Access, so get security to approve it explicitly. Plan for risk-based authentication, which can prompt for a one-time code on an unusual login even with 2-step off; route it to the gate state machine and alert, never loop. Cap attempts and never retry on an authentication error. Serialize runs per identity and treat "logged in elsewhere" as `environment_abort`, after confirming the single-session behavior empirically (G50). Agreements cannot be un-accepted, so a "never-accepted test login" is not feasible; to see first-run agreement screens each release, use a fresh Guest Pass as a manual, non-blocking smoke. Lockout thresholds are unverified.

### Medium

**Focus stealing and window occlusion corrupt input and capture (G20)**
pyautogui sends input to whatever has focus. Windows toasts, Defender, Update prompts, a detached thinkorswim window or a Java dialog can take foreground between steps, and a foreign window can sit on top during a region capture. The spec never verifies foreground before input or occlusion before capture. Keystrokes land in the wrong app (a symbol and quantity typed into a chat client is both a leak and an untraceable failure), clicks hit an overlay, and screenshots include a foreign window the reviewer reports as a thinkorswim bug.
Do: Before each input batch assert `GetForegroundWindow`'s PID is the thinkorswim PID, else pywinauto `set_focus()` on the main frame (it implements `AttachThreadInput` plus `SetForegroundWindow`, which is otherwise refused) and re-check, aborting the step if it still fails; before each capture sample `WindowFromPoint` at a grid inside the target rect and require all hits to belong to the thinkorswim process; log every focus correction as an event and treat a rising count as a new-popup signal. On the dedicated VM: Focus Assist on, Windows Update active hours set, Defender and OEM prompts off, screensaver and lock disabled, autologon to the console session, and `tscon` to console on any RDP disconnect. Skip `BlockInput` (it requires administrator rights and its interaction with injected input is untested).

**Typed vault password leaks into action logs, recordings and agent prompts (C09)**
The orchestrator logs in by typing the vault password, and the spec stops at "credentials live in a secrets vault". Any keystroke log or screen recording (which G53 rightly adds) captures the typed value; the remember-password option can persist it; if login fails and agent mode takes over, the only way the agent can proceed is to be handed the password inside a prompt sent to a cloud API; and the SQLite store and HTML report would then hold it for months. The login field itself is masked, so mid-typing screenshots show dots; the exposure is the keystroke log, recording and agent prompt. A plaintext brokerage password in a retained log is a reportable security incident at a broker.
Do: Add a step attribute `secret: vault_ref`. For such steps the executor pulls the value at the last moment, types it with the recorder hook paused and screenshot and recording capture suspended, logs only `<redacted:login.password>`, and clears any clipboard use afterwards. Login is scripted-only: agent fallback is disabled before the post-login checkpoint and a login failure is a terminal `env_error`, never a handoff. Assert the remember-password checkbox is off at every login. After the run, scan logs, DB rows, report HTML and agent transcripts for the plaintext (held in memory only; a hash-based scan cannot find a secret embedded in a larger artifact) and fail the run with "secret leaked" if found. Declare the typed-credential path and the paused hook in C11's prerequisites so endpoint tooling does not treat it as a keylogger.

**Corporate EDR, DLP and proxy controls can block injection, capture and egress (C11)**
If the rig is a managed corporate Windows machine, as any internal Schwab box would be, endpoint controls fight every part of this design: EDR agents flag SendInput from unsigned Python processes, global keyboard hooks and screen capture by unknown processes; AppLocker may block `python.exe`; DLP and the corporate proxy will block, inspect or silently strip multi-megabyte image POSTs to an external AI API. These behaviours are environment-specific and unverified for any particular configuration, but on day one of a pilot on managed hardware nothing works, and the usual workaround, an unmanaged box on a guest network, violates the same policies G07 and G08 point at.
Do: Add an "environment prerequisites" section listing exactly what the harness does on the box: process names and whether they are signed, input injection (SendInput via pywinauto/pyautogui), global hooks (recorder), capture method (BitBlt/DXGI), files written, egress hosts, payload type and size, and the typed-credential path. Obtain written exceptions from endpoint security, DLP and proxy owners before building, and ask whether a TLS-inspecting proxy is in path (then trust its CA in the Python environment). Ship a preflight that injects a click into Notepad, installs and removes a hook, captures the screen, and POSTs a 2 MB image to the model host; classify any failure as `env_error` naming the blocking control. Package the harness as a code-signed executable (PyInstaller plus `signtool` with a corporate or OV certificate) so it can be allow-listed by publisher and hash; expect AV heuristics to flag PyInstaller bundles until then. Java Access Bridge is enabled per user via `jabswitch` and `.accessibility.properties`, not by a Java security setting; `-javaagent` goes in the launcher's vmoptions.

### Low

**DPI awareness of the automation process is undefined (G11)**
"Same resolution, DPI" constrains the machine, but the Python process's DPI awareness decides whether coordinates are virtualized. pywinauto, pyautogui and pyscreeze each already call a DPI-awareness API at import, so the issue is ordering and level consistency, not absence: at 125 or 150% an inconsistent level means screenshots at logical size, clicks off by the scale factor, and the computer-use agent's coordinates mapped into the wrong space. Current builds run on Java 11+ (DPI-aware), so the historical Java 8 bitmap-scaling transition is not a live risk.
Do: Set DPI awareness once and deliberately: an application manifest for the orchestrator executable (Microsoft's recommended route) or `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` as the first executable line before importing pyautogui, pyscreeze, pywinauto or mss; log `GetProcessDpiAwareness` at run start and fail if it is not what was requested. Run the canonical tier at 100% on a single display and assert it from the orchestrator's own aware process: `GetDpiForSystem() == 96` and `GetSystemMetrics(SM_CXSCREEN/CYSCREEN)` equal to `EnumDisplaySettings`' physical `dmPelsWidth/Height` and to the pinned size. Do not assert on `GetDpiForWindow(tos_hwnd)`: for a DPI-unaware target it returns 96 regardless of monitor scale. Store dpi, scale, awareness level and display geometry in every image's metadata and have the diff engine refuse mismatches. Keep checkpoint coordinates relative to the thinkorswim client rect so a window move does not shift them.

## 6. What would make it materially better

The strongest decisions, each drawing on several gaps. Most of them are cheap to decide now and expensive to retrofit.

**1. Define the build identity as a run input, with internal and external modes (G12, G13, G14, G66, G67).** Every run records what it tested: build from the window title, JRE from the bundled `release` file, vmoptions hash, environment fingerprint. Internal mode is triggered from the build pipeline or an RC watcher and has a written gate (triage complete N business days before GA, named sign-off). External mode says plainly that the goal is detection within the first closed-market window after release, pins builds only through VM snapshots, keeps N-1 and N-2 snapshots for upgrade-path and backtest runs, and runs a canary machine that updates first. Writing both modes down stops the project from being judged against a bar it cannot reach.

**2. Add an Oracle layer and put assertions in the flow files (G28, G29, C05, C06, G64, G65, G31).** Before any vision model sees a diff, OCR (or JAB where it exposes values) extracts typed fields per checkpoint, an `expect:` block per step evaluates equals, within-tolerance, present, absent and changed-since-previous-step against landmark-anchored regions, and `invariants.py` checks arithmetic (Net Liq, buying power, P/L sums, option multipliers, no NaN or N/A). Independent sources are CSV exports and clipboard copies from the app's own grids, the Schwab market-data API with the 20-minute paperMoney delay modelled, and, if authorization allows, thinkorswim Web's DOM via Playwright. An assertion failure is a hard FAIL regardless of the pixel score, a screenshot cannot become a baseline until the oracle passes, and the reviewer receives expected-versus-extracted text with native crops. This is the only way "wrong numbers" ever gets caught.

**3. Require a per-build change manifest and reconcile in both directions (G30, G31, G57).** A YAML manifest per build (ticket key or release-note line, summary, affected panels or checkpoint ids, expected visual or mock, feature flag), built from the internal ticket export or the public release-notes page with an LLM proposing the mapping and a human approving it. The reviewer may say "expected" only with a non-null `manifest_ref`; a diff on an unmentioned panel gets a higher bug prior; and every manifest entry must have a covering checkpoint that confirms the change actually appeared, or it is printed as "no covering checkpoint" and drafted as a flow stub. This is the "intended outcome" input the spec's goal assumes and never names.

**4. Build one input gateway with keystroke-level never-send enforcement and run-start settings attestation (G01, G02, G03, G04, G06, G61, C04, G05, G47).** All input, scripted and agent, goes through one gateway whose low-level hook drops Enter, Space, Ctrl+Enter and order hotkeys while a ticket or confirm dialog is up and drops any click without an armed token. A run-start attestation flow screenshots and OCRs Application Settings (confirmation on, Shift+click send off, hot keys disabled) and the per-panel Active Trader Auto send checkbox, and asserts the `D-` paperMoney account from the selector. The agent's tools are the gateway's named actions, not raw coordinates or free text. The kill switch kills the process tree, then a fresh scripted login runs a verified Cancel All and diffs Working and Filled against the start snapshot; a nightly fire drill proves each bypass is blocked. Decide separately, with the risk owner, whether tiny identity-gated paper sends are allowed so the post-order lifecycle is tested at all.

**5. Calibrate noise with A/A runs, score per region and component, and bound masks (G26, G27, G15, G25, C03, G35, G24).** Phase 0 runs the full library five times on one build and measures the per-checkpoint, per-region noise floor; any non-trivial floor is a flow defect (settle, caret, hover, flash, scroll) to fix before any threshold exists. Thresholds are per checkpoint, scoring is at window (translation only), region and connected-component level, and a component the size of a button or digit fails regardless of the global score. Masks are landmark-anchored, typed with value rules checked by OCR, versioned with owner, reason and expiry, and capped by a per-panel budget (0% over Qty, Price, Buying Power Effect). A global rendering shift is detected as one run-level event. Every baseline carries a data epoch so expirations, rolls and holidays trigger re-approval rather than scored diffs.

**6. Use OnDemand replay for frozen data where it works, and futures-session recordings for streaming checks (G23, G65, G22, G62).** Spike OnDemand first under the test login on the target machine: availability, buffering time, failure rate over 20 launches, which gadgets replay, and whether it conflicts with the paperMoney-only login. If it passes, chart and chain checkpoints capture at a pinned timestamp with playback paused, byte-identical across baseline and candidate, and custom thinkScript studies get expected label values pinned per timestamp. Streaming behavior (frozen quotes, flicker, ladder re-centering) is checked by 10 to 20 s recordings during the Globex session, which stays inside the market-closed constraint. Define "market closed" in config with an exchange calendar library, not wall-clock cron.

**7. Isolate state with VM snapshots, separate logins and a scripted server-side reset (G46, G47, G44, G45, G48, G10, G14).** A golden VM snapshot restores local state (workspace file, usergui folder, vmoptions, rendering pipeline); a scripted post-login reset restores server-side state (Application Settings, watchlists, drawings, alerts, saved orders, studies) and takes a tight `profile_clean` checkpoint. The Explorer runs under its own login and snapshot, last, never in the same session as scripted flows. Use the margin account as the golden populated portfolio and the IRA as the empty visual-suite account; seeding is a named human's job during market hours, on an expiration calendar. Every flow has preconditions and a `reset_ui` teardown. Without this, every diff is partly yesterday's leftovers.

**8. Persist triage decisions and make them change the next run (G34, G32, G33, G66, G52).** A per-diff state machine in SQLite keyed by a tolerant fingerprint, so a decision made once suppresses the same diff tomorrow, clusters identical signatures across checkpoints, and reopens when a ticket marked fixed-in-build X still shows the fingerprint. Baseline approval is human-only, per checkpoint or cluster, never per run, with content-addressed images and pointer-based revert. Serve the report from a small local web app whose controls write back. Name the triage rotation, time box and release gate, and alert on dead-man, env_error and new high-confidence bugs so the report is not the only signal.

**9. Build an eval set and change control for the reviewer, plus nightly synthetic-fault canaries (G36, C02, G35, C01).** 300 to 500 labeled diffs (mutations over real captures, A/A pairs, real release diffs labeled by two humans) give per-category precision and recall, tier-1 recall, and calibration curves that set routing thresholds; every prompt, model, mask or redaction change is gated on it, and model id plus prompt hash is stamped on every verdict. A deterministic 20 to 30 item mutant catalog (erase a button, change a digit in Buying Power Effect, swap BUY/SELL) runs through the real diff, mask and reviewer path every night and sets `detector-degraded` on a critical miss. Review is asynchronous and batched so an API outage produces an `unreviewed` report rather than none.

**10. Make scripted mode real: a locator ladder, a recorder, and anchored flows with owners (G09, C07, G38, G53, G54).** Week 1 decides whether Java Access Bridge is usable (`java --list-modules` on the bundled runtime for `jdk.accessibility`, `jabswitch -enable`, a tree dump per panel). The flow schema carries a locator ladder (JAB, template anchor, OCR, coordinates) and logs the rung per step. A recorder emits anchored YAML; a nightly flow lint reports broken anchors as maintenance, not app bugs; agent rescues are first-class events that produce a proposed anchor patch rather than a silent green. Every action is logged with a click-point crop so Explorer findings replay and promote into `flows/quarantine/`.

**11. Treat environment failures as a separate outcome class with gates and a watchdog (G37, G17, G18, G20, G40, G41, G49, G43).** The orchestrator passes gates (launched, authenticated, workspace_loaded, canary_flow_passed) verified by anchor crops; a popup sentinel matches every unexpected window against a versioned catalog; capture requires settle, must-see anchors and no anti-anchors; a comparability gate yields `not comparable` instead of a confident bug. An external watchdog with a heartbeat file restarts a hung JVM, collects `hs_err_pid*.log`, dumps and client-log slices, and resumes at the next flow boundary. App log exception signatures are a reviewer input. Only `completed` runs feed regression metrics.

**12. Decide the data path and authorization before Phase 1 (G07, G08, C09, C11, G05).** Which model endpoint and retention terms security has approved for screenshots, whether computer use (beta) is covered, and a local-model fallback; a redaction stage in capture so only redacted artifacts are stored and diffed; a named accountable owner and written authorization; secret-marked login steps with capture paused and a post-run plaintext scan; an environment-prerequisites section and written EDR, DLP and proxy exceptions with a preflight that proves injection, hooks, capture and egress work. These are the items that stop the project after it is built if they are left for later.

**13. Put budgets, cadence and coverage accounting in config (G39, G50, G51, G57, G58, G60).** Hard caps on agent steps, rescued steps, explorer actions and wall-clock, reviewer items, dollars per run and per week, and a deadline relative to the next market open; a smoke tier per RC under 30 minutes, nightly full suite, weekly explorer and Tier B configuration cells, Friday-night soak; parallelism equal to the number of test logins. A surface x persona matrix with required `persona`, `surface`, `requires` entitlement tags, and a report that prints NOT COVERED and NOT RUN cells so "any and all users" is a measured claim rather than an assumption.

- Tooling: pywinauto, pyautogui and pyscreeze each call a DPI-awareness API at import; `GetDpiForWindow` returns 96 for any DPI-unaware window; pywinauto `set_focus` implements `AttachThreadInput` plus `SetForegroundWindow` (0.6.9); `BlockInput` requires administrator rights; `pyautogui.dragTo` interpolates moves only with `duration>0`; computer-use `left_click_drag` is mousedown, move, mouseup; `pyautogui.locateOnScreen` supports confidence thresholds only with opencv-python; `jabswitch -enable` writes `%USERPROFILE%\.accessibility.properties` (JDK 17/21 man pages) and survives a JRE replacement; `jaccessinspector` and the client-side `WindowsAccessBridge` DLL ship with a JDK, not a JRE; Java Access Bridge is Windows-only and pywinauto has no JAB backend; the Java2D flags named are valid JVM properties that Oracle documents as implementation-specific; `IsHungAppWindow`/`SendMessageTimeout` do not detect a blocked Swing EDT; the GDI quota is 10,000 objects per process; `hs_err_pid*.log` lands in the JVM working directory unless `-XX:ErrorFile` is set; the Windows process image is the install4j launcher, not `javaw.exe`; SQLite locking is documented unsafe on SMB/NFS. (G09, G11, G16, G20, G40, G41, G42, G51, G53, G63, C04, C07, C11)
- Vendor: Anthropic's published deprecation policy is at least 60 days' notice before retiring a public model (not 30, and "12-month cycles" is not a policy); the computer-use tool schema has had four tool-type versions with hard 400s on older types for current models; zoom is a native action (default in `computer_toolset_20260801`, `enable_zoom` on `computer_20251124`); the current toolset no longer takes display dimensions, so the harness owns screenshot size and coordinate scaling; the documented baseline recommendation is about 1280x720; Message Batches turn around "within 24 hours", prompt caching works with batches, the 50% discount stacks with cache pricing and cache hits are best-effort; the SDK retries 429/5xx twice by default; per the docs as of November 2026 the newest models require 30-day retention by default and are excluded from zero-data-retention unless expressly authorized; the standard-tier image downscale is about 1568 px on the long edge, with 2576 px allowed on Claude Opus 4.7 and later; computer use is a beta feature. (G06, G07, G28, G35, G39, C01)
- Window titles are readable with `GetWindowText`; no OCR is needed for the build string or active-window checks. (G37)
- OCR on thinkorswim's default small fonts is unreliable without upscaling: use 3x upscaled crops for the few recurring text and numeric assertions, which is why the narrow AI-reviewer yes/no question is the cheaper route for release-note reconciliation. (G28, G31)

### Corrections the skeptics made to earlier drafts (so the final recommendations differ from the first ones)
- A dead process cannot send going forward, but working orders already accepted survive the client, so a hard stop needs a verified Cancel All; locking the machine on a trip conflicts with the unlocked-console requirement. (G03, G10)
- An unsent staged order is not persisted and cannot fill at the open; only a sent order can. The fixture check at run start is still the right breach detector. (G44)
- A host allowlist on Schwab domains closes none of the Explorer's real exits, since chat, share and alerts run over Schwab hosts. (G05)
- Trade surveillance does not see paperMoney orders; the account-restriction risk is from automated-access detection on logins and sessions. Severity lowered from critical to high. (G08)
- The JAB setting survives a JRE replacement; the real risk is a bundled runtime without `jdk.accessibility`. (G09)
- A VM software rendering pipeline does not cause false positives (baselines come from the same box); it limits representativeness. Reverting to a golden image before every run triggers the launcher's update download each time. (G10)
- The named executor libraries are already DPI-aware at import; the issue is ordering and level consistency, and a `GetDpiForWindow` assertion on the thinkorswim window cannot detect 125/150% scaling. (G11)
- Java2D anti-aliasing is deterministic on one machine for a fixed build; A/A noise comes from state and timing. (G26)
- thinkorswim's green and red differ in luma, so a P/L colour flip is visible to grayscale SSIM; whole-window dilution is the real failure. (G27)
- Identical images already yield no reviewer calls under the spec as written; the triage stage's value is the sub-noise and clustering gates. (G35)
- "Cancel a staged order during disconnect" is an invalid assertion under the never-send rule; maintenance is reported on weekends, not every after-hours window; paperMoney runs on production servers. (G43)
- The margin and IRA accounts on one login cover the populated and empty states without a second login. (G45)
- Workspaces are local files handled by a snapshot revert; settings, watchlists, alerts, drawings and studies persist to the login at change time, not on exit, so a process kill does not undo them. (G46, G47)
- One machine can finish inside a weeknight window (about 17.5 hours); the binding constraints are the per-login session rule and flake handling. Content-addressed storage gives little cross-run dedup for a trading UI. (G50, G51)
- Delta debugging by GUI replay is multi-minute per probe; bound it or make it manual. (G54)
- An off-screen Send button cannot be mouse-clicked, so off-screen dialogs do not defeat the cursor guard; keyboard activation is the separate bypass. Mixed-DPI dual monitors need physical hardware. (G58)
- OnDemand replays market data only; it cannot test a DST scheduler failure. (G62)
- The memory setting lives in the login-screen Setup button and vmoptions `-Xms/-Xmx`, not Application Settings; FLEXGRID is the Flexible Grid chart layout. (G63)
- A thinkorswim drag does not bypass confirmation unless Auto Send is on, which G01 already covers; `pyautogui.dragTo` interpolates with a non-zero duration. (C04)
- The login password field is masked, so mid-typing screenshots do not leak it; a hash scan cannot find a secret embedded in a larger artifact. (C09)
- Java Access Bridge is enabled per user via `jabswitch`, not by a Java security setting; `-javaagent` goes in the launcher's vmoptions. (C11)
- Auto-ticketing at a fixed confidence threshold is unsafe until confidence is calibrated; pHash fingerprints need a Hamming tolerance. (G34)
- A "three-flow smoke before merge" in daytime CI conflicts with the market-closed constraint; baseline PNGs in git need LFS or object storage. (G32)
- The "identical stale screenshots read as a clean release" mechanism was overstated; a hung JVM still needs a watchdog, and the launcher may host the JVM in-process rather than spawn `javaw`. (G40)
- Server-side order rejections cannot be exercised without Send; the odd-input rules apply only to client-side validation. (G56)
- Schwab pre-market begins at 7:00 ET, not 4:00; verify hours against Schwab's current page before coding windows. (G22)
- The spec's "named checkpoints" partly answers the identity question (G33), and the cut-off section may already contain metrics (G66).

### Refuted gaps (considered and set aside)
- **C08, report images at page scale hide digit-level bugs; no 1:1 region triage.** Refuted as a standalone gap: 1:1 crops, flicker toggles and region-level approve/mask actions are a presentation detail of the Reporter whose description was cut off, and the triage substance is already in G34 (persisted decisions) and G27 (region and component scoring). It is listed in section 8 as one line to check.
- **C10, the goal needs a post-release net: staged rollout, telemetry, rollback.** Refuted: launcher-side staged rollout, per-build telemetry and a rollback runbook are the platform owner's release process, not something this harness builds, and an external author cannot act on any of it; whether Schwab stages thinkorswim rollouts is unverified. G12 already states that "no issues once released" is unreachable by post-release testing and reframes the external goal, and G66 already asks for escape-rate metrics and kill criteria. The one usable line, run the smoke tier against the first build out, is a cadence point under G50.
