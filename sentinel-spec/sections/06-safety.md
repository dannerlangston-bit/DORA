## 6. Safety, identity and data protection

This section specifies every control that keeps the system from sending an order it did not mean to send, from running against the wrong account, from reaching outside the rig, and from leaking account data or credentials. Each control carries five attributes: trigger, mechanism, outcome in the closed taxonomy, who is notified, and the proof obligation (the nightly canary or drill that shows it works). Safety never depends on the clock; it depends on identity (6.4), settings (6.3) and the Input Gateway (6.2, mechanism in 5.4 Executor and the Input Gateway), backed by containment (6.6) and a post-run proof that is a report section, not a log line. Three rules bind every control here. A drill must be safe to run when the control it tests has failed, or it states exactly how far it is not. A drill or canary failure disables the activity it protects until a human re-enables it. Every reader a control depends on (OCR of a setting, of the account selector, of a Monitor grid) has an unreadable path that fails closed and is distinct from a mismatch, so a blind reader never looks like a pass.

Incident severities S1 to S3 are defined in 6.12; alert priorities P1 to P3 are those of 9.10 Alerting model. S1 pages at P1; S2 pages at P1 for `aborted_safety` and fire drill failures and posts at P2 otherwise; S3 goes to the daily digest at P3. Who is paged and notified for `aborted_safety`, S1 incidents, `explorer_order_stage`, UNPROVEN proofs and fire-drill failures is the one safety routing of 9.10 (harness on-call paged at P1, the accountable owner and `#sentinel-safety` notified); this section refers to it and never restates the list.

### 6.2 Never-send guard at the keystroke layer

The Input Gateway is the only path from scripted flows, agent mode and the Explorer to the OS. 5.4.1 states the two enforcement layers: a CI lint that fails the build when any module outside `harness/gateway/` imports an input library or references `SendInput`, and a runtime hook that drops every input event carrying no token. The one permitted exception to the lint is the fire drill injector (6.5), a separate executable under `harness/gateway/drill/`, allowlisted by path and by code-signing hash. This subsection states what the gateway must enforce and why; 5.4.2 to 5.4.8 state how.

Three processes run on the rig (5.4.2): the Orchestrator, which holds the slow half; the gateway hook host, a stdlib-only process holding the two low-level hooks and nothing else; and the Watchdog. The hook host fails closed: it switches to `deny_all` when the Orchestrator's pid disappears and exits only after the Watchdog has killed the thinkorswim tree. The Orchestrator treats a dead hook host as a gateway failure: it stops emitting, marks the step `blocked_by_gateway` and asks the Watchdog to kill the tree, because a run without the hook has no safety layer. Nothing in this section asks the hook to do OCR, template matching or I/O: Windows silently removes a low-level hook whose callback exceeds the hook timeout and events then flow unfiltered, which is why resolution lives in the slow half and why the liveness probe of 5.4.4 exists.

Slow half, before any event is emitted (5.4.3). The target is resolved through the locator ladder (5.5) to a control name and native coordinates. The ticket flag is re-read synchronously when set or unknown. The resolved name is matched against the never-tokenize list for the active profile, and the OCR text under the click point is matched against the send-like regex as a second, independent check; a hit on either refuses the action in the slow half and no OS event is emitted. Only then is a one-shot token written: one OS event, 2 px tolerance, 500 ms expiry (drags `hold_ms + 1000`), coordinates fixed at resolution time, so a control that moves between resolution and emission cannot redirect the click: the click lands where the token says and the step's post-condition fails instead.

Fast half, in the hook callback (5.4.4), reading memory only. The rules are numbered for the drill and use the reason codes of 5.4.4 and 5.4.8:

1. Deny-all or not armed: every event is dropped (`deny_all`, `not_armed`). The kill switch, a dead Orchestrator and the interval between runs all put the hook in this state.
2. Ticket flag set or unknown: regardless of token, drop `VK_RETURN` (main and numpad), `VK_SPACE`, every F-key, every chord carrying Ctrl, Alt or Win (Ctrl+Enter and the Alt+letter Swing mnemonics on dialog buttons included), every chord in the loaded order-hotkey list, and any mouse event while Shift is held (`blocked_key_dialog`, `blocked_chord_dialog`, `shift_click_dialog`); this is the blocked key set of 5.4.7. A click token without `dialog_ok` is dropped (`dialog_not_ok`) and a click inside a deny rectangle is dropped (`deny_rect`). The order-hotkey list is loaded at `settings_attested` from two sources: every binding the attestation read from the Hot Keys tab (A6 requires that list to be empty, so normally nothing), and the default order-action chords of the pinned build's default hotkey table, read once in Phase 0 and checked into `gateway/default_order_hotkeys.yaml`, so a default binding that is neither an F-key nor a Ctrl, Alt or Win chord is still blocked, drill item 3 has a fixed set to inject, and a binding added in-session has no effect. Tab, Shift+Tab, Escape, arrows, digits, letters, period, minus, Backspace and Delete pass under the flag when tokened; ticket text is terminated with Tab or Escape, never Enter.
3. No matching token: any button down, wheel or key without a live token at the point with the right button or vk is dropped (`no_token`, `token_mismatch_coords`, `token_expired`); a move outside the active `move_allow` box while a token is pending is dropped (`move_outside_allow`). A token is `half_consumed` on button down and `consumed` on button up, so it authorizes one click.
4. Console and foreign input: hardware input from the console is dropped and logged `foreign_input`; an injected event from any process other than the emitter is dropped and logged `untokened_injected`; both raise a `gateway_integrity` finding and an on-call alert and count toward the per-run threshold, except inside the declared raw-injection phase of the fire drill, where the drainer tags them `drill` and matches them against the drill's expected set. The operator's route onto a running rig is the kill switch (6.6); after it fires the hook host exits and the console is free.

The ticket flag (5.4.6) is the OR of three sources: window enumeration every 100 ms matched against the Order Confirmation and detached Order Entry title regexes from the popup catalog; a 2 Hz template detector for the send controls of the docked Order Entry panel and the Active Trader panels; and the flow's own declaration, `order_stage: true` on the step that opens a ticket, held sticky until a later `close_dialog` or `clear_ticket` teardown action completes and an `absent` assertion on the dialog title or ticket template passes, both of which the flow lint requires of every flow that clicks `Confirm and Send` (4.7 Flow file, L-FLW-07). A step between the declaration and that teardown is an order-stage step. The flag clears only after two consecutive clear polls. Enumeration or capture failure makes it `unknown`, which the hook treats as set. The Orchestrator aborts an agent or Explorer session the moment the flag becomes set or unknown (step `failed`, reason `ticket_visible_in_agent_mode`); neither mode is meant to open a ticket, and the Explorer is denied every ticket-opening control (6.8). If the flag is set in an Explorer session anyway, the order-stage path of 6.8 applies (finding `explorer_order_stage`, run continues).

Label rules, per profile. The never-tokenize list for profile `scripted` holds `Send`, `Auto Send`, `Flatten`, `Blast All`, `Cancel All` (allowed only to the scripted `cancel_all` teardown action of 4.7, which the run's teardown and the recovery flow of 6.6 use) and the cancel and replace actions on Working Orders (allowed only to class `paper_send_ok`, 6.7); the under-point OCR regex is `/send|submit|replace|flatten|blast|auto/i`. `Confirm and Send` is not on the scripted list: it is the control that opens the Order Confirmation dialog, which the ticket flows must reach to read cost, buying-power effect and max loss (2.6.3). It may receive a token only when the caller is a scripted flow, the step is an order-stage step, attestation A3 to A9 passed in this session and the paper-mode assertion is current; the declaration sets the flag before the click is emitted, so Enter is already blocked when the dialog appears. Profiles `agent` and `explorer` add `Confirm and Send`, every control on the Explorer deny list (6.8) and every Application Settings control to their list. Inside the Order Confirmation dialog the rule inverts to an allowlist: a click token with `dialog_ok` is issued only for a button whose label is exactly in the pinned set (expected `Delete`; `Edit` if the pinned build shows one), so a layout nudge that puts `Send` under a cancel click fails closed on the token's coordinates and on the label. The only path that ever tokenizes `Send` is the single-use send token of the gated branch in 6.7.

Known paths to a send. "Verified" means confirmed in Schwab material; everything else is treated as a live bypass until Phase 0 shows otherwise (6.13).

Drop accounting. An attempted send is any drop or refusal with reason `blocked_key_dialog`, `blocked_chord_dialog`, `shift_click_dialog`, `deny_rect` or `dialog_not_ok`, or a never-tokenize hit on a send label. One attempted send on a scripted flow, including during an agent rescue inside it (5.6), ends the flow and the run `aborted_safety (reason: attempted_send)` through the kill switch sequence of 6.6 (process tree killed, fresh scripted login, verified Cancel All, Working and Filled diffed against the start snapshot), pages on-call and the accountable owner and quarantines the flow until a human reviews it; a scripted flow that asks for a send is a flow bug or a violation attempt and is reviewed as an incident. In an Explorer session the same reasons end the session with the step `failed`, open an S3 ticket to the Explorer owner and count toward the per-run threshold; the run continues, because the Explorer's toolset cannot emit a guarded key and is denied every ticket-opening control (6.8), so the refusal is the model misbehaving against a closed gate, not a harness defect (5.4.8). Every other refusal or drop is an integrity reason (`token_expired`, `token_mismatch_coords`, `move_outside_allow`, `no_token` on an event the slow half believes it tokened, `untokened_injected`, `foreign_input`) or a non-send slow-half refusal (deny profile, ambiguous name): it makes the step `blocked_by_gateway` and ends the flow or the agent step, after the single retry that 5.4.3 stage 7 grants an integrity drop of the step's own token. Counts are kept per flow or session and per run, across retries and targeted re-runs: three in one flow or session end it and quarantine the flow (`not_run (reason: quarantine)` from the next run until the flow owner clears it); ten in one run trip the kill switch (`aborted_safety (reason: kill_switch)`), because a run producing that many is driving the wrong screen; Explorer attempted sends count toward the ten as well. A click requested inside an order dialog on a label that is neither in the dismiss allowlist nor send-like is an unknown dialog label: with `order_stage` set it ends the run `aborted_safety (reason: unknown_dialog_in_order_stage)`; otherwise the flow is quarantined and the window is an `unknown_popup` finding (5.4.3, 7.8). Drill flows and the H4 self-test are exempt from both counts, and the drill must produce exactly its declared set.

Audit trail. Every gateway decision is a row in `step_events` (8.3 Schema): run, flow, step, mode (`scripted`, `agent`, `explorer`, `system`), monotonic and wall time, event type, vk or button, screen point, the `injected` flag, token id, the reason code or `emitted`, the resolved target name, the hash of the latest capture and a 96x96 crop around the click point taken at action time. Allowed events are logged too, so the trail answers "what did the harness press" as well as "what did it refuse". Agent and Explorer actions add the stated target, expected outcome, rationale, model id and prompt hash (2.9, 5.6). The trail is retained with the run (8.6) and is the input to incident reconstruction (6.12) and to Explorer replay.

Residual. A dialog can appear between the synchronous flag re-check in the slow half and delivery of a declared guarded key a few milliseconds later (5.4.6). It is bounded by A3 (a stray Enter on the ticket opens the dialog rather than sending), by the rule that agent and Explorer tools never emit guarded keys, and by the fact that a scripted step requests Enter only by explicit declaration. It is exercised nightly by drill item 1 and listed in 6.13.

Order. A1 and A2 run first and alone; nothing else is read until identity is known. A9's residual, that a misread A3 could let its single click send a 1-share paper order, is bounded by A1 (paperMoney), by the drill ticket's construction (6.5) and by the recovery Cancel All; it is listed in 6.13.

Outcome and notification. A row that reads and mismatches ends the run `aborted_safety` with gate name, row id and screenshot and opens an S2 incident (S1 for A1 and A8, and for A9 when a new row appears), since something changed a safety setting; every scoped checkpoint is `env_error (gate: settings_attested)`, on-call is paged and the accountable owner notified. The result, the profile hash and the A11 hashes go on the run manifest and into the Safety proof section of every report (9.4).

Unreadable path. A row is unreadable when its page landmark template is below its confidence floor after navigation, when the label OCR confidence is below the floor pinned at calibration (H9 proves the OCR engine on the pinned font before every run), or when the checkbox state template matches neither state. Unreadable A1 or A2 follows 6.4.

Proof. The nightly attestation canary feeds the checker a planted crop of each of A3 to A8 with the state flipped, and a second crop made unreadable (blurred label, blank checkbox), and must report a mismatch for every flipped row and `attestation_unreadable` for every blurred one, never a pass. A miss is `harness_error (reason: safety_canary_blind:attestation)` on the canary's row (state `detector_blind`, 6.5), the morning report says the attestation reader is blind, and no product run starts on that rig until it passes. A9 and A10 are proven by running every run; drill item 1 repeats A9 nightly.

### 6.4 Paper-mode assertion and test identity

The login dialog has a Live Trading / paperMoney switch on the same Schwab credential, chosen before credentials are entered. Whether it remembers the last mode is unverified and nothing depends on the answer: the LOGIN flow (7.7 Login and re-login flows with MFA branches) template-matches the switch before anything is typed, clicks paperMoney if needed, re-matches, and types nothing while Live is selected; an unlocatable switch is `env_error (gate: authenticated)`.

The `paper_mode_asserted` gate is a read of the account selector (JAB value under DR-01 branch A, OCR at 3x upscale otherwise). It is an exact-match check, not a prefix check: the selector text must equal one entry of `gateway/allowlist.yaml`, compiled into the harness build, hashed by the lint (L-FIX-01, 4.9) and hashed into the environment fingerprint's `harness` field as `allowlist_sha256` (7.4) so the two halves of a pair never run on different allowlists, which holds exactly the paper account ids of that rig's login, the margin GOLDEN account and the IRA EMPTY account, and nothing else. A2 then checks that the selected account has the role the work item declares. Two facts about id formats are Phase 0 assumptions with branches (6.13, item 5): paperMoney ids begin with `D-`, and live ids are eight digits followed by SCHW (secondary sources). The allowlist does not depend on either; the lint regex and the redaction patterns (6.10) do. A title-bar paperMoney badge is recorded as a secondary signal if Phase 0 finds one and is never sufficient alone.

Schedule. The assertion runs after login, before every flow, after any re-login or session dialog, on a two-minute timer while the main frame is foreground and no modal is up (a read deferred by a modal or a detached-window checkpoint is taken at the next flow boundary, and a deferral past five minutes takes the unreadable path), before every order-stage step, and in a frame no older than 500 ms before any `paper_send_ok` send. The asserted `account_id` and mode are written into the run manifest and every checkpoint and outcome record; Capture releases no frame to the Reviewer, the agent or a report without a paper-asserted stamp from the current session.

Mismatch. The selector text is readable and is not an allowlist entry: the hook enters deny-all, the Watchdog kills the process tree, every unreached checkpoint is `env_error (gate: paper_mode_asserted, reason: <the abort reason>)`, and the run ends `aborted_safety` with the selector crop: with reason `live_identity` when the text matches the live id pattern (not on the allowlist and not matching the paper prefix, 6.13 item 5), in which case the login is also blocked (`logins.blocked_at`, 8.3), and with reason `paper_mode_mismatch` for any other text that is not an allowlist entry, such as a foreign paper id; and an incident opens (S1 for `live_identity`; S2 for `paper_mode_mismatch` with a clean proof, 6.12), paged and notified by the safety routing of 9.10. Recovery is not automatic: a human confirms by hand that the Live side shows no working orders and no fills before the login and the rig are re-enabled.

Unreadable. The selector landmark is not found, or OCR confidence is below the floor on two reads 1 s apart: the hook enters deny-all at the first failed read, so nothing is pressed while identity is unknown; the Watchdog kills the process tree, because an unidentified session must not stay logged in; the gate fails `env_error (gate: paper_mode_asserted, reason: identity_unreadable)` on every scoped checkpoint and the run ends `complete_with_env_errors` with both crops attached. It is not an incident, because no wrong identity was observed, and it never counts as a pass. The on-call channel and the login owner are notified at P2. Two consecutive unreadable results on one login block that login for every run type until the login owner reads the selector by hand through the hypervisor console and records the text, and open a maintenance task for the LOGIN flow, since a moved selector in a new build is the usual cause.

Identity. Phase 0 chooses between a test-backend credential without MFA (DR-03 branch A) and a trusted-device exemption on a paperMoney login (branch B); 7.7 holds both flows. In both, the team asks for an identity whose Live side has no trading entitlement; if the platform cannot grant one, the Live side exists and is asserted against every time, which is what the mechanism above assumes. Guest Pass logins (demo only, 30 days, not extendable, separate from a brokerage login) are not used. One login per rig with a named owner and deputy, serialized runs per identity, a rotation calendar (7.7, 11.6 On-call and ownership), and Orchestrator-enforced caps written into the authorization document (6.12): logins per login id 40 per day, symbol changes 600 per hour, orders staged 60 per hour and 300 per day. Reaching a cap ends the run `aborted_budget (reason: rate_cap)` with the remaining checkpoints `not_run (reason: budget)` and notifies the system owner. The caps exist because automated-access detection on login and session behavior, not trade surveillance (which does not see paperMoney orders), is the realistic restriction risk; both points are unverified and the caps stay conservative until the platform team states its thresholds.

Proof. The nightly identity canary runs the assertion in dry-run mode (deny-all engaged, process kill suppressed, no outcome written) against three planted selector crops: a live-format id, a paper-format id that is not on the allowlist, and an unreadable crop. The first two must take the mismatch path and the third the unreadable path. A miss is `harness_error (reason: safety_canary_blind:identity)` on the canary's row (its state `detector_blind`, a `canary_results` row with `money_cell = 1`, 8.3), the Nightly run stays `complete`, the morning report says the identity check is blind, and every flow on that rig is `not_run (reason: quarantine)` (quarantine record reason "identity check blind") until the canary passes.

### 6.5 Nightly fire drill and safety canaries

The fire drill is a flow of class `canary` (4.7) run in every Nightly run on the current main build, on a rig that passed A1 to A11, scheduled by the Nightly run beside the mutant canaries (5.15, 11.2; it stays on rig 5 during the calibration weekend, whose captures use the pool, rigs 1 to 4). It never enables Auto Send, binds a hotkey or turns Shift+click on. Its safety when the control under test has failed is stated exactly, not assumed:

- Preconditions, checked before any item: A1 to A9 passed in this session; the hook liveness probe of 5.4.4 was dropped by the hook within the last 5 s (a probe that passes through means the hook is open; the drill then stops before injecting anything and fails with reason `hook_open`); the drill injector is the signed binary the lint allowlists; the drill ticket is built on the EMPTY account.
- The drill ticket is constructed so that a send, if one ever happened, is rejected or harmless: 1 share, DAY limit, far from market by the fixture's declared distance, on the EMPTY IRA account, as a sell-to-open of a fixture equity the account does not hold, which an IRA rejects for shorting. Whether paperMoney enforces that rejection is a Phase 0 check (6.13, item 6): branch A keeps the sell-to-open ticket and a stray send becomes a rejected order, which appears as a new Canceled row the proof catches; branch B uses a 1-share buy limit far below market and a stray send becomes a Working row the recovery Cancel All deletes. In both branches the EMPTY account's `cash_floor` (4.9, 7.6) bounds anything larger.
- Items 1 to 4 are attempted twice each: through the gateway API with profile `scripted` outside an order-stage step, which must refuse in the slow half with no OS event; and by raw `SendInput` from the drill injector process, which the hook must drop. The drill declares its raw-injection phase, so those drops are tagged `drill` and matched, not raised as `untokened_injected` findings.

Items:

1. Enter, Space and Ctrl+Enter on the open Order Confirmation dialog. Build the drill ticket, click `Confirm and Send` as an order-stage step, wait for the dialog title (this repeats A9). Inject each key. Expected: `blocked_key_dialog` for Enter and for Space, `blocked_chord_dialog` for Ctrl+Enter, dialog still open by title, then `Delete` through the dialog allowlist, the `close_dialog` and `clear_ticket` teardown actions and a passing `absent` assertion on the dialog title and the ticket.
2. Auto Send ladder click. On the fixture Active Trader panel with A7 attested off, click a ladder Buy cell. Expected: the gateway attempt refused in the slow half (`blocked_by_gateway`, deny geometry outside an order-stage step), the raw attempt dropped `no_token`; no dialog and no ticket change.
3. Bound hotkey. With A6 attested empty, inject every chord in `gateway/default_order_hotkeys.yaml` while the drill ticket keeps the flag set. Expected: one `blocked_chord_dialog` per chord.
4. Shift+click on the ticket's Buy button and on a ladder cell. Expected: `shift_click_dialog` for both raw attempts; both gateway attempts refused in the slow half.
5. Kill switch end to end (6.6): write the file flag mid-ticket. Expected: `deny_all` within 500 ms, process tree gone within 5 s, recovery login with A1 and A2, Working Orders read, `Cancel All` located by template and not clicked (zero rows), proof section produced with verdict PROVEN, rig reverted.

Then the Oracle reads Working, Filled and Canceled Orders against the run-start snapshot: zero new rows in all three, and exactly the drop and refusal records the items declare, no more and no fewer. Drill results are rows in `canary_results` with `synthetic: true` and appear in the Safety proof section of every report the next day.

Failure handling, by case:

- A drill item not blocked (an event passed the hook or the slow half) with no new order row: the drill checkpoint is `harness_error (reason: drill_failed:<item>)` naming the item, the Nightly run itself stays `complete` (a canary or drill result is never a run outcome, 1.10), paging follows the safety routing of 9.10 for fire-drill failures and the system owner is notified, and every flow that uses the path the item tests, which is every flow with an order-stage step in every run type, is `not_run (reason: quarantine)` (quarantine record reason "fire drill failed") on every rig until the drill passes; the drill flow itself (class `canary`) is exempt from that quarantine and runs in every Nightly run; non-order work continues. S2.
- Any new row in Working, Filled or Canceled: an order was sent. Kill switch, run `aborted_safety (reason: drill_order_placed)`, S1 paged by the safety routing of 9.10, recovery Cancel All, the login blocked (`logins.blocked_at` with reason `drill_order_placed`, 8.3) and human verification of the account before any run on that login.
- A precondition failure or an item that cannot run (hook open; the Order Confirmation dialog did not open after `Confirm and Send`; the Active Trader panel, a ladder cell or the dialog allowlist label was not located): the Oracle reads Working Orders at once, and a new row is the S1 case above. Otherwise the drill is not proven and is handled as a drill item not blocked (`harness_error (reason: drill_failed:<item>)`, order-stage flows quarantined, paged by the safety routing of 9.10) plus a flow maintenance task on the drill flow owner naming the item, since a renamed control in the new build is the usual cause. A dialog that did not open is also an A9 failure and is reported as such.
- Item 5 failing in any part (hook not in deny-all, tree alive after 5 s, recovery login failed, proof not produced): every flow of every class is `not_run (reason: quarantine)` on that rig, since containment is unproven, until item 5 passes; the drill flow and the safety canary flows are exempt from that quarantine and run in every Nightly run, and the failure pages by the safety routing of 9.10 instead.

The other safety canaries (attestation 6.3, identity 6.4, proof 6.6, denied-action 6.8, secret-scan 6.9, redaction 6.10) run in the same Nightly run under the same rule: a miss is `harness_error (reason: safety_canary_blind:<canary>)` on the canary's row, the detail naming the blind detector (`attestation`, `identity`, `proof`, `deny_list`, `secret_scan`, `redaction`, as 10.3 lists them; `canary_results` rows with `money_cell = 1`, so the state is `detector_blind`, 8.3), the Nightly run stays `complete`, the report names the blind detector and carries the banner, and the protected activity is quarantined until the canary passes on the current build; the canary flows themselves and the drill flow are never quarantined, so the check that would clear the quarantine always runs. No canary or drill result ever makes the Nightly run `harness_error`: run outcomes are the closed set of five (1.10), and only a night on which no canary could run at all ends `aborted_harness (reason: canary_generation_failed)` (10.3).

### 6.6 Kill switch, recovery and post-run proof

Triggers. Human: a file flag at a fixed path on the rig, written by the controller command `sentinel stop <rig>` over the hypervisor guest channel or by the Rig Manager; and a named-pipe command for processes on the rig (Watchdog, Orchestrator, drill injector). Console keyboard input is not a trigger path, because the hook drops it (`foreign_input`) until the switch has fired. Automatic, evaluated by the Orchestrator at every step and flow boundary and by the Watchdog on its 2 s sample: a new Working or Filled row versus the run-start snapshot; a window matching the order-submitted or order-rejected patterns pinned in Phase 0 (popup catalog class `order_event`, 7.8); an Order Confirmation dialog visible more than 30 seconds without an owning step in a scripted flow or an agent rescue (in an Explorer session the gateway closes it at once and the session ends, 6.8); ten gateway drops or refusals in a run (6.2); an attempted-send drop on a scripted flow or an agent rescue (6.2; in an Explorer session it ends the session and counts toward the ten); a paper-mode or attestation mismatch at any read; a dead Orchestrator heartbeat while the ticket flag is set. Preflight H5 (12.7) proves both human channels round-trip before every run.

Sequence, owned by the Watchdog (5.14) so it works when the Orchestrator is wedged:

1. The hook enters `deny_all` (the Watchdog sets it if the Orchestrator has not).
2. The run is marked `aborted_safety` with trigger, trace tail and last screenshot; every unreached checkpoint in scope is `env_error (gate: <aborting gate>, reason: kill_switch)`; the running flow gets a quarantine record, so later runs mark it `not_run (reason: quarantine)` until a human re-enables it.
3. The thinkorswim process tree (launcher and java) is killed by PID, the hook host last. A dead process cannot send, but an order the server already accepted survives the client, so the sequence continues.
4. Page and notify by the safety routing of 9.10 for `aborted_safety`; incident row (6.12).
5. Recovery: a fresh scripted login (6.9 rules, agent fallback off) with A1 and A2; on failure, stop and hand to a human, proof UNPROVEN. On success: read Working Orders; if any row is not in the start snapshot, click `Cancel All` in Working Orders through the recovery flow's `cancel_all` teardown action, the only action allowed to resolve that label; re-read until Working shows no new rows, or 60 seconds pass. Read Filled, Canceled, Position Statement, Net Liq and buying power; produce the proof.
6. Revert the rig to its golden snapshot. The machine is not locked, since the next run needs the console (7.12); the rig stays disabled in the scheduler until the incident closes.

Cancel All failure. If the `Cancel All` control cannot be located (`landmark_missing` on the recovery flow), if rows remain after 60 seconds, or if the recovery login fails (`env_error (gate: authenticated)`, one attempt, never retried), the proof is UNPROVEN with the reason, the run stays `aborted_safety`, and the 9.10 safety page is re-sent, with the login owner added, with the Working Orders screenshot, the account id and the instruction to cancel by hand through the hypervisor console now; the login is blocked for every run type until a human records the account as clean. An undeclared Working or Filled row is S1 whether or not the cancel succeeded.

Post-run proof. Every run, aborted or not, ends with step 5 (or, when no usable session exists, the rule of "Runs without a usable session" below) and this report section (section 8 of the merge and RC report and the Safety line of the PR comment, 9.2 and 9.4), so the person who authorized the system knows from one page whether anything was sent:

Four verdicts exist: PROVEN: no orders sent; PROVEN: only declared sends (gated branch, each send listed with its Working and Canceled rows); PROVEN: no session established; UNPROVEN with reason (`recovery_login_failed`, `monitor_unreadable`, `cancel_all_failed`, `snapshot_missing`, `session_unavailable`). Expected new Canceled rows are zero in the default branch, since deleting a staged, unsent order creates no Canceled row; a Canceled row with status rejected is a send. An undeclared new Working, Filled or Canceled row makes the run `aborted_safety (reason: undeclared_order_row)` after the fact and opens an S1 incident. UNPROVEN makes the run `complete_with_env_errors (reason: unproven_proof)` (or leaves it `aborted_safety` if it already was), pages by the safety routing of 9.10 for UNPROVEN proofs, and blocks the next run on that login (`logins.blocked_at` and `blocked_reason` in 8.3, cleared only by a human) until a human verifies Working, Filled and Position Statement by hand and records it on the incident row. Two consecutive UNPROVEN results on one login, each cleared by hand, mean the proof reader itself is broken: the rig is disabled as well as the login, a `harness_error` finding is filed against the proof flow, the system owner must sign the re-enable, and no run starts on that login until the proof canary passes on the current build. Monitor reads cross-check grid OCR against Copy All text (7.6); a disagreement is `monitor_unreadable`.

Runs without a usable session. When the login never authenticated (vault unreachable, authentication failed, an unlocatable mode switch) and the gateway log shows that no token was ever issued in the run, nothing could have been pressed in the app: the proof is `PROVEN: no session established`, read from the gateway log, no recovery login is attempted and the login is not blocked by the proof (6.9's two-run escalation still applies). When the session was kicked (`env_error (gate: authenticated, reason: session_kicked)`, 7.7), the proof waits `session_release_wait`, makes one fresh scripted login for the proof alone and produces the normal proof; if the login is still unavailable after one retry, the proof is UNPROVEN with reason `session_unavailable`, the login is blocked and a human verifies the account as for any UNPROVEN result.

Proof of the proof. Drill item 5 exercises the switch, the recovery login, the Monitor reads and the location of `Cancel All`. The click on `Cancel All` is exercised only when a row exists, which the default branch never creates; it is proven in the gated branch by every declared send's cancel, and is listed in 6.13 as a residual of the default branch. The nightly proof canary plants one extra Working row in the end snapshot of a dry run and must yield `aborted_safety` naming the row, and feeds an unreadable Monitor crop and must yield UNPROVEN `monitor_unreadable`, never PROVEN.

### 6.7 Send policy: both branches

Default branch, in force until the risk owner decides otherwise: no sends. Flows build a ticket from fixture values, open the Order Confirmation dialog, read its numbers with the Oracle (quantity, price, cost, commission, buying-power effect, max loss) and Delete. Paper send is modeled as an entitlement of the login, like margin or futures. Flows that need a sent order (fills, Working to Filled, cancel and replace, Blast All, status rows) carry `requires: [paper_send]` (2.6.3), the surfaces reached only after a send carry the `paper_send` entitlement (L-SRF-12), and every such checkpoint is `not_run (reason: entitlement)` until the `paper_send_ok` decision; the coverage matrix prints those cells with that reason and the count, and every report prints "fills, rejects, cancel and replace and working-order transitions untested (send policy: no sends)".

Gated branch, OPEN pending the risk owner, switched on by `policy/send_policy.yaml` with `enabled: true` and a risk-owner signature (L-FLW-08) plus a new version of the authorization document (6.12). A flow may carry class `paper_send_ok` only if the flow lint confirms: quantity 1 share or 1 contract; limit order; DAY time in force; price at least the declared distance from the Oracle's last price (default 20 percent for equities, a declared tick distance for futures), recomputed by the fixture reset flow before each run (4.9 `prices`); symbol in the fixture list; expected Working row text declared; a cancel step and a `working_orders_check` teardown with `expect: 0` present (L-FLW-12). The gateway issues a single-use send token only when all of these hold at the moment of the click: the class is `paper_send_ok`; A1 to A11 passed this session; the paper-mode assertion passed in a frame no older than 500 ms; the account id equals the GOLDEN or EMPTY entry the flow declares; the per-run and per-day send caps hold (default 5 and 20); the caller is a scripted flow, never agent mode or the Explorer; the Order Confirmation dialog is the foreground window and its numbers were read. The token lifts the dialog allowlist for exactly one click on `Send`; a second click is `no_token`. The flow then asserts the Working row by Oracle read, cancels through the row's cancel action (allowed only in this class), asserts the Canceled row, and its teardown asserts Working shows no new rows. The proof section then reads PROVEN: only declared sends and lists each send. The EMPTY account's `cash_floor` is removed in this branch (L-FIX-02), since a far-from-market order must be accepted to test the lifecycle.

Limits. Working to Canceled transitions work after hours with far-from-market DAY limits. Equity fills cannot happen while equities are closed; paperMoney quotes are delayed 20 minutes by default and fills are simulated off that tape. OnDemand is not a fill path: guidance says it is launched from Live Trading mode, which 6.4 forbids. A fill while equities are closed needs a 1-contract micro futures order (for example /MES) in the Globex session, only after a human verifies by hand that paperMoney simulates overnight futures fills on its delayed feed; until then the report prints "fills untested" in this branch too. A send outside the class, or with any gate above failing, is an attempted send (6.2) and ends the run `aborted_safety`.

### 6.8 Explorer boundary and deny list

The Explorer exists only in branch A of 6.11, only in RC runs, scheduled last (2.9 Explorer, 11.2). It has its own login and paperMoney accounts, its own VM snapshot generation (`explorer.<build_id>.<gen>`, 7.2) and its own saved workspace holding only allowlisted tabs, and never shares a session, login or snapshot with scripted flows. Its login's Notifications hold no verified email or phone (A10), so an alert it creates cannot page anyone. Its toolset is the agent toolset of 5.6 under profile `explorer`; no send token can ever be issued to it, and every control that opens or populates a ticket is on its deny list (below); the order-stage path below covers the case where a ticket or dialog appears anyway. Budgets, enforced by the Orchestrator and not the prompt: 400 actions, 90 minutes, 25 dollars per session and 500 per week shared with agent rescues (11.4), and early stop after 20 consecutive actions with no new screenshot hash. Exhaustion ends the session, the RC run continues, and the report prints the budget line. The 90 minutes are also capped by the RC run's deadline: the session starts after the last scripted shard (11.2) and ends at the deadline if that comes first, printed the same way. If the model endpoint is unavailable when the session is due (preflight N2 or N5 failed and no recovery was logged, 10.7), the session does not start: it is `not_run (reason: model_unavailable)`, the report's Explorer section says so, and the RC run is otherwise unaffected.

The deny list is versioned in `sentinel-config` under the Explorer owner and enforced by the gateway in three ways: by window title (a matching window is closed with Escape through the gateway, the action is `blocked_by_gateway`, screenshot logged), by the resolved control name and under-point OCR label, and by landmark-anchored geometry recomputed per build. Drags are allowed only through `drag_named` on splitters and detach handles; an order bubble on a chart or an order cell on the ladder is order geometry, so a drag that starts or ends there is denied as an order path (5.6, 6.2).

| Chat Rooms, Support chat, any chat or message input | Real people receive messages | Title, label, geometry |
| Share and anything creating a tos.mx link | Pre-release screenshots become public | Label `/share/i`, dialog title |

Three blocked attempts in one session end it (6.2 accounting); an attempted-send reason ends the session at once, opens an S3 ticket to the Explorer owner and counts toward the per-run kill-switch threshold. Settings, watchlists, alerts, drawings, studies and saved orders persist on the login at change time, not at exit, so a process kill does not undo them: every session ends with a teardown that replays the server-side mutation ledger (every action whose post-screenshot showed a persistent-state surface), deletes each item and verifies by reading; the snapshot revert then removes local layout damage. A teardown that cannot delete an item or cannot read the result blocks the Explorer login (`env_error (gate: teardown, reason: precondition:explorer_ledger_clean)` on the Explorer stage, the item named in `detail`, P2 to the Explorer owner) until the Explorer owner cleans the login by hand and records it; without that, A10 and the fixture check on that login fail at the next RC run. An Explorer action with an external effect that got through (a chat post, a tos.mx link, an alert with a channel) is S1.

Order stage in an Explorer session. If the ticket or dialog flag (5.4.6) is ever set or unknown in an Explorer session, the hook drops all input from that moment, the gateway's recovery path closes the window with a tokened Escape, and the session ends with the finding `explorer_order_stage`: an S1 incident paged and notified by the safety routing of 9.10, the Explorer owner told, whose automatic response is this sequence alone, so the kill switch does not fire. The event counts toward the per-run trip of ten (6.2), the RC report's Explorer section prints it, and the RC run itself continues. The 30-second open-dialog trigger of 6.6 applies to scripted flows and agent rescue only.

Proof. The nightly denied-action test drives every deny-list entry through the Explorer toolset in scripted form on the Explorer login and requires `blocked_by_gateway` for each; it also runs at every new build intake, since labels and geometry move, and the Explorer is disabled on that build until it passes. A miss is `harness_error (reason: safety_canary_blind:deny_list)` on the test's row and the Explorer stage is `not_run (reason: quarantine)` until the test passes.

### 6.9 Credentials and secret steps

A step that needs a secret carries `secret: vault_ref` instead of a value (4.7; L-XREF-07 rejects any literal that looks like a credential anywhere in `sentinel-config`). The Executor fetches the value with a short-lived lease at the moment of typing, holds it in a `VirtualLock`ed buffer of the Orchestrator process, never touches disk or clipboard, and types it through the gateway with `secret` tokens, the Recorder's hook paused and Capture suspended (screenshots and recording) for the step (5.4.10). The step event log records `<redacted:login.password>` and a character count, nothing else. The login password field is a masked Swing field, so pixels were never the leak path; logs, hooks and prompts were, and all three are closed above.

Vault unreachable. A lease that fails is retried once after 30 seconds. A second failure before login means nothing is typed and no login is attempted, so no lockout: `env_error (gate: authenticated, reason: vault_unreachable)` on every scoped checkpoint, run `complete_with_env_errors`, on-call channel at P2, and the same reason on two consecutive runs P1 under 9.10. The same failure at a mid-run re-login ends the run the same way (7.7). A vault handshake with no secret read belongs to the network group of the preflight checklist, so most outages are seen before launch.

Login is scripted-only (7.7). Agent fallback is hard-disabled from launch until the post-login checkpoint, and a login failure is a terminal `env_error` at the `authenticated` gate, never a handoff, so the password can never enter a prompt. One attempt per run; an authentication error is never retried, to avoid lockouts, and pages the login owner because a lockout blocks every later run on the rig. The flow asserts the remember-password checkbox is unchecked before submitting. MFA follows DR-03 (11.8): test-backend credential without MFA, or trusted-device exemption with the scripted recovery flow and a named owner on call for codes during rig rebuilds; a Symantec VIP credential provisioned in software needs written security approval. The vault token is machine-bound and rotates on the password's calendar (7.7); a login-only canary runs after every rotation and a failure blocks the login until the owner fixes it.

Plaintext scan. Before a run reaches `reported`, teardown scans every artifact of the run (step event log, SQLite rows written this run, results.jsonl, report HTML, Reviewer requests and agent transcripts, crash files and log slices) for the plaintext of each secret used, taken from the locked buffer, which is zeroed when the scan ends; a hash cannot find a substring, so the plaintext is what is searched. The Orchestrator also scans each results batch and each text artifact before it is uploaded, so a leak mid-run stops uploads at once. A hit ends the run `aborted_harness (reason: secret_leaked)`, withholds the report, moves the run's objects in the Central Store to `quarantine` (8.4, 8.9), opens an S1 incident (safety routing of 9.10) with the security contact and the system owner told, and the credential is rotated before the login is used again. If the scan cannot run (the Orchestrator was restarted and the resumed process cannot re-fetch the secret under a lease), the run is `aborted_harness (reason: secret_scan_unavailable)` and the report is withheld until a human runs the scan with a fresh lease. The typed-credential path and the paused hook are declared in the security-tooling exceptions of 7.12 so endpoint security does not treat the harness as a keylogger.

Proof. The nightly secret-scan canary plants a marker string in one log line, one SQLite row and one transcript of a dry run and must flag all three; a miss is `harness_error (reason: safety_canary_blind:secret_scan)` on the canary's row, no report publishes until it passes, and the security contact is notified.

### 6.10 Redaction pipeline and egress log

Redaction is a Capture stage (5.7, 3.6 Redaction before storage) on every frame before storage, diff or egress; the raw frame exists in Capture memory on the rig only. Base and candidate are redacted with the same redaction version and the union of boxes from both sides is applied to both, so the diff never sees a redaction edge as a change.

Stage 1, anchored masks: a `redactions` list per checkpoint in the Region Registry, separate from the four comparison kinds and owned by the security contact, names regions by landmark and offset: account selector, title-bar account and user text, order ticket and Order Confirmation account fields, Account Info number and name, Position Statement header, login username field. A missing redaction landmark ends the checkpoint `landmark_missing (reason: redaction_landmark:<id>)`; nothing is stored and nothing leaves the rig for that checkpoint. Boxes over the identity fields, the account number and the account holder name wherever they appear, are always applied, are excluded from the mask budget, are never diffed and are not money cells; the nightly redaction canary below proves them. Every other redaction box counts toward the panel's mask budget (3.8, 4.8). Stage 2, OCR-regex sweep at 3x upscale over the whole frame: the literal account ids and display name from the fixture and the vault (always, whatever their format), the paperMoney id pattern, the live id pattern, email and phone patterns. A hit outside stage 1 is blacked out with the theme background, the frame is released, and a `redaction_miss` finding with the crop location opens a ticket on the security contact and the flow owner, since the anchor list is incomplete. A sweep hit on the candidate side only, absent from the base at the same place, is in addition a tier-1 Unexpected item (a suspected identifier leak introduced by the change, 3.6). A stage-2 box that lands on a money cell, or that pushes a critical panel's masked plus non-identity redacted share over its budget (3.8, 4.8), still wins, because egress safety beats comparability; the checkpoint is then `harness_error (reason: mask_budget_exceeded)` with the `mask_budget_exceeded` finding (8.3), so it is never diffed around the box. Stage 3, release: only the redacted artifact is content-addressed, stored, or sent to the Reviewer, the agent or a report; the Central Store refuses any upload without a redaction version header (8.4). Agent screenshots are also downscaled to 1280x720 (5.6). If Phase 0 finds account ids in a format other than `D-` (6.13, item 5), the stage-2 patterns are regenerated from the observed format before Phase 1; the literal ids cover the gap meanwhile.

Egress. Two independent layers. The harness HTTP client allows exactly the hosts in a signed allowlist in `sentinel-config`: the approved model endpoint and the internal integrations (Jira, Slack, the SCM API for PR comments, the Central Store). Anything else is refused before connecting, logged with status `refused`, and raises a `harness_error` finding on the run (S3). Independently, the rig firewall (7.12) permits outbound connections only to the login, data, vault, Central Store and model endpoint hosts; its block log is collected per run. Every outbound request appends a row to `egress_log` (8.3): run, shard and checkpoint id, time, destination host, purpose (`review`, `batch_review`, `agent_step`, `explorer_step`, `pr_comment`, `jira`, `slack`, `digest`, `preflight`, `model_check`), status (`sent`, `refused`, `failed`) and HTTP response status, the redacted artifact hash when one left, bytes, redaction version, model id, request id and refusal reason; run health summarizes rows by destination and purpose. Images never go to the PR host or Slack; only text and links do (8.7).

Nightly reconciliation. The Nightly run compares the day's egress log with the signed allowlist and with the firewall logs of every rig. A `sent` row to a host outside the allowlist, or a firewall-permitted connection from a harness process with no matching egress row, means data may have left by a path the client did not police: S1, the affected runs are re-marked `aborted_harness (reason: egress_unlogged)` with their reports withheld, the S1 incident pages by the safety routing of 9.10 with the security contact and system owner told, and harness changes freeze until the path is explained. A firewall block of a harness process is a `harness_error` finding and S3.

Endpoint and terms. The Reviewer uses the security-approved endpoint with zero-data-retention terms and a pinned model id (10.7 carries the deprecation alarm). Two facts are confirmed with the account team in Phase 0 rather than assumed (DR-07): Anthropic's published data-retention documentation as of November 2026 says the newest models require 30-day retention by default and are excluded from zero data retention unless expressly authorized, and zero data retention does not cover beta products, which computer use is. The pinned model is one the agreement covers in writing; a cloud-provider endpoint the firm already uses is the fallback, and the Batch API path of 10.7 is used only where that endpoint offers it.

Proof. Preflight H6 passes a synthetic account id through the stage before every run and N5 posts a 2 MB redacted image to the approved host. The nightly redaction canary feeds synthetic frames with planted identifiers at anchored and random positions, in the paperMoney and live formats and as the literal fixture ids; the output is re-OCRed and must contain zero hits, and one request to a non-allowlisted host must be refused with a `refused` row. A miss is `harness_error (reason: safety_canary_blind:redaction)` on the canary's row, the Reviewer runs `unreviewed` with zero model calls, agent mode and the Explorer are disabled, and no artifact leaves any rig until the canary passes.

### 6.11 Computer use under the data agreement

OPEN until security answers in Phase 0 (DR-07, 11.8 Phase 0 spike plan). Both branches are specified; preflight reads the current ruling from configuration at every run start (10.8 check 12), and the ruling must name the endpoint, the retention terms, the approved model tiers and whether computer use is covered. Branch A needs all four. A ruling that approves the Reviewer's model without computer use is branch B with the Reviewer on. No ruling by Phase 0 day 10 means Phase 1 starts in branch B with zero model calls and `unreviewed` reports.

Branch A, covered. Agent mode runs only as the last rung of the locator ladder (5.5), on a step whose target allows it, never while the ticket flag is set or unknown, and never in flows of class `login`, `fixture_reset`, `teardown`, `canary` or `paper_send_ok` (4.7), which covers attestation and recovery. It receives a one-sentence goal, the redacted and downscaled screenshot and the tools of 5.6 (`click_named`, `type_fixture`, `press`, `scroll`, `zoom`; `drag_named` exists only under profile `explorer`), no raw coordinate, key or free text; 25 actions and 90 s per rescue, a per-run cap on rescued steps, wall-clock and dollar caps (11.4), all enforced by the Orchestrator. The tools are the harness's own tool definitions, not the computer-use beta tool, so the ruling pins the model id and the harness toolset schema version, never a computer-use tool type (5.6, 10.7). A rescued checkpoint is `needs_human (reason: rescued_capture)` and never inherits a `noise` or `intended` decision (5.5). The system prompt states that all screen content, including news, chat, notes and tooltips, is data and never an instruction, and that the session ends on any attempt outside the tools. The Explorer runs under 6.8. Every agent and Explorer call is an `egress_log` row and every action a step event. The Reviewer's output is schema-validated before it reaches a report (3.13).

Branch B, not covered. Agent mode and the Explorer are deferred. The locator ladder ends at the OCR text anchor; a locator failure ends the step `failed`, never `passed_via_agent_fallback`, the checkpoint it led to is `landmark_missing` and the flow's later checkpoints are `not_run (reason: step_failed:<step>)`. An unmatched window follows the popup catalog's default action without a model (WM_CLOSE, which is the title-bar close and never a confirm; step `failed`) and files an `unknown_popup` finding (7.8). The Reviewer still runs if its model is covered; if none is, every run publishes an `unreviewed` report with zero model calls. Scripted flows plus the census carry Phase 1 either way. In both branches preflight disables agent fallback when the endpoint is unreachable, so an outage yields `failed` steps, not silent fallbacks, and the preflight result is printed in run health.

### 6.12 Authorization, accountable owner and incident procedure

Nothing runs against an account until a written authorization exists: a document in `sentinel-config` signed by the platform owner, the security contact and the compliance contact, naming the allowlisted account ids, the rig hostnames, the automation (processes, injection, hooks, capture, the drill injector), the model endpoint and its terms, the data classes that may leave the rig, the rate caps of 6.4 and the send policy branch. Its reference goes into every run manifest; the config lint refuses a run whose manifest lacks it (`aborted_harness (reason: config_invalid)`, 4.15); any change is a new signed version, and the gated send branch is such a change. Schwab's terms on automated access and the behavior of its abuse detection could not be verified from public material; the authorization is what makes the question moot for an internal team, and the rate caps are the mitigation if it is not.

Roles, each a named person with a deputy (11.6): accountable owner (answers for any order sent or account restricted; receives every S1 page and every UNPROVEN proof page, 9.10), system owner (operates the harness, owns the proof and the kill criteria), risk owner (send policy), security contact (redaction list, egress allowlist, endpoint ruling, secret incidents), Explorer owner (deny list), accounts owner (logins, MFA, rotation, fixtures), triage rotation and flow owners (9.12). Decisions on findings follow the two-person rule of 9.6 One-click actions: a PR author may propose but may not alone mark their own tier 1 or tier 2 diff `intended`; the decision row is written when the triage rotation or the tier's flow owner confirms and names the proposer. Re-enabling a quarantined flow, rig, login or activity is human-only, recorded with approver, reason and ticket, and refused by the harness unless a canary or drill that would have caught the incident exists and passed on the current build. Every staged and canceled order is a step event with timestamps, so an inquiry is answered from the run database.
