## 10. Reliability of the system itself

Sentinel's own failures must be as visible as the app's. This section specifies how the harness, the rigs, the network, the account and the model API fail into the closed outcome taxonomy of 1.10 Outcome taxonomy (nothing here adds an outcome; it adds reason codes, listed at the end of 10.1), and the nightly proofs that the detector still sees what it claims to. The component contracts are in 5.14 Watchdog and 5.15 Canary Service and Calibration Service; this section owns the rules they follow.

### 10.1 Failure classes and the diff-engine rule

Three classes, one rule: no capture produced under a harness, environment or app failure enters the Diff Engine, the Invariant Checker or the Reviewer. Only comparison outcomes feed the false-positive and escape metrics; the three classes feed run health.

| Class | Definition | Detected by | Checkpoint outcome | Step and run effect | Who sees it |
|---|---|---|---|---|---|
| Harness failure | Our code or config failed: Orchestrator crash or heartbeat silence, Watchdog death, Gateway hook host death (one restart per shard out of its own budget, then `aborted_harness (reason: hook_lost)`), unhandled exception, canary generation failure, SQLite or artifact store error, heartbeat file unwritable (a registry or config lint failure is not this class: it ends the run `aborted_harness (reason: config_invalid)` before any capture, 4.15 Cross-file rules and the lint pipeline) | Watchdog, exception handlers, preflight group H (12.7 Preflight checklist) | `harness_error` with a reason code (a listed code, else `exception:<class>`), last screenshot, stack trace and a Watchdog event id | Step `failed`; resume at the next flow boundary; `aborted_harness` once the restart budget is spent; unreached checkpoints of an `aborted_harness` run are `harness_error` with the run's abort reason as the reason (for example `harness_error (reason: dead_man)` or `harness_error (reason: orchestrator_restart_budget)`; 1.10) | On-call channel; run health block of every report |
| Environment failure | The world around the app failed: a state machine gate, rig lost, console locked, wrong display mode, network or backend down, login failure, session kicked, fixture drift, version mismatch | Gate anchor checks, preflight groups R, B, N and G, Rig Manager heartbeat | `env_error` with gate name and screenshot | Unreached checkpoints in the shard get `env_error` with the same gate; run `complete_with_env_errors` | On-call channel, one alert per run per gate; coverage matrix shows the cells as not covered |
| App failure | thinkorswim died or stopped responding: JVM crash, hang (Event Dispatch Thread frozen past max wait), OutOfMemoryError, process tree gone | Watchdog process and staleness checks, crash files, client log signatures | `assertion_failed (assertion: app_alive)` on the checkpoint being captured, with the cause `jvm_crash`, `hang`, `oom` or `process_exit` in `detail` (4.13); `not_run (reason: app_crash)` for the rest of that flow; a tier-1 finding `app_crash` with hs_err_pid, dumps and the log slice attached | Step `failed`; relaunch through every gate and resume at the next flow boundary, where the next flow starts from its preconditions (a sweep ladder never resumes mid-way, 10.2); the first three app failures in a shard are each relaunched, and a fourth marks the remaining checkpoints `not_run (reason: budget)` and ends the run `aborted_budget (reason: app_restart_budget)`. A crash or hang during the gate sequence of a relaunch (between `launched` and `canary_flow_passed`) is another app failure: `assertion_failed (assertion: app_alive)` on the first unreached checkpoint of the shard, the `app_crash` finding, and one more relaunch consumed; it is never `env_error`. The same holds at the shard's first launch: a crash or hang signal before `launched` passes, or anywhere in the first gate sequence, is `assertion_failed (assertion: app_alive)` on the shard's first checkpoint, the `app_crash` finding and one relaunch consumed, and with the relaunch budget spent the run is `aborted_budget (reason: app_restart_budget)` with the unreached checkpoints `not_run (reason: budget)` (10.2 sampling rule 3, 5.2). On `process_exit` the Watchdog first checks for a running launcher update and a changed build manifest; if either is present the event is `env_error (gate: launched, reason: version_changed_mid_run)` for the checkpoint in progress and the rest of the shard (7.3), with no `app_crash` finding and no relaunch consumed | Unexpected section, tier 1, with artifacts; never sent to the Reviewer |

Three app-failure cases are distinct and never merged:

1. Process gone or EDT frozen: the trio above. It is a product finding, so the Reviewer may never reclassify it and it never appears as `env_error`.
2. An app error or exception dialog on screen at capture, with the process alive: `invariant_violation` INV-14 (2.7 Layout invariants). The popup catalog routes error dialogs to INV-14, not to the dismiss list (7.8 Popup catalog policy and starter entries). The Watchdog still collects the log slice and attaches it to the finding.
3. Restart budgets exhausted: run `aborted_budget` (app relaunches) or `aborted_harness` (Orchestrator restarts), per 10.2.

A step's locator failing on every rung is not a harness failure even when the agent rung is disabled: the step is `failed`, the checkpoint it led to is `landmark_missing`, later checkpoints of the flow are `not_run (reason: step_failed:<step>)`, and the failure is a finding beside the checkpoint (5.2 Orchestrator). When two detectors fire in one step, the 1.10 precedence applies: environment over app over harness (`env_error`, then `assertion_failed (assertion: app_alive)`, then `harness_error`). A hang during a network drop is `env_error (gate: connectivity)`; a hang with the network healthy is an app failure; an Orchestrator exception raised while handling either is evidence on the same checkpoint, not a second outcome and not a harness failure of it.

Reason codes this section introduces, for the reason table in 12.2 Outcome taxonomy: `harness_error`: `orchestrator_died`, `watchdog_dead`, `heartbeat_unwritable`, `disk_full`, `artifact_persist_failed` (8.9), `hook_lost`, `canary_generation_failed`, `detector_blind` and `detector_degraded` (the missed mutant's synthetic row, 10.3), `canary_path_divergence`, `safety_canary_blind:<canary>`, `drill_failed:<item>`, `validation_self_test`, `chaos_unobserved`, `aa_drift_global`, `rig_lost`; `env_error` gates: `connectivity`, `rig_lost`, `preflight.<item>`; `not_settled`: `unstable`, `aa_drift`; `not_run`: `app_crash`, `budget`, `model_unavailable` (an Explorer session or agent-only step skipped because the model endpoint is down, 10.7); `needs_human`: `reviewer_unavailable`, `reviewer_cap`, `global_shift`, `uncalibrated`; `assertion_failed` assertions: `app_alive` (cause `jvm_crash`, `hang`, `oom` or `process_exit` in `detail`, as 4.13 stores it), `size_reached` (2.5.1 Hosting modes) and `soak.<metric>`; run `aborted_harness` reasons: `preflight.<item>` for a failed group H item of 12.7 (a Watchdog absent at run start is `preflight.H8`), `dead_man`, `watchdog_dead` (the Watchdog lost mid-run), `heartbeat_unwritable`, `disk_full`, `rig_lost`, `hook_lost`, `orchestrator_restart_budget`, `canary_generation_failed` (only when no canary could run at all); run `aborted_safety` reason `drill_order_placed`; run `aborted_budget` reasons `app_restart_budget` (10.2), `dollar_cap` (the run's model spend reached the per-run ceiling of 11.4 Cost model, 10.7) and `superseded` (an RC run stopped by a newer RC build, 10.9, 11.2); findings: `app_crash`, `new_log_signature`. The run-abort codes `watchdog_dead`, `heartbeat_unwritable`, `disk_full` and `rig_lost` appear on `harness_error` rows only as the run's abort reason on unreached checkpoints, which is how 4.13 lists them; `hook_lost` is also the direct reason of the checkpoint in progress when the hook host dies. The canary result states `detected`, `missed`, `detector_blind`, `detector_degraded` and `generation_failed` are not outcomes (10.3); `detector_blind` and `detector_degraded` are also the `harness_error` reason on the missed mutant's synthetic row, and the Nightly run's own outcome stays `complete`.

### 10.2 Watchdog

Placement. Three harness processes run on the rig (5.1 Component diagram and process layout): the Orchestrator, the Gateway hook host and the Watchdog; the thinkorswim process tree is the fourth. The Watchdog is a separate Python process started at rig logon by a scheduled task under the harness user, before the Orchestrator, in the same interactive session (a service cannot see the interactive desktop). Neither process is the other's child, so either can die alone. The Watchdog emits no input events and never writes SQLite.

Heartbeats, both directions. The Orchestrator writes `C:\sentinel\run\<shard_id>\heartbeat.json` (8.4 Artifact layout on disk) atomically (temp file, then rename) at every step start and end, every gate, and at least every 10 s during long waits:

```json
{
  "run_id": "pr-48213-3", "shard": 2, "attempt": 1, "state": "running",
  "flow_id": "flow.trade.order-ticket.stock.limit", "step_id": "s07",
  "checkpoint_id": "flow/dialog.order-confirmation/flow.trade.order-ticket.stock.limit/s07",
  "ts": "2026-11-09T14:03:21.412-05:00", "mono_ts": 184233.118,
  "app_pid": 6120, "orchestrator_pid": 4412, "hook_host_pid": 4420,
  "expect_screen_change_since": "2026-11-09T14:03:21.100-05:00",
  "max_wait_s": 20,
  "capture_suspended": false,
  "last_capture_sha256": "9f2c..."
}
```

`expect_screen_change_since` is set when the Executor emits an input that should change the screen and cleared when the settle rule accepts a capture; `max_wait_s` is the checkpoint's declared max wait, so the hang threshold follows the checkpoint. While `capture_suspended` is true (secret steps) the Watchdog takes no screenshot and computes no hash. `mono_ts` is the monotonic clock, so a wall-clock correction cannot fake or hide staleness.

The Watchdog writes its own `C:\sentinel\run\<shard_id>\watchdog.json` (pid, mono_ts, last trigger) every 2 s. The Orchestrator reads it at every gate and flow boundary. Age over 30 s or a dead PID means the run has no dead-man coverage and no kill-switch second half (6.6 Kill switch, recovery and post-run proof), so the Orchestrator finishes the step in progress, runs teardown, and ends the run `aborted_harness (reason: watchdog_dead)`; the remaining checkpoints are `harness_error (reason: watchdog_dead)`. It does not restart the Watchdog itself: a process that has to be restarted mid-run is a harness bug for the system owner. The central dead-man (below) is the second layer for the case where both processes die.

Heartbeat on a full or read-only disk. A failed heartbeat write is a harness failure, never a retry loop: the Orchestrator retries once after 1 s, then signals the Watchdog over the named event with code `self_abort` (so the Watchdog does not treat the stale heartbeat as a hang and restart it), runs teardown with capture disabled, and ends the run `aborted_harness (reason: heartbeat_unwritable)`. A heartbeat write that fails with `ENOSPC` is the full-disk case below (`disk_full`), not `heartbeat_unwritable`. The Watchdog checks free space in its sampling loop and the Orchestrator reads the result at every flow boundary, against the rig floor of 8.6 Retention and backup (R7 in 12.7: the larger of 20 GB and twice the projected shard size; the larger of 100 GB and twice the projected run size is the control host's floor, not the rig's); below the floor mid-run is a run-health warning, and below 2 GB the Watchdog's mid-run disk check makes the Orchestrator stop capturing, tear down and end the run `aborted_harness (reason: disk_full)`, with `harness_error (reason: disk_full)` on every checkpoint left without an outcome. A single artifact write that fails (`ENOSPC` or any other error, after the one retry of 8.4 Artifact layout on disk) is the store case of 8.9 Store failure modes: that checkpoint is `harness_error (reason: artifact_persist_failed)` and the run cannot be `complete`; it ends `aborted_harness (reason: artifact_persist_failed)` at teardown unless the free-space check ends it first. On `ENOSPC` the Orchestrator asks the Watchdog for an immediate free-space check, so a disk that is actually full ends the run `aborted_harness (reason: disk_full)` with the remaining checkpoints `harness_error (reason: disk_full)`. If the Watchdog's own journal write fails it writes an Application Event Log entry (source Sentinel, event 9001) and raises the named event; the control host's dead-man covers the rest.

Sampling, every 2 s:

1. Heartbeat age over 120 s in `running`, or over 5 minutes in `provisioned` and `launched` (installs and launches are slow): the Orchestrator is hung.
2. Orchestrator PID alive; hook host PID alive. A dead hook host is reported to the Orchestrator, which fails closed per 5.4 Executor and the Input Gateway: the step in progress is `blocked_by_gateway (hook_host_dead)`, its checkpoint `harness_error (reason: hook_lost)`, later checkpoints of the flow `not_run (reason: step_failed:<step>)`, the thinkorswim tree is killed and the hook host is restarted once per shard out of its own budget, which consumes no app relaunch; a second hook host death in the shard, or a `magic` or `layout_version` mismatch of the shared memory, ends the run `aborted_harness (reason: hook_lost)` (5.4.2 Process layout and shared state).
3. App process tree. PID from the main window: `FindWindow` on the main-window title regex (a config value; community sources report `Main@thinkorswim [build NNNN]`, confirmed in Phase 0 per 7.3 Pinned build install and version read), class `SunAwtFrame`, then `GetWindowThreadProcessId`; the tree is every process descended from that PID or running from the pinned install folder, enumerated with psutil. Unknown to verify in Phase 0 (DR-04 rig build): whether the install4j launcher hosts the JVM in-process or spawns a `javaw` child. Branch in-process: the window PID is the launcher PID and the tree is one process. Branch child: the window PID is the child and the launcher is found by the install-folder rule. Both branches are covered by the same two rules, so no code path depends on the answer. If no frame matches the title regex for 30 s while the heartbeat says `running`, the Watchdog journals `main_frame_missing` and tracks the tree by the install-folder rule alone. If the regex matches nothing for 5 minutes after launch while a process from the install folder is alive, the Watchdog reports `launched` gate failure to the Orchestrator, which falls back to the Help > About read of 7.3 to confirm the build and treats a missing main frame as `env_error (gate: launched)` only at the shard's first launch and only when no hang or crash signal (staleness, crash file, Event Log 1000 or 1002, empty tree) fired. A crash or hang signal during the gate sequence of the shard's first launch is an app failure too, before `launched` passes as well as after: `assertion_failed (assertion: app_alive)` with its cause in `detail` on the shard's first checkpoint, the `app_crash` finding, and one relaunch consumed, never `env_error`; when the relaunch budget is spent the run is `aborted_budget (reason: app_restart_budget)` and the unreached checkpoints are `not_run (reason: budget)` (5.2). During a relaunch after an app failure the same stall is a `hang` app failure charged to the first unreached checkpoint and to the relaunch budget (10.1), never `env_error`; an empty tree is the `process_exit` app failure.
4. Working set of the tree against a ceiling (1.5 x `-Xmx` plus 1 GB) and GDI object count against 9,000 (the Windows per-process default quota is 10,000; exhaustion paints nothing and looks like a hang).
5. Screenshot staleness, the primary hang detector. Hash the main window region. If `expect_screen_change_since` is set, the hash has not changed since then, no anti-anchor template (spinner, Loading, Reconnecting) is on screen and `max(2 x max_wait_s, 60 s)` has elapsed, the app is hung. `IsHungAppWindow` and `SendMessageTimeout(WM_NULL)` are not the detector: AWT pumps native messages on its own toolkit thread, so a blocked Swing Event Dispatch Thread still answers Windows. They stay as a cheap secondary check for JVM-wide stalls (GC storm, native deadlock). Under JAB branch A (DR-01), a JAB query that does not return within 5 s is a third signal.
6. Crash files. A new `hs_err_pid*.log` at the `-XX:ErrorFile` path or in the JVM working directory, a new heap dump at `-XX:HeapDumpPath`, a new `.dmp` in the WER LocalDumps folder, or Application Event Log IDs 1000 or 1002 for a tree process is a crash even if a process is still alive. An `OutOfMemoryError` line in the client log slice or a new heap dump is cause `oom` (in `detail`) even when the process survives, because the app's state is no longer trustworthy.

Reaction, one sequence for hang, crash and Orchestrator death:

1. Full virtual-screen screenshot into a restricted-ACL folder; it passes the Capture redaction stage (5.7 Capture) before it is stored or shown and never goes to the Reviewer.
2. Best effort `jcmd <pid> Thread.print` and `GC.heap_info` from a JDK on the rig matching the bundled runtime's major version (from its `release` file). A 15 s timeout (a GC-loop stall blocks dumps) is logged, not fatal. If the attach mechanism is disabled by vmoptions or refused, the artifact list records "thread dump unavailable: attach disabled" and the remaining artifacts stand alone.
3. Collect: the client log slice since the last successful checkpoint (directory located in Phase 0 and pinned in config; community reports disagree on the path; if no log directory is found the artifact list says "client log: not located" and the finding is still filed), hs_err_pid files, heap and WER dumps, Event Log entries, process metrics, both heartbeat files and the last 20 Input Gateway events.
4. Run `reset_input_state` through a fresh gateway instance (stuck modifiers survive the injecting process), then kill the process tree, children first, and confirm nothing from the install folder survives. When the Orchestrator is dead, kill the hook host last so the deny state covers the whole sequence.
5. Append a JSON line to `watchdog_events.jsonl`. The Orchestrator ingests the journal into `step_events` on resume, preserving the single-writer rule (8.2 Single-writer rule).
6. Signal the Orchestrator over a named event; it records the outcome for the step in progress (the class outcome from 10.1), and relaunches the app. If the Orchestrator is dead, start `orchestrator --resume <run_id>`. Before a `process_exit` is classified as an app failure, the Watchdog checks the launcher log for an update in the failure window and compares the build manifest and the relaunch's build-id read (7.3) with the values read before the failure; if either changed, the event is `env_error (gate: launched, reason: version_changed_mid_run)` for the checkpoint in progress and the rest of the shard, no `app_crash` finding is filed and no relaunch is counted.

Restart and resume rules:

- Resume at the next flow boundary (the next surface for the census, the next (surface, host) ladder for a sweep); the next flow starts from its preconditions and a ladder never resumes mid-way, because 2.5 runs it in descending order from a large size on one laid-out cell. The remaining steps of an interrupted ladder are `not_run (reason: app_crash)`. Recorded checkpoints keep their outcomes; the one in progress gets the class outcome from 10.1 (`harness_error (reason: orchestrator_died)` for an Orchestrator death, the reason 8.3 seeds); the rest of an interrupted flow is `not_run (reason: app_crash)` for an app failure or `not_run (reason: step_failed:<step>)` for an Orchestrator death, since the flow's later steps were never attempted. The relaunch re-enters the state machine at `launched` and passes every gate again, `paper_mode_asserted` included, through the re-login flow of 7.7 Login and re-login flows with MFA branches.
- Session rule (DR-06). Branch "second session ends the first": killing the orphaned tree is enough; the relaunch logs in at once. Branch "sessions coexist": the orphan's server session may linger, so the relaunch waits `session_release_wait` (default 60 s, measured in DR-06) before the login, and a "logged in from another location" or "already logged in" dialog is POP-04 of the popup catalog (7.8 Popup catalog policy and starter entries, 12.8) with action abort, so it ends as `env_error (gate: authenticated, reason: session_kicked)` with the screenshot and no re-login on either DR-06 branch, never a retry loop (7.7 allows one login attempt per run).
- Budgets per shard per run: 3 app relaunches, 2 Orchestrator restarts, 1 Gateway hook host restart. The first three app failures in a shard are each relaunched; a fourth app failure (a failure during a relaunch's gate sequence counts, 10.1) marks the remaining checkpoints `not_run (reason: budget)` and ends the run `aborted_budget (reason: app_restart_budget)`. Spending the Orchestrator budget: run `aborted_harness (reason: orchestrator_restart_budget)`, remaining checkpoints `harness_error (reason: orchestrator_restart_budget)`. Spending the hook host budget, which is its own and separate from the other two: run `aborted_harness (reason: hook_lost)`, remaining checkpoints `harness_error (reason: hook_lost)`; a hook host restart never consumes an app relaunch, although the app tree is killed with it so the deny state covers the gap. The two `aborted_harness` cases page harness on-call at once and the `aborted_budget` case posts to the on-call channel (9.10 Alerting model). Environment re-logins (session expired, Disconnected dialog) count against the re-login budget K of 7.7 and end as 7.7 says; crash and hang relaunches count against the 3 here; the proactive relaunch below counts against neither.
- Proactive relaunch after 40 flows or 90 minutes of app uptime, whichever is first, to bound heap pressure; never inside a flow; a step event, not a failure, and it does not consume the restart budget. Every capture is tagged with app uptime and restart count.
- Crash during teardown. If the app dies in `teardown` after every checkpoint has an outcome, one relaunch (if budget remains) re-attempts teardown through the recovery login of 6.6; if teardown still cannot read Working and Filled, the post-run proof is UNPROVEN, the run is `complete_with_env_errors` and the next run on that login is blocked until a human verifies the account, exactly as 6.6 states. If the Orchestrator dies in `teardown`, the Watchdog restarts it with `--resume`, which re-enters at `teardown` with every checkpoint outcome intact. A crash after `teardown` and before the Central Store acknowledges the run (`reported`) is not a lost run: the rows and artifacts are on the rig, shipping retries with backoff, and the run row the control host wrote as `aborted_harness (reason: dead_man)` at the deadline is replaced by the real outcome when the rows arrive, with the alert closed as "late arrival" and the delay recorded in run health.

JVM flags. The pinned thinkorswim.vmoptions template carries `-XX:ErrorFile`, `-XX:+HeapDumpOnOutOfMemoryError` and `-XX:HeapDumpPath` pointed at the artifact folder (7.3), plus `-XX:+CreateCoredumpOnCrash` where 5.14 lists it; validity against the bundled JDK major is checked in Phase 0 (check 3 in 7.14 Phase 0 checks owned by this section, which also reads whether the updater or the login-screen Setup dialog rewrites vmoptions). Branch "launcher ignores or rewrites vmoptions": the vmoptions hash is part of the environment fingerprint (7.4 Environment fingerprint), so a rewrite by the login-screen Setup dialog or an update surfaces as a fingerprint change (`not_comparable (reason: fingerprint_mismatch)` against the pair rig, or `needs_human (reason: uncalibrated)` when both rigs changed alike and no Calibration exists for the new rendering key (7.13)), never as a silent loss of crash files, and the Watchdog scans the JVM working directory for the default `hs_err_pid<pid>.log` as well. The rig image enables WER LocalDumps for every executable in the install folder.

Dead-man, two layers. Local: the Watchdog knows the run deadline (11.2 Cadence and time budgets per run type); if the Orchestrator has not reached `reported` by deadline plus grace (15 minutes for a PR run, 30 for a merge run, 60 for an RC run, 06:00 America/New_York for the Nightly run, and for a Calibration run 06:00 America/New_York after each night's pass, that is the first 06:00 after the pass is scheduled to end, 11.2), the Watchdog kills the Orchestrator and the tree, runs `orchestrator --resume <run_id> --finalize`, which writes `aborted_harness (reason: dead_man)` for a run that reached `running`, with `harness_error (reason: dead_man)` on every checkpoint without an outcome; for a run still before `running` at that deadline the finalize treats it as a failure of the gate in force (5.2): `env_error (gate: <state>, reason: timeout)` on every scoped checkpoint and the run `complete_with_env_errors` (a Nightly or Calibration run has already ended `aborted_harness (reason: start_failed)` at its earlier start deadline, 11.2). Either way the finalize ships the rows. Central: the Reporter and Integrations host covers only a run that reached `running` (its scope manifest uploaded and `run_started` received) and then stopped reporting. For such a run it expects a rig heartbeat summary every 60 s and a `run_completed` event by the same deadlines as the local layer; a missing `run_completed` posts a dead-man alert to on-call naming the run, the rig and the last heartbeat received, and the host writes the run row as `aborted_harness (reason: dead_man)`, so the morning report shows a missing run, not an empty page. A run that never reached `running` is never `dead_man`. A run that sent `run_started` and whose rig then falls silent before `running` is the lost-rig case of 10.7. While it emits `run_queued` with its queue position every 60 s it waits; at its start deadline (11.2 Cadence and time budgets per run type: PR run 45 minutes and merge run 3 hours from the trigger; RC run the RC start deadline, the G-N sign-off time minus 8 hours; Nightly run 02:00; weekend Calibration run Saturday 02:00) it takes the start-deadline outcome of 11.2 Queue and saturation: a PR run is `aborted_budget (reason: pool_saturated)`, a merge run is coalesced into the next merge run, an RC run is decided by the release manager (9.12), and a Nightly or Calibration run is `aborted_harness (reason: start_failed)` with every scoped checkpoint `harness_error (reason: start_failed)`, a P1 to the harness on-call (9.10) and the "canaries pending" banner on the next PR comment. A trigger followed by neither `run_started` nor `run_queued` within 15 minutes raises the dead-man alert as "run not started" (9.10), and the run takes the same start-deadline outcome. Both layers use the same reason, so 9.10 and 12.7 see one vocabulary. Once a month the Rig Manager stalls a test Nightly run on rig 6 on purpose after `run_started` (Orchestrator suspended, heartbeats and `run_completed` withheld, a shortened deadline); the central layer must raise the dead-man alert and write the `aborted_harness (reason: dead_man)` row within 15 minutes of that deadline, and a stall that produces neither is `harness_error (reason: chaos_unobserved)` on the self-test row and a P1 (guarantee G5 of 1.4, chaos suite of 7.11).

### 10.3 Canary Service and the mutant catalog

Purpose: prove every night that the deployed path (masks, thresholds, Region Registry, redaction, downscaling, Reviewer prompt and pinned model together) still flags the defect classes the system exists for. The eval set (10.4) tests the Reviewer offline; the canary tests the path as deployed.

Catalog. One file, `canaries/mutants.yaml` in `sentinel-config`, with the entry schema of 4.11 Mutant catalog entry. The catalog contains M01 to M33 exactly as 12.5 Starter mutant catalog tables them (12.5 is authoritative for those rows, the seed 20260101, the `money_cell` flag and the snake_case classes of the table below) and may grow from M34 on, each new id the next in sequence (L-MUT-01); M25 is the identical control. The acceptance mutant of 10.10 is M12, bound to the Flexible Grid cell of the worked example. A critical checkpoint is a checkpoint of a surface whose registry entry sets `critical: true` (4.5, tier 1 only; the order tickets for stock, option and futures, the Order Confirmation dialog, Position Statement, Account Info, option chain, the Active Trader ladder at two sweep sizes, Monitor Activity and Positions, Working Orders). Every critical checkpoint has at least two behavioral catalog entries bound (lint L-MUT-03, an error). How many mutants each critical checkpoint gets (20 to 30) and whether they cover the six brief classes of L-MUT-05 are counted over the mutants generated at each Nightly run, not by lint: a shortfall is listed as a coverage gap in the morning report. The acceptance mutant, in the schema's shape:

```yaml
- mutant_id: M12
  checkpoint_id: sweep/charts.flexible-grid.active-trader-cell/flexgrid/480x360
  class: overlapped_panels
  mode: image
  money_cell: false                   # the ladder is a tier-1 region, not a money cell (3.8): a non-money mutant
  generator: {op: translate, params: {dy: -14, layer: rgn.ladder.viewport, fill: background_sample}, seed: 20260101}
```

Determinism. Image mutants are generated at the start of every Nightly run from the current approved captures of the main build with the catalog seed: same image, same seed, same bytes, checked by sha256 against the previous night. When the approved capture changes, the mutant regenerates and the result row records the new `baseline_sha256`. A missing landmark, a missing approved capture, a generator exception or a catalog that fails the G3 preflight hash makes that mutant `harness_error (reason: canary_generation_failed)` with the mutant id. One mutant's generation failure is that mutant's row state, `generation_failed`, and nothing more. The run's canary state is `generation_failed` only when a critical checkpoint has zero generated mutants or the stage generated none; otherwise it is the worst of the other states (Result states below). When it is `generation_failed`, `detector_state` in `system_state` is set, on-call is paged P1 and the morning report carries the same banner as `detector_blind` with the line "canaries did not run", while the Nightly run's own outcome stays `complete` because its other work finished. Only when no canary could run at all (the stage produced no mutants and no behavioral canary flow started) is the Nightly run `aborted_harness (reason: canary_generation_failed)`. A detector that was not tested is not trusted; nothing is skipped silently.

Injection. Each image mutant is the candidate capture of its checkpoint against the approved capture as base, through the Diff Engine, Invariant Checker, Oracle, classification and the Reviewer queue, as in a merge run; behavioral mutants run their `canary` flow on the Nightly rig. The global-shift mutants M21 and M23 are judged as a batch: each is applied to every bound checkpoint of the night's synthetic batch, and the whole-window pre-pass of 3.7 runs over that batch alone, which must give one `needs_human (reason: global_shift)` cluster under a `global_rendering_shift` finding; the Nightly run's own A/A pre-pass (10.6) never sees these images. The record carries `synthetic: true`, which the Stores enforce: synthetic records never promote a baseline, never create or match a decision, never post to Jira or Slack, never appear in finding lists, and count in no metric but canary pass rate (9.1 Rules for every report).

Path equivalence (5.15 Canary Service and Calibration Service). Mutants enter through the same `evaluate_checkpoint` entry point and the same harness commit as the day's merge run captures. Every night one real merge-run pair is re-evaluated through the canary entry point and must reproduce its outcome, metrics and components exactly; a difference is `harness_error (reason: canary_path_divergence)` on the self-test row, with the detector-blind banner until it clears.

Safety canaries. The attestation canary (6.3), the identity canary (6.4), the proof canary (6.6), the denied-action test (6.8), the secret-scan canary (6.9) and the redaction canary (6.10) run beside the mutants as flow-class `canary` items of the Nightly run (6.5 Nightly fire drill and safety canaries). A miss is `harness_error (reason: safety_canary_blind:<canary>)` with the blind detector named (`attestation`, `identity`, `proof`, `deny_list`, `secret_scan`, `redaction`), the same P1 and banner as `detector_blind`, and the flows that depend on that detector `not_run (reason: quarantine)` until it passes. The fire drill runs after them: an item the gateway did not block with no new order row is `harness_error (reason: drill_failed:<item>)` with the flows that use that path `not_run (reason: quarantine)` and a P1 page; a new Working or Filled row is run `aborted_safety (reason: drill_order_placed)` with the login blocked. In both cases the Nightly run's outcome follows the ordinary rules (`complete` for the first, `aborted_safety` for the second).

Registry validation self-test. The Nightly run also runs the probes P1 to P8 of 2.2.3 against a registry copy with one surface removed; exactly one `unregistered_surface` must result, else `harness_error (reason: validation_self_test)` and the morning report says the registry probes are blind (guarantee G1 of 1.4).

Scoring. A mutant is detected when its final outcome is in its `expected` list; otherwise the result row names the mask, decision, threshold or landmark that absorbed it (`identical`, `noise`, `intended` or, for the controls, any finding). The result rows are `canary_results` in 8.3. A mutant's synthetic outcome is a row of `synthetic_outcomes` (8.3), keyed by run, mutant and checkpoint and referenced by its `canary_results` row; `outcomes` holds real rows only: the A/A pass, the canary flows and the run's scoped checkpoints, including the `harness_error` rows a synthetic cause writes on them (`canary_generation_failed`, `canary_path_divergence`). M27 is scored on the rejection message it makes the app show, not on the Price cell it leaves blank, so it is not a money-cell mutant.

- Money-cell mutants (`money_cell: true`: mutants on money cells, the regions with a `money_role` of 4.8, one closed list: `qty`, `price`, `bp_effect` (Buying Power Effect), `max_loss`, `send`, `cancel` and `delete`, on the Order Confirmation dialog and the order ticket, the ticket's Confirm and Send button being `send` (3.8); the ladder price column, P/L, balance and BUY and SELL label cells are tier-1 regions, not money cells, so their mutants, M12 among them, are non-money and count toward `detector_degraded` under the next bullet; the account number and account holder name are identity fields, always redacted and never diffed, so no money-cell mutant targets them and the redaction canary M19 proves them instead): 100 percent. One miss sets the mutant's result state and the canary state to `detector_blind`: `detector_state` in `system_state` is written, run health is red, the banner is posted, on-call is paged P1 and RC sign-off is blocked. The mutant's `synthetic_outcomes` row is `harness_error (reason: detector_blind)` (1.10, 4.13), and its `canary_results` row keeps the outcome the path produced (`identical`, `noise` or `intended`, the evidence of the miss) in `produced_outcome` and names what absorbed it; the Nightly run's own outcome stays `complete`. This is what the brief's "the run is `harness_error`" means: a red detector state, not a run outcome, since the run set is closed. Detection here does not depend on the Reviewer: an unmasked diff above threshold cannot be `noise` under 3.11 Classification decision table, so a miss means a mask, a decision, a threshold or a landmark swallowed the cell.
- All other mutants: detection rate per class at or above the rolling floor, the lower of the 14-night median for that class minus 5 points and 90 percent, and never below the 95 percent rolling target of 9.11 Metrics dashboard and kill criteria once Phase 2 exits. A borderline Reviewer verdict is re-sampled per the borderline rule of 3.15 before it counts as a miss. A missed non-money mutant has result state `missed` and counts toward its class rate; a miss that takes the class below the floor has result state `detector_degraded` (8.3) and sets the canary state `detector_degraded`, the `synthetic_outcomes` row of each missed mutant of that class is `harness_error (reason: detector_degraded)` while the class stays below the floor (4.13), and the banner names the class.

Result states per mutant are `detected`, `missed`, `detector_blind`, `detector_degraded` and `generation_failed` (`state` in `canary_results` in 8.3 Schema). The run's canary state is `generation_failed` when a critical checkpoint has zero generated mutants or the stage generated none (Determinism above); otherwise it is `detector_blind` when any row is `detector_blind`, else `detector_degraded` when any row is `detector_degraded`, else `ok` (`missed` rows and a single mutant's `generation_failed` row leave it `ok`). It is written into the Nightly run's `summary_json` and into `detector_state` in `system_state`, which 9.10 and the report banner read, and a green Nightly run clears it.

Morning message. On `detector_blind` or `generation_failed` the Reporter posts to on-call and stamps a banner on every report and PR comment until a Nightly run passes; on `detector_degraded` it posts and lists the classes:

PR and merge runs continue under the banner; the RC gate cannot be signed while it is up. The Reporter also files a SENT Bug: Highest for `detector_blind` and `generation_failed`, High for `detector_degraded` (9.9 Jira and Slack rules).

Gate and governance. The full catalog also runs in CI on any change to masks, thresholds, the Region Registry, the Reviewer prompt or few-shot set, the pinned model id, the redaction stage or the downscale path, and on every Calibration run; the change merges only with a passing result attached. Catalog changes are PRs reviewed by the tier's flow owner and the system owner: adding a class requires the generator, a unit test (the mutant differs from base only inside the target region) and the expected-outcome mapping; removing or weakening a mutant requires a reason and a ticket. Each result row stores the catalog version, and the morning report lists critical checkpoints with fewer than 20 live mutants as a coverage gap.

### 10.4 Eval set and Reviewer change control

Eval set (construction and shares in 3.14 Eval set, metrics and gates). 300 to 500 labeled items stored content-addressed, labels as JSON lines in `sentinel-config` with labeler ids: mutants from the same generators on a different seed stream than the nightly catalog; A/A pairs from Calibration runs labeled `no_visible_difference`; real PR and merge diffs labeled by two humans independently with a third adjudicating. Tier-1 checkpoints are at least 40 percent of the set; the held-out 30 percent is never used to choose a prompt or a threshold.

Metrics, per model id and prompt version, stored in `reviewer_evals` (8.3): precision and recall per verdict; tier-1 recall of `does_not_match_manifest` on mutants on its own; hallucination and rubber-stamp rates; a reliability diagram and expected calibration error for the confidence field; the `needs_human` routing threshold read off the curves, not set by hand.

Change control. A change to any element of the reviewer version tuple of 3.15 Model and prompt change control; degraded modes (model id, prompt hash, schema version, few-shot ids, effort, crop policy version, redaction version), or to any Region Registry semantic the Reviewer depends on, runs the eval set on the held-out split and the full mutant catalog in CI. Merge is blocked if any gate in 3.14 falls, if tier-1 recall drops more than 1 point even while the gate holds, or if any critical mutant is missed; the result is attached to the PR. The model id from the API response, prompt hash, few-shot version, mask version and redaction version are stamped on every verdict so a shift in the verdict mix can be attributed.

Gate failure mid-release. The nightly 30-item eval subset of 3.14 runs on the deployed tuple every night. If it fails a gate, or a weekly full evaluation does, the Reviewer is disabled by config (`reviewer_enabled: false`) from the next run: no model calls are made, every above-threshold diff on a declared surface is `needs_human (reason: reviewer_unavailable)` with `review_state: pending`, `collateral` and all invariant and assertion outcomes are unaffected because they need no model, and every report and PR comment carries the line "Reviewer disabled since <date>: eval gate <name> failed; N items await a human". An RC in flight is not blocked by the disabled Reviewer, because sign-off already requires human triage of every `needs_human` and `collateral` item (3.16 What the reviewer may never do, item 10); it is blocked by the untriaged items themselves until triage clears them. The Reviewer returns only when a tuple passes the full gate set in CI and the system owner merges the pin.

Runtime controls. Borderline confidence (within 0.10 of the routing threshold) is re-sent twice and the majority verdict with the median confidence is kept (3.15). Each week a human re-labels a random 5 percent of `noise` outcomes that came from an approved signature and the 5 percent of `intended` verdicts 3.15 samples; the overturn rates are report metrics.

### 10.5 Flake tracking, targeted re-runs and quarantine

Targeted re-run (mechanics in 3.10 Targeted re-run and flake logic). When a checkpoint's diff exceeds its region threshold, or an invariant fired, and no assertion failed, the Executor runs the declared normalize routine (Esc, park the mouse, drop focus on the neutral control, reset scroll, reselect the sub-tab), waits for the settle rule and re-captures, up to twice in the same session for a diff, and once for an `invariant_violation`, which is re-captured only to confirm that it persists (an `assertion_failed` is final without a re-run). All captures must agree within the A/A floor, and a re-captured invariant must fire again; a violation that does not reproduce is instability like a disagreeing diff. All agree: a product change, and classification proceeds (3.11). Any disagree: instability, outcome `not_settled (reason: unstable)`, both images attached, routed to the flow owner, never to the Reviewer or the Unexpected list. A re-capture never crosses a flow step and the first capture is always kept. Checkpoints declared `recapturable: false` (4.7 Flow file: the state cannot be re-entered in the session) skip the re-run and classify from the single capture, with the finding marked "not re-captured: recapturable false". The run carries a re-run budget; when it is spent before stability is decided the outcome row records `stability: unknown (cause: budget)`, run health prints `rerun_budget_exhausted` for the sharding review, and the finding is listed with "not re-captured: budget" (3.10).

Flake statistics. `flake_stats` in SQLite (8.3), per checkpoint over a rolling 30 days: captures, re-captures, unstable outcomes, verdict flips between two runs of the same build (the merge run versus the Nightly A/A pass), step retries, agent fallbacks. An observation is one compared capture of the checkpoint on one build. The flake score is unstable outcomes plus verdict flips over observations; the dashboard flake rate of 9.11 is the same ratio over all checkpoints compared.

Quarantine. A checkpoint enters quarantine on any of: flake score above 0.10 over the last 5 or more observations of the same build; `not_settled (reason: aa_drift)` on 3 consecutive Nightly runs (10.6); the gateway drop thresholds of 6.2 and 5.4.8 (any safety-reason drop quarantines the flow; 3 integrity-reason drops in one flow quarantine it); 3 unstable outcomes in 7 days; 2 verdict flips on one build; a non-zero A/A floor on a frozen checkpoint not fixed within 5 business days (7.13 What invalidates calibration); or a flow whose 30-day agent-fallback rate exceeds 5 percent, which quarantines the whole flow (11.5). Drill and safety-canary flows (6.5) are exempt: a trigger on one pages per the safety routing of 9.10 instead of quarantining it (3.10). Quarantine is a record in `quarantine.yaml` in `sentinel-config` (4.1) with exactly one of `checkpoint` or `flow`, plus `owner`, `ticket`, `entered` and `reason`, one of the codes in the table below; lint rule L-XREF-11 checks that the checkpoint or flow exists. The record is opened by the Orchestrator as a PR, or by the Quarantine action of 9.6 One-click actions and who may perform them, and merged by the system owner.

**Quarantine reasons.** The closed list of `reason` codes in `quarantine.yaml`; `taxonomy.yaml` carries it as `quarantine_reasons`.

| Reason | Entered when | Introduced by |
|---|---|---|
| `flake` | flake score above 0.10 over the last 5 or more observations of the same build, 3 unstable outcomes in 7 days, or 2 verdict flips on one build | 3.10, 10.5 |
| `aa_drift` | `not_settled (reason: aa_drift)` on 3 consecutive Nightly runs | 10.6 |
| `aa_floor` | a non-zero A/A floor on a frozen checkpoint not fixed within 5 business days | 3.9, 7.13 |
| `maintenance_budget` | the budget-overrun cut of the maintenance model, lowest tier first | 11.5 |

While quarantined, the checkpoint is `not_run (reason: quarantine)` on every run, shown in the coverage matrix in its own color, never as covered. Exit requires a fix plus 5 consecutive clean captures in a Calibration run with a zero floor, cited in the PR that removes the record; nothing un-quarantines automatically. Above 2 percent of tier-1 checkpoints quarantined, run health is red and the RC gate blocks.

Step retries and agent fallbacks are recorded as `passed_after_retry` and `passed_via_agent_fallback` with the locator failure as a finding beside the checkpoint; two fallbacks on the same step and build open an "update scripted flow" ticket, and flows in fallback is a run health metric.

### 10.6 A/A drift on the Nightly run

Every Nightly run captures, on the current main build, all tier-1 checkpoints plus a rotating 20 percent of the rest, twice in one session on one rig (the pass is sharded over rigs 4 and 5 with each checkpoint's two passes in the same session, 11.2 Cadence and time budgets per run type). Each selected checkpoint gives one pair, pass 1 against pass 2, diffed per region against the Calibration floors (3.9 A/A calibration and threshold derivation; this is the shape 3.9 step 7 refers to). Zero-floor regions on masked_live checkpoints are excluded from drift: their live data moves between the two passes, and their rule checks still run. The environment fingerprint is checked first. When the rendering key of 7.13 differs from the Calibration's only in the JRE release or `render_probe_hash`, the pass runs against the previous floors, and if it passes those floors carry over to the new key (7.13). For any other change of the rendering key no floor exists: every A/A diff is evaluated at threshold 0 and reported `needs_human (reason: uncalibrated)`, the morning report names the changed field and a Calibration run is queued (7.13 What invalidates calibration). `not_comparable (reason: fingerprint_mismatch)` is reserved for a candidate and base that differ from each other, which two passes on one rig cannot.

- A frozen checkpoint with any diff above its floor: `not_settled (reason: aa_drift)` for the night, flake statistics updated, flow owner notified; three nights running triggers quarantine.
- More than 2 percent of checkpoints above floor, or the global-shift pre-pass of 3.7 Three-granularity diff (fraction of checkpoints above epsilon, and whether diff pixels sit on text edges by an edge-density measure) indicating a rendering change: `harness_error (reason: aa_drift_global)`, and the morning report says thresholds are invalid until a Calibration run passes. On a product run the same pre-pass yields one `needs_human (reason: global_shift)` cluster under the run-level `global_rendering_shift` finding with zero Reviewer calls (3.7).

### 10.7 Degraded modes

Model API.

- Review is asynchronous and idempotent. A run reaches captured-and-diffed with zero model calls; every checkpoint above threshold that needs a verdict is recorded `needs_human (reason: reviewer_unavailable)` with `review_state: pending`, and the Reporter publishes the report in state `unreviewed` with the line "Reviewer pending: N items". `collateral`, invariant violations and assertion failures are already final.
- The Reviewer job drains the queue of 3.15, keyed by (run id, checkpoint id, diff hash, mask version, prompt hash); verdicts are cached under the key of 3.13 (base hash, candidate hash, mask version, prompt hash, model id), so an item already answered is served from the cache and not re-sent. When a pending verdict lands, the item is re-evaluated through the 3.11 table with the verdict as input R and the outcome becomes what the table gives (`intended`, `noise` only via the A/A floor, or `needs_human (reason: reviewer_no_match)`, which is also the outcome for a declared removed surface the Reviewer does not confirm (3.11 row 25a), or `needs_human (reason: reviewer_uncertain)`), `review_state` goes from `pending` to `done`, and the Reporter re-renders. If a human decision already exists on that item, the verdict is attached as an annotation only and never changes the outcome or the decision.
- Late results. A verdict that lands after the report was published creates a new report version, edits the PR comment in place (9.1), re-runs decision matching for the item because the category is part of the signature (9.7 Decision persistence and inheritance), re-ranks the Unexpected list, and fires the new-high-confidence-collateral alert of 9.10 at that moment if the item now qualifies. An item a human decided before its verdict landed is the exception: the outcome stays as the decision left it, `review_state` becomes `done`, the verdict is stored as an annotation, the item is not re-ranked, re-matched or re-alerted, and a verdict that disagrees with the decision is listed in the weekly summary and joins the eval development split (3.15). If a newer run of the same PR has published since, the late verdict is recorded against its own run and the comment's history table shows it; the live comment keeps showing the latest run.
- Which path a review takes is 3.15's rule, by run type and nothing else (no queue-length trigger): synchronous calls serve every PR run item inside the 45 minute budget under a concurrency semaphore of 4 with the SDK's default retries on 429 and 5xx; merge, RC and Nightly runs, and the late re-review of an item still pending after its report, use the Message Batches API: one batch per run, `custom_id` derived from the queue key `checkpoint_id:region:cluster` as 3.15 writes it, results read by `custom_id` in any order, `expired` entries resubmitted once, `errored` entries retried once and then left `needs_human (reason: reviewer_unavailable)`; tier-1 items not back from a batch by the report deadline minus 10 minutes are sent synchronously the same way (3.15). Most batches finish within an hour and the hard maximum is 24 hours, so a batched run is posted `unreviewed` at its deadline and completed later. While the DR-07 ruling requires zero data retention the batch path is off (3.15), and whether the security-approved endpoint offers the Batch API is confirmed in Phase 0 under DR-07; an endpoint without it uses the synchronous path with the semaphore and the queue drains over time. Reviewer caps per run (PR 60, merge 200, RC 500) leave items beyond the cap `needs_human (reason: reviewer_cap)`. No run ever waits on the model.
- Spend ceilings (11.4 Cost model, `policy/budgets.yaml`). The Orchestrator sums the usage block of every model response of the run (Reviewer, agent rescue, Explorer) against three ceilings. An Explorer session that reaches 25 dollars ends that session only, with the run-health line of 2.9 Explorer; the run continues. The weekly ceiling stops model calls until the week ends, with the items it excludes `needs_human (reason: reviewer_cap)` and `cause: dollar_cap` in `detail` (3.15); it aborts no run. The per-run ceiling is the only one that ends a run: when the run's model spend reaches it, the Orchestrator makes no further model call, finishes the step in progress and ends the run `aborted_budget (reason: dollar_cap)` at the next flow boundary; checkpoints not yet captured are `not_run (reason: budget)`, items still waiting for a verdict are `needs_human (reason: reviewer_cap)` with `cause: dollar_cap` in `detail` and `review_state: done` (the later change 4.13 allows for a pending item), teardown and the post-run proof run as usual, and on-call is told (9.10). Recorded outcomes stand.
- Deprecation. Full model ids are pinned per component in config and stamped on every verdict and agent step. Agent mode uses the harness's own tool definitions (`click_named`, `type_fixture`, `press`, `zoom`, `scroll` and the Explorer-only `drag_named`; 5.6 Agent-mode toolset) with image inputs, not the computer-use beta tool, so there is no computer-use tool type to pin; the second pinned item is the harness toolset schema version, also stamped on every agent step. A daily job calls `GET /v1/models/{id}` for each pinned id; a missing id is an alarm. The Models API does not publish retirement dates, so the system owner records each vendor deprecation notice in `model_deprecations.yaml` (the published policy is at least 60 days before a public model is retired; verify at Phase 0); alarms fire at announcement, T-45, T-30 and T-14 until the migration PR, which must pass 10.4, merges. Preflight N2 sends one agent request with the pinned toolset schema version and fails the item if the request shape is rejected.
- Preflight N2 or N5 failing (12.7) is a degraded mode, never `env_error`: the run continues, and the failure sets `review_mode: deferred` and `agent_available: false`, which disables both agent fallback and the Explorer. `review_mode: deferred` means every item that needs a verdict is `needs_human (reason: reviewer_unavailable)` with `review_state: pending` until the endpoint returns (3.15). With the agent unavailable the locator ladder of 5.5 Locator ladder ends at the OCR text anchor; a locator failure is step `failed`, the checkpoint the step led to is `landmark_missing`, the flow's downstream checkpoints are `not_run (reason: step_failed:<step>)`, and the failure is posted as a finding with the pre-attempt screenshot and the base build's screenshot at the same step, labeled "scripted locator failed; agent fallback disabled". Nothing hangs and nothing falls back silently. An agent-only step (one with no scripted rung) is skipped and its checkpoints are `not_run (reason: model_unavailable)`. The flag is re-checked once per flow and a recovery is logged. If `agent_available` is still false when the Explorer is due (T+6:20 of an RC run, 10.9), the Explorer does not start: its session is `not_run (reason: model_unavailable)`, the RC report's Explorer section and run health print "Explorer: not run, model endpoint unavailable", the Explorer owner and harness on-call are told, and the run is otherwise unaffected; a recovery logged before T+6:20 lets it start as planned. DR-07 branch B (computer use not covered) sets the same flags permanently; there the Explorer is out of scope (11.8), not `not_run`.

Network.

- Preflight failures (N1 to N5) are `env_error (gate: preflight.<item>)` or a degraded mode, never a diff. A failure inside a listed `maintenance_windows` entry (7.10 Quiet windows from the exchange calendar) reschedules the run once with a notice instead, per 7.11 Network preflight and chaos suite.
- Mid-run, the anti-anchors Disconnected and Reconnecting stop capture. The Orchestrator pauses up to 5 minutes polling connectivity (the post-login probe of 7.11 Network preflight and chaos suite: indicator not Disconnected, pinned quote fresh). Network back within 5 minutes: re-assert paper mode (a reconnect may re-authenticate), run the light fixture check, then retry the current step once; the step is `passed_after_retry` and its checkpoint is captured normally, or `not_settled (reason: timeout)` if it will not settle. Between 5 and 15 minutes: the checkpoint in progress and the rest of its flow are `env_error (gate: connectivity)`, and the run resumes at the next flow boundary after the same re-verification. Past 15 minutes: the shard's remaining checkpoints are `env_error (gate: connectivity)` and the run ends `complete_with_env_errors`. A paused masked_live checkpoint pauses its lockstep partner too; a partner that cannot resume in the same minute makes the checkpoint `not_run (reason: budget)` per 11.3 Sharding and parallelism. Pause time counts against the wall budget.
- Loss of the central store: artifacts and SQLite are local, so the run continues and publication retries with backoff; if the rig cannot reach the host by the deadline, the dead-man alert fires with "rig unreachable, run data intact on rig" and the late-arrival rule of 10.2 applies when it reconnects.

Rig.

- Rig Manager heartbeat per rig every 30 s to the control host; 3 minutes of silence is a lost rig. The shard is re-queued once, in full (its Run Store is on the lost rig and rows ship only at `reported`), to a rig of the same fingerprint class if the wall budget allows; when no budget or rig allows it, the shard's checkpoints are `env_error (gate: rig_lost)` and the run ends `complete_with_env_errors`. A second loss of the same shard ends the run `aborted_harness (reason: rig_lost)` with `harness_error (reason: rig_lost)` on every unfinished checkpoint, because two lost rigs in one run is a fleet or harness fault, not weather. When a lost rig returns, its Run Store rows ship with their `attempt` number and are kept as a superseded attempt for diagnosis, never merged into the live attempt.
- Snapshot checksum mismatch, a non-interactive desktop or wrong display mode: `env_error (gate: preflight.<item>)` at `provisioned` with the item id (R1, R6, R2); a black probe screenshot from the capture self-test is `aborted_harness (reason: preflight.H3)` (12.7). A Windows update outside the snapshot process changes a rig's fingerprint: when its pair rig differs, every checkpoint of the pair is `not_comparable (reason: fingerprint_mismatch)` naming the field; when both rigs changed alike and no Calibration exists for the new rendering key (7.13), diffs are evaluated at threshold 0 as `needs_human (reason: uncalibrated)` and a Calibration run is queued (7.13); either way on-call is alerted.

### 10.11 Soak: long sessions, resource budgets and the freeze detector

Why. Leaks, handle exhaustion and six-hour freezes never appear in a 45-minute run, and a user keeps thinkorswim open all day. Soak is the RC-only activity that 2.11 schedules as `soak_items` and 11.2 places on rig 5 for 6 hours in parallel with the census shards.

Schedule and base. One rig, the candidate build, the tier B workspace with the most gadgets, data mode masked_live with the Region Registry (a six-hour frozen window is not available on either DR-02 branch). The base curve is the lineage soak of the last released build, recorded when that build was the RC and stored with its fingerprint in the Central Store; it is comparable only when the fingerprint matches, otherwise every soak comparison checkpoint is `needs_baseline` and the candidate curves are shown alone. There is no base soak rig: the fleet of 11.2 has none to spare and a 12-hour back-to-back pair does not fit the 8-hour budget.

Activity loop. A scripted loop of tier-1 and tier-2 flows with no order-stage steps beyond building and deleting a ticket (symbol changes on every gadget, chart period and study changes, tab switches, a scan, Monitor sub-tab cycling, a ticket built and deleted), one cycle every 15 minutes, 24 cycles. Each cycle ends with a soak checkpoint `flow/<workspace-surface-id>/soak/c<nn>`: settle, capture, invariants, and two diffs: against the lineage soak capture at the same cycle index, and against the run's own cycle-1 capture, which catches drift inside the session (a leaked window, a growing panel, a stuck tooltip, a stale quote badge). Both diffs classify through 3.11 with the same taxonomy as any checkpoint.

Resource sampler, every 60 s, for every process in the tree: working set and private bytes, GDI and USER object counts (`GetGuiResources`), handle and thread counts, CPU, and JVM heap after GC by `jcmd GC.heap_info` where attach is allowed (best effort, as in 10.2). The ticking clock region of the status bar is hashed every 2 s as the freeze detector: a hash unchanged for 10 s with no anti-anchor on screen is a freeze, handled as the app-failure trio of 10.1 with cause `hang` in `detail`, and the soak continues after relaunch under the same 3-relaunch budget; the relaunches are the finding. A crash in soak is the same trio: a product finding, never `env_error`.

Budgets, declared in `soak.yaml` in `sentinel-config` and calibrated from the lineage curve, each an assertion `soak.<metric>` evaluated at every cycle checkpoint:

| Metric | Default budget | Assertion |
|---|---|---|
| Working set growth | Under 25 percent above the hour-1 value, and under 1.5 GB absolute growth | `soak.working_set` |
| Monotonic growth | Linear fit over the trailing 3 hours of working set or private bytes with slope under 60 MB per hour | `soak.growth_slope` |
| GDI objects | Under 9,000 at every sample (quota 10,000) | `soak.gdi_objects` |
| Handles and threads | Within 20 percent of the hour-1 value | `soak.handles`, `soak.threads` |
| Heap after GC | Under 80 percent of `-Xmx` at every sample where readable | `soak.heap` |
| Freezes and relaunches | Zero freezes; zero relaunches | `soak.freezes`, `soak.relaunches` |
| Render latency | Clock tick observed at least once per 2 s window in 99 percent of windows | `soak.render_latency` |

A breach is `assertion_failed (assertion: soak.<metric>)` on the cycle checkpoint, tier 1, with both curves attached, a product finding the Reviewer never sees. New exception signatures in the client log slice (stack headers whose normalized first three frames are absent from the lineage run's signature set) are a tier-2 finding `new_log_signature` on the cycle checkpoint, with the count and the first occurrence; findings, not outcomes, so they never change the checkpoint's outcome. When the client log cannot be located (10.2), the report's soak section says "log signatures: not available" rather than reporting zero.

Report. The RC report's soak section (9.4 Merge and RC report structure) shows both builds' curves per metric with the budget line, restarts, new exception signatures, the memory ceiling reached, and the 24 cycle outcomes. Sign-off at G-N (10.9) requires every soak finding dispositioned. A soak that did not run or did not finish is `not_run (reason: budget)` per unreached cycle and is printed as such in the release gate checklist, never as passed.
