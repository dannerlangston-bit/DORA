Emergency calibration (decision): a fingerprint change that was not planned as a new snapshot generation (7.2) leaves every checkpoint without a calibrated floor, so each above-zero diff is `needs_human (reason: uncalibrated)` at threshold 0 until a Calibration run passes (7.13; `not_comparable` is reserved for a candidate and base that differ from each other). The pool rigs 1 to 3 then run a tier-1-only Calibration run the same night, sharded across them as 1.6 shards the weekend run (five passes of about 180 min, about 5 h on three rigs; rigs 4 and 5 carry the Nightly run), so tier-1 thresholds are valid the next morning, while tiers 2 and 3 stay `needs_human (reason: uncalibrated)`, visible in every matrix and in run health, until the weekend run. Planned fingerprint changes land on Friday after the operating day for this reason.

Sensitivity (PA-03): if Phase 0 measures the census at the 20 s per visit that 2.4 budgets, the merge per-side time is 390 min; a pair without reuse is then 780 rig-min, 213 min on four rigs, over the 3 h budget, and the run proceeds by the cut rule of 2.11 with the lowest-tier census checkpoints `not_run (reason: budget)` printed in the matrix; with reuse it is 507 rig-min, 141 min, inside the budget. The PR run stays inside its budget either way (49 min per side, 43 min wall worst). So a slow census makes base-capture reuse a requirement, not an optimization, or grows the pool to six pool rigs with eight logins.

Daily capacity (PA-10), counting startups: with reuse a PR run costs about 70 rig-minutes and a merge run about 375, so the day needs about 37 rig-hours, 57 percent of the 64 rig-hours a 4-rig pool offers in the operating day; without reuse about 56 rig-hours, 87 percent, above the growth trigger of R15. Base-capture reuse is therefore a Phase 1 week 4 deliverable, and the pool grows by one rig pair if two weeks of measured utilization exceed 70 percent.

Queue and saturation. Runs wait in one queue per pool with priority RC, then merge, then PR, then age. A queued run emits `run_queued` with its queue position every 60 s, which the dead-man timer (9.10 Alerting model, 10.2 Watchdog) accepts in place of `run_started` until the start deadline. Start deadlines, measured from the pipeline trigger: PR run 45 min (one budget), merge run 3 h; an RC run has the RC start deadline, the G-N sign-off time minus 8 hours (8 hours being its budget), and an RC run that cannot start by it is not aborted: the release manager decides (9.12) and the on-call and release channels are told (9.10). A PR run that has not started by its deadline is written `aborted_budget (reason: pool_saturated)`; its comment is the abort block of 9.2 PR comment template with the text "Sentinel did not run: pool saturated, N runs ahead; push again or re-run the build job", the check `sentinel/pr-run` fails with "Sentinel did not run", and the on-call channel gets one P2 per hour naming the queue depth. A merge run that misses its start deadline is not aborted: merges coalesce, so it joins the next merge run and the report names the range. Nightly and Calibration runs have start deadlines too: a Nightly run 02:00 (its 4-hour budget before the 06:00 dead-man deadline), a weekend Calibration run Saturday 02:00 (the latest start whose five passes and Saturday-night sixth pass still end inside `all_quiet`), and an emergency calibration 01:00 (its five passes of about 5 hours end by the 06:00 start of the operating day). A Nightly or Calibration run that has not reached `running` by its start deadline, for example because rig 5 or the pool rigs cannot be provisioned or the run is stuck in its gate sequence, ends `aborted_harness (reason: start_failed)`, written by the Orchestrator when the run is on a rig and otherwise by the Reporter service; every scoped checkpoint without an outcome is `harness_error (reason: start_failed)`; the harness on-call is paged at P1 per the `aborted_harness` row of 9.10; and until a Nightly run's canaries, fire drill and safety canaries next pass, every report and the next PR comment carry the banner "canaries pending: {run type} run {run_id} did not start". A Calibration run that did not start is queued again for the next `all_quiet` window (the next night for an emergency calibration), and checkpoints without a floor stay `needs_human (reason: uncalibrated)` until one passes. An RC pre-emption of the Nightly run is the skip below, not this outcome. During an RC run the pool is reserved until the pair work and its targeted re-runs end (about T+4:00 expected, T+6:00 worst case): PR runs triggered in that window are held with their deadline suspended, the placeholder comment says "queued behind RC run, pool expected free at HH:MM", the check stays pending, and goal 1's 45-minute promise is suspended for that window and printed as such in the RC report. RC respin. A new RC build supersedes the RC run in flight for its train: the running run schedules no new flow, stops at the next flow boundary, runs teardown and the post-run proof on every rig, and ends `aborted_budget (reason: superseded)` with its unreached checkpoints `not_run (reason: budget)`; its partial report is published labelled "superseded by {build}" (9.4); the new RC run starts at once on all six rigs with the pool reservation transferred, so queued PR runs stay held. RC runs pre-empt the Nightly run: when an RC run still holds rigs 4 and 5 at 22:00, the Nightly run is skipped and alerted (9.10), and its canaries, fire drill and safety canaries run in the next free window, on rig 5 after the RC run or at the next 22:00, before any further PR comment is trusted; until then every report and PR comment carries the banner "canaries pending: last Nightly skipped for RC run {run_id}". Outside the operating day the pool is off (11.4); a PR, merge or RC run triggered then waits until 06:00, a PR run with the placeholder "queued until 06:00 America/New_York", and its start deadline is measured from 06:00. The Nightly and Calibration runs are exempt from the operating day (7.10): they run in their own night windows above. Queue depth above 3 PR runs, or any PR run waiting over 20 min outside an RC reservation, posts P2 "pool saturated".

Fleet (decision): 6 rigs, 6 logins, one login per rig. Rigs 1 to 4 are the pool; rig 5 runs the Nightly run and the soak (candidate only, compared against the lineage soak curve of 10.11); Calibration runs are sharded across the pool, rigs 1 to 4, in one weekend `all_quiet` window, while rig 5 keeps the Nightly canaries, fire drill and safety canaries (1.6); rig 4 stays on after the operating day for the Nightly A/A pass; rig 6 is the Explorer rig with the Explorer login (6.8 Explorer boundary and deny list), which cannot load the fixture workspaces, so rig 6 does no scripted work. Rig 6 is the hardware spare: it replaces a failed pool rig only after the Rig Manager re-snapshots it with that rig's login, recorded with the operator's name, because a login is never on two rigs at once.

### 11.3 Sharding and parallelism

Parallelism equals the number of logins. Each rig has one login and no login has two sessions at once whatever DR-06 finds, because positions, watchlists, alerts and settings are per login and appear in captures. The Explorer login never does scripted work.

The shard rule is that of 2.11 `order_and_cut`, stated here as well. Census items are keyed by (surface tab, data mode), the tab being Monitor, Trade, Analyze, Scan, MarketWatch, Charts, Tools or Setup, each with its dialogs and context menus, so a shard is all frozen or all masked_live; flow items are keyed by a stable hash of `flow_id` within tier; flows that share a `state_scope` (4.7: they touch the same server-side state) or a fixture are pinned to one shard so teardowns do not race. A shard is one session on one rig (frozen) or one session on each rig of a pair (masked_live) and loads only the workspaces it needs. Shards are packed longest-first (LPT) by measured p50, session startups included (PA-04: 4 min, 8 min for a session with a fixture reset). The shard planner assigns masked_live shards to rig pairs first, frozen shards to the rigs that remain, and a frozen shard may use a pair rig that is idle; the Rig Manager asserts fingerprint equality on a pair before the first capture and a mismatch makes the shard's checkpoints `not_comparable (reason: fingerprint_mismatch)`. A frozen shard whose base capture is reused runs the candidate only; otherwise its rig runs base then candidate (one snapshot per build, 7.2 Snapshot lifecycle, so the switch is a revert to the other build's snapshot and a second session startup, counted in 11.2).

### 11.4 Cost model

Rig VMs. A rig is a 4 vCPU, 16 GB, 100 GB Windows 11 Enterprise VM (7.1 Rig specification). Rigs 1 to 3 run only in the operating day (PA-12) on business days, rig 4 also through the Nightly run, rig 5 always, rig 6 only during RC runs, plus about 60 VM-hours a month of weekend calibration: about 2,500 VM-hours a month, 4,320 if all six stay on; at an internal chargeback of 0.10 to 0.25 dollars per VM-hour including the Windows licence (placeholder) that is 250 to 625 dollars a month, or 430 to 1,080 always on. ### 11.5 Maintenance model

Repositories (8.1, 8.5 What lives in git and how a run pins it). `sentinel` holds the harness and is pinned per run as the harness commit. `sentinel-config` holds everything a run is asked to do: Surface Registry, Dependency Map, flows, Region Registry and masks, Workspace Corpus, popup and mutant catalogs, fixtures, eval labels, released baseline manifests, `taxonomy.yaml`, `phase0/branches.yaml`, `policy/send_policy.yaml`, `policy/release_gate.yaml`, `policy/budgets.yaml` (11.4), `quarantine.yaml` (10.5), the credential rotation calendar of 7.7 in `ops/credential_rotation.yaml` and the triage and on-call roster in `ops/oncall.yaml` (11.6). CODEOWNERS routes `flows/` and `registry/` to the tier's flow owner. Every maintenance action in this section is a pull request to `sentinel-config` that passes `sentinel lint` (4.1 Conventions, repository layout and the lint; 4.15 Cross-file rules and the lint pipeline); nothing here edits SQLite by hand.

Recorder. A flow is authored by driving the app once with the Recorder on (global mouse and keyboard hook plus a screenshot per action); it emits YAML steps whose targets are image anchors (a template of about 40x20 px around a stable icon or label, versioned with the flow) plus an offset, with an OCR text anchor as the next rung and JAB first under DR-01 A. Secret steps record as `secret: vault_ref` with the hook paused and capture suspended; anchors are per display tier. Re-anchor mode shows each broken anchor beside the agent's final click target and lets the owner accept the proposed crop or re-record the step.

Pre-run anchor lint. Before every run the Orchestrator matches every anchor of every scheduled flow and every Region Registry landmark against the latest approved base-build capture of its checkpoint. A miss is a maintenance item posted to the flow owner in run health, not a checkpoint outcome; the flow still runs and ends `passed_via_agent_fallback` with the locator failure recorded as a finding, `failed` when the ladder is exhausted or fallback is disabled, or `landmark_missing` for a region. It exists so the owner hears about a broken anchor before the fallback quietly takes the flow over, and it runs in CI on every PR touching a flow, mask or registry file.

Flow fields. Every flow file carries `owner` and `tier` (4.7). Its health figures are not flow-file fields: the Reporter derives `agent_fallback_rate` and `flake_rate` from `step_events` and outcomes over 30 days and `last_repaired` from git history, and prints them per flow (5.16). A successful agent fallback records the final click target and anchor crop, which Phase 3 turns into an anchor-patch PR to the owner. Two consecutive fallbacks on one step on one build open an "update scripted flow" ticket (9.9 Jira and Slack rules). Checkpoint quarantine follows 10.5 Flake tracking, targeted re-runs and quarantine exactly: flake score above 0.10 over at least 5 observations, `not_settled (reason: aa_drift)` on 3 consecutive Nightly runs (10.6), the gateway drop thresholds (any safety-reason drop, or 3 integrity-reason drops in one flow, quarantine the flow; 6.2), 3 unstable outcomes in 7 days, 2 verdict flips on one build, or a non-zero frozen A/A floor unfixed for 5 business days; the Orchestrator opens the `quarantine.yaml` PR and the system owner merges it. In addition a flow whose 30-day fallback rate exceeds 5 percent is quarantined whole by the same mechanism (reason `fallback_rate`, a trigger 10.5 and 3.10 list), because a flow the agent keeps rescuing no longer tests what it was written to test. A quarantined item is `not_run (reason: quarantine)` on every run, in its own color in the coverage matrix, never covered; the owner has five business days, and exit needs the fix plus five clean captures in a Calibration run (10.5). Above 2 percent of tier-1 checkpoints quarantined, run health is red and the RC gate blocks.

Budget overrun (decision). When a role's logged hours exceed its budget for two consecutive weeks, the cut is made visibly, never by letting items age past SLA: the system owner quarantines the lowest-tier flows with the highest fallback or flake rate until the open backlog fits the budget, each through the `quarantine.yaml` PR with reason `maintenance_budget`; their checkpoints are `not_run (reason: quarantine)`, the coverage percent for that tier drops in the matrix and the report header prints "tier 3 coverage reduced: maintenance budget, N flows". Tier 3 is cut first, then tier 2; tier 1 is never cut this way. A tier-1 overrun pages the system owner, freezes new flows until the backlog clears (the flake kill rule of 1.5) and is reported to the release manager because tier-1 coverage below 100 percent blocks the RC gate. The same rule applies when time to triage runs above 2x target for two releases (1.5): tier-3 scope is cut and the cut is printed.

The morning after a toolbar redesign. The merge run that lands it declares the toolbar surfaces, so their census diffs classify `intended`, while diffs on undeclared surfaces that merely host the toolbar classify `collateral` and are triage's first item. Flows anchored on the toolbar miss their first rung and walk the ladder: the OCR text anchor usually holds if labels survived, otherwise the step is `passed_via_agent_fallback` with a finding or `failed` if preflight disabled fallback; regions anchored to toolbar landmarks are `landmark_missing`; run health clusters by anchor template ("38 flows in fallback, 31 on anchor toolbar_trade_tab"). Next morning triage confirms the redesign against the manifest; tier owners open re-anchor mode, accept the proposed crops for rescued steps, re-record the rest, re-anchor the landmarks, pass the lint in one PR per tier, and a targeted re-run returns `passed` in scripted mode: about 15 minutes per flow with proposals, so 40 flows is two people for half a day, against three person-days without the Recorder. The next merge run uses the redesigned build as base, so the census diffs disappear; a human approves the RC lineage baseline at the RC run.
