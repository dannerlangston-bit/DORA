## 7. Environment, state and determinism

This section fixes everything outside the product that can move a pixel or a number: the rig, the installed build, the server-side state on the login, the market data, the clock and the network. One principle applies throughout. Whatever affects a capture is pinned, read live at run start, recorded in the environment fingerprint and compared between the candidate capture and the base capture, whether the two halves of the pair ran on one rig back to back or on two rigs in lockstep (7.4). An environment that cannot be verified never produces a diff; it produces `env_error` (a gate failed before the checkpoint, with the gate name, a reason and a screenshot) or `not_comparable` (the two halves of the pair do not match), and both go to the on-call channel, not the triage queue (9.10 Alerting model). Every failure path in this section ends in exactly one outcome with a reason code from the vocabulary in 12.2 Outcome taxonomy and a named place where a human sees it; nothing is skipped, retried or defaulted without a record. Facts about thinkorswim, paperMoney and Schwab are marked verified or unverified where they appear, each with the branch that handles the other answer; 7.14 lists the Phase 0 checks.

### 7.1 Rig specification

The fleet is six Windows 11 VMs and six logins (11.2 Cadence and time budgets per run type): rigs 1 to 4 are the pool for PR and merge runs, rig 5 runs the Nightly run and the soak, Calibration runs are sharded across the pool (rigs 1 to 4) in one weekend `all_quiet` window while the Nightly canaries and the fire drill stay on rig 5 (1.6, 7.13), rig 6 is the Explorer rig and the pool spare; RC runs use all six. One rig is one VM, one thinkorswim login and one worker; parallelism equals the number of logins. A physical D3D rig joins as a tier B rendering cell in Phase 3 (11.7 Prerequisites checklist, row 4) with its own fingerprint and calibration. Phase 1 pins one display configuration; further configurations (theme, font size, a second monitor, 125 percent scaling) arrive in Phase 3 as entries in `configs/allowed.yaml` (4.6 Workspace Corpus entry, rule L-WSP-05), each a fingerprint of its own with its own calibration, never a variant inside one fingerprint. A low-memory cell (a reduced heap in a vmoptions variant) is a tier B cell of the same kind.

Every row below is read live before the state machine leaves `provisioned`; the preflight id is the 12.7 Preflight checklist item that reads it, and a failed R or B item marks every scheduled checkpoint of the shard `env_error (gate: preflight.<item>)` and ends the run `complete_with_env_errors`. A value that an R or B item reads takes that item's outcome even when it is readable and differs from the pinned specification. The fingerprint lint's `env_error (gate: provisioned, reason: rig_spec_mismatch)` (4.12 Environment fingerprint, rule L-FPR-02) applies only to fingerprint fields that no R or B item reads, such as the running-process allowlist, the GPU, the theme and the font size. A value that cannot be read at all is `env_error (gate: provisioned, reason: fingerprint_unreadable:<field>)`; the fingerprint never carries a null and is never inferred from the snapshot name.

### 7.2 Snapshot lifecycle

Four snapshot kinds per rig, each named and hashed; every run starts from a revert. Snapshots are per VM, so each rig carries its own copies and the Rig Manager creates a build's snapshot on a rig the first time that rig needs the build.

- base-os.<gen>: hardened Windows (7.12), display, time zone, layout, autologon, security exceptions, no thinkorswim. A new generation is built only to take Windows Update, a driver or hypervisor change, or a hardening change, and triggers a calibration run before use (7.13).
- app.<build_id>.<gen>: base-os plus the pinned build with auto-update disabled (7.3), thinkorswim.vmoptions written, the Workspace Corpus files in the install's usergui folder, the first-launch dialogs handled (7.3 step 6), the app closed cleanly, and under login Branch B the device trust established (7.7). A pair on one rig is two reverts: app.<base>.<gen> for the base half, then app.<candidate>.<gen> for the candidate half (2.11), so base reuse is decided before any candidate work and the candidate half never inherits local state the base half left behind. When the base capture is reused (7.4) the base revert and pass do not happen.
- explorer.<build_id>.<gen>: as app, built on rig 6 with the Explorer's own login and profile; the Explorer never runs on an app snapshot and no scripted flow ever runs on an explorer snapshot (6.8 Explorer boundary and deny list).
- upgrade.<N-1> and upgrade.<N-2>: the previous released builds with the tier B profile library in usergui, consumed by the release-night upgrade run (11.8 Phase 0 spike plan, DR-04 Branch B, and 10.9 Release-day timeline) and rebuilt from each release. That run captures every first-start dialog as a checkpoint, and the validate step below captures a fresh install's first launch the same way, so both the upgrade-in-place path and the fresh-install path are exercised.

Lifecycle: create (automated from the artifact; the only human step is an agreement dialog, 7.3 step 6; the operator's name is logged when one occurs), validate (live fingerprint equals the manifest written at creation; one smoke flow passes; the first-launch screens are captured), calibrate (every base-os generation; app snapshots when 7.13 says so), use (the Rig Manager reverts before every run and before the second half of a pair, verifies the snapshot manifest hash (preflight R1) and records the snapshot id in the run row), retire (a build older than the last release and not one of the two newest main builds is deleted; its fingerprint and calibration rows stay in SQLite). Disk per rig: the two newest main builds, the last released build, the two upgrade snapshots and the branch builds of PR runs in flight, each about the size of one install; branch-build snapshots are deleted when their PR run reports.

Failure outcomes of the lifecycle, each visible in run health and the on-call channel:

| Failure | Outcome |
|---|---|
| Revert fails (hypervisor API error or timeout) | The Rig Manager retries the revert once after 60 s. A second failure marks every checkpoint of the shard `env_error (gate: provisioned, reason: snapshot_revert_failed)`; the shard is re-queued to a pool rig of the same base-os generation if the budget allows (10.7 Degraded modes, rig rules), else the run ends `complete_with_env_errors`. |
| Revert reports success but the snapshot manifest hash differs (wrong or tampered snapshot) | `env_error (gate: preflight.R1)` on every checkpoint of the shard; the snapshot is quarantined and rebuilt. |
| No rig can be provisioned (hypervisor unreachable, pool exhausted) | The run stays queued and never reaches `running`, so it is not a dead-man case (`dead_man` applies only to a run that reached `running` and then stopped reporting, 10.2); past its start deadline it takes the start-deadline outcome of 11.2: a PR run `aborted_budget (reason: pool_saturated)`, a merge run coalesced into the next merge run, an RC run decided by the release manager (9.12), a Nightly or Calibration run `aborted_harness (reason: start_failed)` (11.2 Queue and saturation, paged per 9.10). The Rig Manager's provisioning failure is posted to the on-call channel (9.10 Alerting model). |
| Snapshot creation fails (install, vmoptions write, corpus copy, first launch, fingerprint read) | No snapshot is written. The run that needed it marks its checkpoints `env_error (gate: provisioned, reason: install_failed)` with the installer log attached (7.3). |
| Validate fails (fingerprint differs from the manifest, smoke flow fails) | The snapshot is deleted, the failure is a maintenance item for the Rig Manager owner, and runs needing the build take the `install_failed` outcome above. |

Under pinned-install Branch A a revert does not re-download the build. Under Branch B (the launcher cannot be stopped from updating) a revert would download on every launch, so Branch B snapshots are taken after the updater has run, the run manifest records the build the launcher produced, and both halves of a pair revert to snapshots taken the same night. Teardown never relies on killing the process: local state is covered by the revert; server-side state persists at change time, so the server-side teardown (verified Cancel All, positions-flat check, 5.2 Orchestrator state `teardown`) runs before the revert, and a forced kill after a crash leaves server-side drift that the next run's fixture reset flow (7.6) repairs or reports.

### 7.3 Pinned build install and version read

Install, Branch A (expected, pipeline artifact), run by the Rig Manager on the target rig:

1. Fetch the artifact for the build id and verify its checksum against the pipeline record (preflight B1). Mismatch: `env_error (gate: preflight.B1)`, nothing installed.
2. Revert to base-os.<gen>.
3. Install silently to the standard path with the auto-update check disabled, using the build flag or launcher configuration the build team provides (DR-04 deliverable, 11.8). A non-zero installer exit or a missing main executable afterwards is `env_error (gate: provisioned, reason: install_failed)` with the installer log attached. Acceptance of the mechanism itself: two launches 24 hours apart, update host reachable, same build id in the title (preflight B2 re-checks the setting every run).
4. Write thinkorswim.vmoptions from the checked-in template (pipeline flags, heap, -XX:ErrorFile, -XX:+HeapDumpOnOutOfMemoryError, -XX:HeapDumpPath pointed at the artifact folder and -XX:+CreateCoredumpOnCrash, the list 5.14 and 10.2 name, flags checked against the bundled JDK major version); record the sha256.
5. Copy the Workspace Corpus files into usergui; record each sha256.
6. Launch once. The popup catalog (7.8) handles What's New (POP-02) and the Message Center (POP-06). A user, exchange or terms agreement (POP-03) stops the build as `env_error (gate: authenticated, reason: agreement_pending)`: acceptance is server-side per login and permanent, so it happens once per login, by the accounts owner at the hypervisor console, with the operator's name logged; the harness never accepts an agreement. Because acceptance is per login and not per build, a new build normally produces no agreement and snapshot creation is unattended; only a new agreement version brings a human back. Close the app cleanly.
7. Read the fingerprint (7.4), store it as the snapshot manifest, snapshot.

Branch B (the public launcher checks for updates on every start, verified in Schwab's install guide, and cannot be pinned): snapshot right after a launch in which the updater finished under a hard timeout; the build id read after that launch is the snapshot's build id; the release-night upgrade run captures every first-start dialog as a checkpoint. The pipeline artifact remains the source for the dependency map and static impact step (2.10 Coverage model: Dependency Map and static impact).

Version read, in order:

1. Main window title by GetWindowText on the main frame (class SunAwtFrame, PID in the launched process tree). Community sources report "Main@thinkorswim [build NNNN]"; the regex is a config value confirmed in Phase 0 and recorded in `phase0/branches.yaml` (4.1). No OCR.
2. Only when the title does not match: Help > About, OCR of the build line at 1:1 and upscaled. The About render is captured every run as `render_probe_hash` (7.4) regardless.
3. JRE from the release file in the bundled runtime folder (JAVA_VERSION, IMPLEMENTOR, OS_ARCH; whole file hashed).
4. Jar listing: sorted names and sizes under the install folder, hashed.

The build id is read at launch, after every relaunch and before each flow. A build id at launch that differs from the requested build is `env_error (gate: launched, reason: version_mismatch)` (Branch A: the install failed or the setting did not hold; Branch B: the updater landed a new build); nothing else runs on that rig until a human looks. A change within a run is `env_error (gate: launched, reason: version_changed_mid_run)` for every remaining checkpoint of the shard; the run ends `complete_with_env_errors` and the on-call channel gets both ids and the launcher log. A launcher restart that updates the app shows first as a `process_exit`: the Watchdog checks the launcher log for an update and compares the build manifest before classifying it, and either one present makes it this case rather than an app failure, with no `app_crash` finding and no relaunch consumed (5.14, 10.2). Neither title read is ever retried into a different answer: the first regex match stands and a non-match falls to step 2 exactly once; a non-match there too is `env_error (gate: launched, reason: fingerprint_unreadable:build_id)`. Same build does not mean same UI: server-side configuration changes screens with no client version change, which is why both halves of a pair run in the same data window and why the nightly A/A drift check exists (10.6 A/A drift on the Nightly run).

### 7.4 Environment fingerprint

Read live at gate `provisioned` (OS fields) and gate `launched` (app fields; `render_probe_hash` after `authenticated`), never inferred from a snapshot name, because the updater, a policy refresh or a human on the console can change a rig after it was labeled. Stored per run and per side (8.3 Schema, table env_fingerprints) with the fingerprint id in every capture's metadata. `fingerprint_id` is the sha256 over the canonical JSON of the match-class fields other than `build_id`, so it names a rendering environment, not a build. Candidate and base must agree on every field of class match, else every checkpoint of the pair is `not_comparable (reason: fingerprint_mismatch)` with the differing field names in the outcome record, the run ends `complete_with_env_errors` and the Diff Engine refuses the pair before looking at pixels (preflight G5 does this before any capture when both halves are already provisioned; otherwise the check runs before the first capture of the second half). Class record fields serve diagnosis and redaction. A field that cannot be read is `env_error (gate: provisioned or launched, reason: fingerprint_unreadable:<field>)`; it is never null and never copied from the other side.

Pairing and scheduling by data mode (decision shared with 3.1 Build pair rules and 11.3 Sharding and parallelism):

- Frozen checkpoints: the base half and then the candidate half run on the same rig back to back (base snapshot, run, candidate snapshot, run; 2.11), which makes every OS, display and harness field equal by construction and leaves only the app fields and the data epoch to check. The base half is skipped when a stored base capture of the same checkpoint exists under the base-reuse key of 7.9 (identical `fingerprint_id`, `epoch_id`, fixture file sha256 and golden `seeded_at`); that reuse is recorded per checkpoint in run health as `base_reused`, and a PR run's base is normally its merge run's capture.
- masked_live checkpoints: two rigs reverted from the same base-os generation and the same app snapshot generation, fingerprint equality asserted before the first capture, executing the same checkpoint within the same minute (lockstep; a slip over 60 s re-queues the pair once at the end of the shard and a second slip is `not_run (reason: budget)`, counted as `lockstep_slip` in run health, never a finding, 3.1). If only one rig is free, masked_live checkpoints are `not_run (reason: budget)` rather than captured minutes apart, and the coverage matrix shows them so. A masked_live base capture is never reused.
- Either way, the Orchestrator asserts the fingerprint match before the first checkpoint of a pair and again after every relaunch; a relaunch that changes an app field (a new build landed, a rewritten vmoptions) is `env_error (gate: launched, reason: version_changed_mid_run)` for the rest of the shard.

### 7.5 State model

Saved workspaces are local files, not account-synced (several community sources, one citing the manual, consistent with tos.mx workspace sharing and the installer's option to reuse an old settings folder). Custom studies, scans, watchlists, chart settings and drawings, alerts, notes, saved orders, most Application Settings, Order Defaults and Favorites are server-side on the login and persist when changed, not on exit (reported; the Explorer teardown in 6.8 depends on the same fact). Phase 0 confirms every row below by changing the item on rig A and logging in on rig B (7.14, check 4); a row whose placement is marked unverified is written for the reported placement and has the other branch in the Restored by column.

Three restore mechanisms exist and nothing else: the snapshot revert (local state), the fixture reset flow (server-side state the harness may change, 7.6) and a human (server-side state the harness must never change: safety settings, agreements, the golden portfolio). Every row names one of the three. Drift found by a gate is `env_error` or `aborted_safety` and never reaches the Diff Engine: a drift diff repeats every night and teaches people to ignore the report. Rows marked `account_state` are the ones whose `fixture_drift` outcome is scoped to checkpoints flagged `account_state: true` in the Surface Registry (surfaces that render positions, balances, orders or account history); every other `fixture_drift` row marks the whole shard, because watchlists, studies and settings show on almost every surface.

### 7.6 Fixture reset flow and verify_account_fixture

Scripted only, no agent fallback, because it touches account state. Two stages close two gates. Each stage is a flow of class `fixture_reset` (4.7 Flow file) whose steps and checkpoints appear in the run health section, so a reset is never invisible.

Stage 1, profile, after gate `paper_mode_asserted`, before the attestation that closes `settings_attested` (6.3 Run-start settings attestation):

1. Read the safety rows first (attestation A3 to A7). Any mismatch is `aborted_safety` with the screenshot, before anything is corrected, because something changed a safety setting since the last run and that is an incident, not drift.
2. Application Settings and Order Defaults page by page against the checked-in profiles: OCR, correct differing non-safety controls with scripted clicks, OCR again. One correction pass; a control still wrong after it is `env_error (gate: settings_attested, reason: fixture_drift)` for the shard.
3. Delete non-fixture watchlists; import missing fixture watchlists from checked-in files.
4. Delete all alerts.
5. Delete saved orders and order templates; delete notes on fixture symbols.
6. Re-import custom studies and scans from checked-in exports when the lists differ.
7. Clear drawings on fixture symbols; re-apply checked-in chart settings.
8. Profile checkpoint set (Setup dialogs, watchlist picker, alert book, studies list, saved scans) at tight thresholds; mismatch is `env_error (gate: settings_attested, reason: fixture_drift)`.
9. Attestation A1 to A11 runs and closes `settings_attested`; it changes nothing (6.3).

Stage 2, account, after `workspace_loaded` so Monitor sits in a known layout (closes `fixture_verified`):

1. `verify_account_fixture`: account selector equals the rig's allowlisted fixture account id (exact match, 6.4); Monitor > Activity and Positions; Position Statement rows by Copy All and by grid OCR, cross-checked (2.8.1 Sources); Working Orders; cash and buying power cells. Compare with the fixture file: positions exact on symbol and quantity, working orders exactly zero, cash within `cash_tolerance` (marks move daily even when the market is closed), buying power by rule.
2. Working orders present: `aborted_safety (reason: unexpected_working_order)`, process tree killed, the breach finding carries the Working Orders screenshot and the Copy All text, the incident procedure in 6.12 opens. Under `paper_send_ok` (OPEN, 6.7 Send policy: both branches) orders carrying the run's own tag are cancelled by the verified Cancel All first; a foreign order still aborts.
3. Empty account, positions present or cash out of tolerance: Monitor > Activity and Positions > Position Statement > Adjust Account > Reset All Balances and Positions (restores the $100,000 default; path per Schwab and community sources, labels confirmed in Phase 0), then Set Account Cash to the fixture value when the fixture holds a `cash_floor`. Whether the reset also clears working orders, alerts and history is unverified; the flow re-reads all three. Whether Set Account Cash accepts a small amount is unverified; if it does not, `cash_floor` is removed from the fixture and the Input Gateway alone carries the no-send guarantee.
4. Golden account, positions differ or cash out of tolerance: never reset automatically, because the reset would destroy the seeded portfolio. `env_error (gate: fixture_verified, reason: fixture_drift)` on `account_state` checkpoints of the golden account, a re-seed task to the accounts owner with the Copy All text, and the rest of the run proceeds. The same outcome applies when the date of the fixture's `reseed_due` event in `churn_calendar` (4.9) has passed (an expiration in the seeded list), with reason `fixture_maintenance_needed`.
5. Re-run `verify_account_fixture` after an empty-account reset. A second mismatch is `env_error (gate: fixture_verified, reason: fixture_drift)` on `account_state` checkpoints; the channel gets the screenshots. No third attempt.
6. Recompute the fixture's far-from-market `prices` from the Oracle API, or from the app's own quote by OCR when preflight N3 failed, and record which source was used (4.9 Fixture, rule L-FIX-08).
7. Pinned quote and symbol fixture check for the data epoch (7.9).

Each paperMoney login has a margin account and an IRA, $100,000 each (verified), so the selector is a drift source and each role is fixed: margin is the golden account (populated), IRA is the empty account. A flow names the role it runs on in `account_role` (4.7, default `empty`, which most flows use); a census checkpoint takes the `account_role` of its workspace entry (4.6, default `golden`). The golden account is seeded by a named human during market hours from a checked-in list (equities below $1 and above $1,000, a multi-leg option position, a LEAPS, one futures and one forex position); paperMoney orders fill only while the market is open, so seeding is a calendar task for the accounts owner on the expiration calendar (11.5 Maintenance model), never an Executor step, and expiration day itself is a checkpoint day. The golden account's value cells are `rule` regions, never `diff`. A flow the IRA cannot run (no futures, forex or margin buying power) declares the entitlement and runs on a second login or is `not_run (reason: entitlement)`; paperMoney represents one account type per role, so entitlement cells in the coverage matrix are per login (2.12 Coverage accounting and the matrix). As an independent paperMoney-only layer, the empty account's cash is held at a small fixed amount (`cash_floor`) so an accidental send larger than the fixture size is rejected for buying power; the layer is dropped where `paper_send_ok` is enabled (rule L-FIX-02).

### 7.7 Login and re-login flows with MFA branches

Known facts. Schwab two-step verification offers a Symantec VIP credential (app or hardware token) or a text message code, in "always at login" or "only on untrusted devices" modes; no push approval and no generic TOTP seed were found (consistent across sources; security confirms before the flow is built). Risk-based authentication can prompt for a one-time code on an unusual login even with two-step off (reported). Lockout thresholds are unverified. Whether the login dialog remembers the paperMoney toggle is unverified, so it is asserted every time. No Guest Pass logins (demo only, 30 days, not extendable, separate from a brokerage login).

LOGIN flow: class `login`, scripted only, agent fallback hard-disabled until the post-login checkpoint, every screen a checkpoint, credentials as secret steps (6.9 Credentials and secret steps). One attempt per run; the flow never loops. Every exit is one of the outcomes named below, each posted to the on-call channel with the screen, and the accounts owner is alerted whenever the login itself, not the rig, is the cause.

1. Launcher. Under Branch A no update progress is expected; progress visible (POP-01) is `env_error (gate: launched, reason: version_mismatch)`.
2. Login screen. Assert by template that paperMoney is selected and Live Trading is not, before any typing. If Live is selected, click paperMoney and re-assert; still Live is `env_error (gate: authenticated, reason: live_mode_selected)` and nothing is typed. Assert remember-password is off; clear the username field (Ctrl+A, Delete) so a remembered name never concatenates with the typed one. The Setup button is never touched.
3. Username and password as secret steps: recorder paused, capture suspended, log shows the redacted placeholder. A vault lease that cannot be obtained at typing time (the vault answered preflight N6 and failed since) is `env_error (gate: authenticated, reason: vault_unreachable)` (6.9); nothing is typed.
4. MFA branch (DR-03, 11.8).
   - Branch A, test-backend credential without MFA: the main window is expected next; any challenge screen (POP-21) is `env_error (gate: authenticated, reason: authentication_challenge)`.
   - Branch B, trusted-device exemption: no prompt is expected because the snapshot was taken after trust was established. A prompt means the trust did not survive the revert (whether Schwab rotates the device token per login is unverified; Phase 0 runs ten revert-and-login cycles). The scripted recovery flow captures the prompt as the `trusted_device_prompt` checkpoint, posts it to the accounts owner's channel and waits a configured window (default 10 minutes) for the owner to enter the SMS code through the hypervisor console, once; no code inside the window is `env_error (gate: authenticated, reason: authentication_challenge)`. A VIP credential provisioned with the open-source python-vipaccess tool (OATH secret in the vault, code typed as a secret step) is a sub-branch only with explicit written security approval, because it re-implements VIP Access in software.
   - Any authentication error (bad credential, lockout, disabled login): `env_error (gate: authenticated, reason: authentication_failed)` with the screen; never retried; the rig is held until the accounts owner clears it, because a lockout blocks every later run on the rig.
   - Paging: `authentication_failed` and `authentication_challenge` page both the login owner and the accounts owner; `vault_unreachable` (step 3) pages the system owner (6.9).
5. Post-login popups per 7.8: POP-03 aborts to a human; POP-06 and POP-08 are dismissed and counted.
6. Main window present and the title regex matches (7.3): gate `authenticated`. Absent within the login max wait (default 120 s): `env_error (gate: authenticated, reason: timeout)`.
7. Account selector read by OCR (JAB under Branch A); the text must equal one entry of the hard-coded allowlist of exact account ids for this rig (the fixture's two accounts; `D-` is a format expectation checked in Phase 0, not the test), and the fixture account for the role the work item declares (`account_role`, 4.7 and 4.6) is selected explicitly: gate `paper_mode_asserted`. Mismatch kills the process tree, `aborted_safety` (6.4 Paper-mode assertion and test identity).
8. The OnDemand toolbar is absent by template (7.9); present is `env_error (gate: fixture_verified, reason: ondemand_state)`.

Session rule (DR-06). Community reports say a second login from another location disconnects the first with a message, and that several instances on one machine coexist; both are unverified and Phase 0 tests them. One login maps to one rig and runs on one identity are serialized whatever the answer, so the rule matters only for recovery: the "logged in from another location" dialog (POP-04) is `env_error (gate: authenticated, reason: session_kicked)` for every remaining checkpoint of the shard, the run ends `complete_with_env_errors`, no re-login is attempted for the run (a human or another process is on the test login) and the accounts owner is alerted. The post-run proof still runs (6.6): after `session_release_wait` one fresh login is made for the proof alone; if the login is still unavailable after one retry, the proof is UNPROVEN with reason `session_unavailable`, the login is blocked and a human verifies the account.

Re-login flow. Triggered by the session-expired, disconnected or reconnecting dialog (POP-05), by the Watchdog after a crash or hang (10.2 Watchdog), or by the proactive relaunch every 40 flows or 90 minutes: the Watchdog kills the orphan process tree and collects artifacts (hs_err_pid*.log, client log slice, dumps); `reset_input_state` runs; relaunch; the state machine re-enters at `launched` and passes every gate again, LOGIN flow, paper-mode assertion, attestation, workspace check and `verify_account_fixture` included, with nothing lighter at re-login; resume at the next flow boundary. Two budgets apply, by cause. An environment re-login (POP-05 session expired, disconnected or reconnecting, or a reconnect that re-authenticates, 10.7) counts against the re-login budget K (default 3 per run); past it the run ends `complete_with_env_errors (reason: relogin_budget)` with the remaining checkpoints `env_error (gate: authenticated, reason: relogin_budget)`, as 1.10 states. A relaunch after a crash or hang counts against the Watchdog's budget of 3 app relaunches per shard (10.2): the first three app failures in a shard are each relaunched, and a fourth (a failure during the gate sequence of the shard's first launch or of a relaunch counts, 5.2) marks the remaining checkpoints `not_run (reason: budget)` and the run `aborted_budget (reason: app_restart_budget)`. The proactive relaunch counts against neither, and a hook-host restart has its own budget of one per shard (5.4.2). Before any relaunch login the Orchestrator waits `session_release_wait` (default 60 s, measured in DR-06) so the orphaned server session can end under the coexisting-sessions branch. Re-login checkpoints appear in the report's run health section with their trigger and the budget they consumed.

Credential rotation calendar. Schwab password and vault token rotation per the platform and security policies, by the accounts owner in a maintenance window followed by a login-only canary run (6.9); the calendar `ops/credential_rotation.yaml` in `sentinel-config` (4.1, schema in 4.16; 8.5) records date, owner and validating run id. The on-call and triage roster is the separate file `ops/oncall.yaml` (11.6). A run scheduled inside a rotation window is held, not started, and the hold is a run health line. Every login has a named owner, a backup owner and, for Branch B, a team-owned SMS device; the Explorer login has no verified email or phone (6.8 Explorer boundary and deny list; attestation A10).

### 7.8 Popup catalog policy and starter entries

Policy:

1. Before every step and every capture, the Executor enumerates the top-level windows of the thinkorswim process tree by PID (EnumWindows, GetWindowThreadProcessId; classes SunAwtFrame, SunAwtDialog, SunAwtWindow). Anything other than the main frame, the checkpoint's declared target window and the detached windows the corpus workspace declares is a popup. IsWindowEnabled false on the main frame before an input batch means a modal is up; unless it is the expected dialog by title or template, it is a popup. GetForegroundWindow outside the process tree before an input batch is a foreign-window event and the batch is not emitted: `env_error (gate: running, reason: occluded)` for the checkpoint (or the gate in force when it happens before `running`), as in 5.7 Capture.
2. Transient windows are not popups: owned, untitled SunAwtWindow instances that the app opens under the pointer (menus, tooltips, combo drop-downs, the symbol autocomplete list) while a step is in progress. The gateway's slow half lets the step finish; symbol entry types the fully qualified symbol and commits with the flow's declared key so the autocomplete list closes. One still present at capture time fails settle as `not_settled (reason: unexpected_window:<title>)`.
3. Each popup is matched against the versioned catalog (schema in 4.10 Popup catalog entry): title regex plus small template, action, class, expected phases. Every hit is logged with a screenshot and counted per run and per build; a rise after a build change is a finding in the Unexpected section. Actions are the schema's six: `dismiss_key`, `click`, `wait`, `relogin`, `abort` and `ignore` (4.10); the class decides what happens around the action: `dismissable` (dismiss, count), `env` (abort the shard as `env_error` with the gate in force and the reason in the table; every `env_error` names its gate), `login` (hand to the LOGIN or re-login flow), `app_failure` (app error dialogs, below), `safety` (no input is ever emitted; the kill switch owns it), `order_event` (an order-submitted, order-rejected or order-filled notification; the kill switch fires and the run is `aborted_safety`, 6.6).
4. App error dialogs are never on a dismiss list. An error or exception dialog present at capture is INV-14 `invariant_violation` (2.7 Layout invariants). A process that is gone, or an Event Dispatch Thread frozen past the checkpoint's max wait, is `assertion_failed (assertion: app_alive)` on the checkpoint being captured, `not_run (reason: app_crash)` for the rest of that flow and a tier-1 finding `app_crash` with hs_err_pid files and the log slice attached; the Watchdog collects and relaunches (10.1 Failure classes and the diff-engine rule, 10.2 Watchdog). The Reviewer never sees either.
5. Unmatched: handed to the agent with the dismiss-only toolset (Escape, title-bar close, or a click on a control whose OCR text is in the dismiss allowlist: OK, Close, Later, Not now, Dismiss, Cancel; never Accept, Agree, Confirm, Send, Yes, Save) and reported as `unknown_popup` with a proposed catalog entry; the registry owner has one business day to catalog it (11.10 Risk register, R17). With agent mode disabled (DR-07 Branch B, or preflight N2 failed) the Executor sends WM_CLOSE, which is the title-bar close and never a confirm. An unmatched window whose title matches the order-dialog regex set, or any unmatched window that appears while a step with `order_stage: true` holds the ticket flag, is never handed to the agent and never closed by the Executor: with `order_stage` set the run ends `aborted_safety (reason: unknown_dialog_in_order_stage)` through the kill switch sequence (6.6); otherwise the flow is quarantined and the window is an `unknown_popup` finding (5.4.3, 6.2). If the window persists: inside a flow the step is `failed` with the `unknown_popup` finding, downstream checkpoints are `not_run (reason: step_failed:<step>)`, `reset_input_state` runs and the next flow's preconditions decide on a reload; at a census checkpoint the outcome is `not_settled (reason: unexpected_window:<title>)` and the census moves on.
6. The catalog is versioned with the build; entries carry first-seen build, last-seen build and owner; an entry unseen for three releases is flagged for retirement (`retired: true` with a reason, 4.10), and a starter entry stays in the catalog until it is retired (L-XREF-12). Pre-emption in the snapshot: alert sounds off, Message Center pinned in every corpus workspace, What's New acknowledged at snapshot build, WER dialogs suppressed by LocalDumps.

### 7.9 Data modes operationally

Each checkpoint declares `data_mode` as `frozen` or `masked_live`. The mode and its epoch are fingerprint fields (7.4), so a candidate captured on a different epoch from the base is `not_comparable (reason: fingerprint_mismatch)` with `data_epoch` as the differing field (3.2 Data modes, 7.4), never a diff. The base-capture reuse key is `fingerprint_id`, `epoch_id` (4.9), the sha256 of the fixture file and the golden account's latest `seeded_at`; reuse requires all four equal (4.9, 11.2).

Frozen, Branch A (backend fixture, preferred, OPEN, DR-02). The backend team's replayable market-data mode on the test backend serves a named dataset (dataset id, as-of timestamp, symbol list) to the test-backend credential. The dataset id is in the run config. Preflight N4 checks the fixture's health before launch; a failure is `env_error (gate: preflight.N4)` for every frozen checkpoint while masked_live checkpoints proceed. At gate `fixture_verified` the pinned quote check OCRs the fixture symbol's last, bid, ask and quote time in a watchlist and compares them exactly with the dataset; chart checkpoints use the dataset's last bar; option chain checkpoints read the chain header and expiration list against it. Any mismatch is `env_error (gate: fixture_verified, reason: data_epoch_mismatch)` for the frozen checkpoints of the shard. Both halves of a pair point at the same dataset.

Frozen, Branch B (OnDemand). OnDemand replays stored data from a chosen date and time with pause and speed controls and swaps the account to a $100,000 virtual account (verified to exist on the desktop client). Three constraints:

- Entry mode. Community sources relaying TD Ameritrade and Schwab guidance say OnDemand is used from the Live Trading login, not paperMoney, and forum claims say a funded live account is required; whether the test login reaches OnDemand, and from which mode, is unverified. If OnDemand needs Live Trading mode, Branch B is usable only with a test-backend credential that has no live trading entitlement and with the risk owner's written approval, because the paper-mode assertion cannot hold inside OnDemand; the allowlist then gains the OnDemand virtual account id as an entry valid only while the OnDemand toolbar is visible by template, and that id shown without the toolbar is `aborted_safety`. Otherwise Branch B is off: frozen checkpoints fall back to masked_live with a larger rule set, and chart checkpoints use daily aggregation with a fixed lookback and numeric assertions (an explicit start and end date range is unverified, and intraday history is capped at roughly 30 to 45 days of 1-minute bars).
- Pausing. OnDemand advances in real time once started, so the run pauses at the pinned timestamp before capturing: open OnDemand, set the checked-in timestamp, Go, wait for buffering under the 90 s hard timeout (POP-12), Pause, OCR the OnDemand clock and assert it equals the timestamp (mismatch is `env_error (gate: fixture_verified, reason: data_epoch_mismatch)`), park the mouse, settle, capture. The timestamp is the epoch.
- Stability and coverage. OnDemand is memory heavy and stalls in prebuffering (reported); scans do not work inside it; which gadgets replay is unverified. Phase 0 measures buffering time and failure rate over 20 launches (DR-02 decision rule: at least 18 settle, two paused captures 10 minutes apart pixel-identical outside the clock mask) and lists the gadgets that replay; checkpoints on gadgets that do not are `not_run (reason: scope)` while inside OnDemand. Three consecutive buffering timeouts in one shard abandon OnDemand for the run: the remaining OnDemand checkpoints are `env_error (gate: fixture_verified, reason: ondemand_timeout)` and the on-call channel gets one message. The OnDemand cell has its own heap in a vmoptions variant, hence its own snapshot and fingerprint, and OnDemand account panels have their own baselines.

Masked_live. paperMoney data is delayed 20 minutes by default (verified); real time on a login linked to a funded account is community-reported. The delayed or real-time state is a fixture value (`epoch.data_delay`) read from the delayed-data badge and recorded in the epoch; a change is `env_error (gate: fixture_verified, reason: delay_state)`, not a diff. Region semantics belong to 3.8 Region Registry semantics; operationally, `freeze` regions are pinned by the fixture (fixed chart lookback and strike count, expirations by relative rule, continuous futures symbols with the roll date in the epoch, no positions in the empty account, no news or ticker gadgets in corpus workspaces), `rule` regions use the delay tolerance of 2.8.2 (the displayed value is compared with the API point value as of capture time minus the delay, 20 minutes by default, within 1 tick), and `mask` covers only the clock and connection indicator. Because a setting that turns off quote flashing could not be verified, Capture takes 3 to 5 frames over 1 to 2 seconds at masked_live checkpoints; the settle rule already requires the frames to be identical outside masks, so the per-pixel median the Diff Engine takes equals the settled frame there and changes nothing it compares (3.5), and the extra frames exist so a quote flash is recorded under its mask, never diffed. masked_live checkpoints run in lockstep on two rigs or are `not_run (reason: budget)` (7.4).

Epoch and churn. The epoch record (7.4) is completed by a churn calendar (option expirations, futures rolls, exchange holidays, earnings and ex-dividend dates for fixture symbols; `churn_calendar` in 4.9 Fixture) generated from the exchange calendar library and the market-data API; an epoch change on a frozen region triggers re-approval of the affected baselines (9.8 Baseline lifecycle), not scored diffs. The symbol fixture pre-check at gate `fixture_verified` queries the API per fixture symbol (exists, no split or symbol change since the last run, expected expiration shape); when preflight N3 failed, the pre-check reads the app's own quote by OCR instead and run health says "symbol pre-check: app quote only". A failed pre-check is `env_error (gate: fixture_verified, reason: fixture_maintenance_needed)` for checkpoints using that symbol, posted to the flow owner and the accounts owner.

### 7.10 Quiet windows from the exchange calendar

Most checkpoints need no quiet window: frozen ones are deterministic by construction and masked_live ones are handled by the Region Registry. Three things still do: calibration runs on masked_live checkpoints, masked_live checkpoints that assert values which settle only after a session closes (previous close, day volume), and the chaos suite. Each declares `requires_window` (4.7 flow header, overridable per checkpoint: `none`, the default, `all_quiet`, `equities_quiet` or `futures_break`) and the Orchestrator schedules it from the exchange calendar, never from wall-clock cron. PR, merge and RC runs happen inside the operating day, 06:00 to 22:00 America/New_York (11.1 Planning assumptions, A12); one that would start outside it waits until 06:00. Nightly and Calibration runs are exempt: the Nightly run starts at 22:00 (11.2) and Calibration runs use the weekend `all_quiet` window (7.13).

Why wall-clock rules are wrong (America/New_York throughout):

- Schwab's 24/5 overnight session covers 1,100 or more securities as of July 2025 (S&P 500 and Nasdaq-100 stocks and hundreds of ETFs), quotes moving Sunday 20:00 to Friday 20:00 (consistent across sources, not confirmed verbatim). The list changes, so it is re-read each run from the Public > 24 Hour Trading watchlist and its hash stored as the fingerprint's record field `trading_24h_list_sha256` (7.4), outside the epoch.
- Extended-hours order sessions are reported as 7:00 to 9:25 and 16:05 to 20:00, not 4:00 and 16:00; verify against Schwab's current page before coding windows.
- CME Globex equity index futures: Sunday 18:00 to Friday 17:00 with a daily 17:00 to 18:00 break. Forex: 24/5, Sunday 17:00 to Friday 17:00.
- CME crypto futures and options: 24/7 since June 2026 with only a Saturday 2:00 to 4:00 CT maintenance break, so /BTC and /MBT have no quiet window; they get an always-live profile with `rule` regions and no pixel-diffed quote cell.
- NYSE holidays, 13:00 early closes and DST weekends differ between XNYS and CMES. The two DST transition weekends are calibration-check days: the Nightly run that follows each re-runs the time-axis label check of 7.1.
- Weekend backend maintenance is anecdotal (Saturday-night reports, one Friday-to-Saturday outage), not a schedule; the preflight detects it (7.11), the clock never assumes it.

Implementation: exchange_calendars (XNYS, CMES) or pandas_market_calendars, vendored and pinned in the harness so no network call is needed; tz-aware America/New_York datetimes; the OS is in the same zone, so no offset arithmetic exists in the scheduler. Preflight G4 resolves the sessions of every fixture symbol for the run date plus 90 days; a library import failure, a missing calendar or a data horizon shorter than that is `env_error (gate: preflight.G4)` for every scheduled checkpoint, because the churn calendar and the epoch depend on it, not only the windowed checkpoints. Named windows live in `schedule/windows.yaml` (4.1, schema in 4.16):

```yaml
operating_day: {start: "06:00", end: "22:00"}    # America/New_York; PR, merge and RC runs only (Nightly and Calibration exempt)
windows:
  all_quiet:        # equities, futures, forex closed; crypto futures excluded by profile
    start: {calendar: XNYS, weekday: Fri, time: "20:00"}
    end:   {weekday: Sun, time: "17:00"}   # forex 17:00, Globex 18:00, 24/5 equities 20:00
  equities_quiet:   # only for symbols absent from the 24-hour list read this run (7.4)
    rule: "XNYS closed and symbol not in overnight list"
  futures_break:
    rule: "CMES daily break 17:00 to 18:00, or CMES weekend close"
  none: {}          # default for frozen and masked_live checkpoints
maintenance_windows:  # known backend windows; a preflight N1, N3 or N4 failure inside one reschedules instead of env_error
  - {weekday: Sat, start: "22:00", end: "02:00", source: "ops calendar 2026-10"}
```

The scheduler reads p95 flow durations from SQLite and refuses to start a windowed flow that cannot finish before the window ends or, in a PR, merge or RC run, before the operating day ends; the refusal is `not_run (reason: budget)` and shows in the coverage matrix. A windowed flow that straddles a window edge because its p95 was wrong is `not_settled (reason: timeout)` at the first checkpoint whose rule fails, never silently kept. Order safety does not depend on any window (6.6 Kill switch, recovery and post-run proof, 6.7 Send policy: both branches): staged tickets are cancelled by each flow's teardown and by the end-of-run Cancel All regardless of the clock.

Post-login connectivity check, part of gate `fixture_verified` (10.8 Self-tests at run start, check 13): the status-bar connection indicator is not Disconnected and no reconnect loop appears in the client log slice since launch; the pinned quote is fresh relative to the login's entitlement (within the delay window plus 60 seconds for delayed data, within 5 seconds for real time); the delayed-data badge equals the epoch. Failure is `env_error (gate: connectivity, reason: backend_degraded)` for the shard; failures across rigs on one night post once as a maintenance event and feed the maintenance calendar.

Mid-run network loss follows 10.7: the anti-anchors Disconnected and Reconnecting stop capture, the Orchestrator pauses up to 5 minutes polling connectivity, re-verifies `fixture_verified` and resumes; past 15 minutes the shard's remaining checkpoints are `env_error (gate: connectivity)` and the run ends `complete_with_env_errors`. A rig that stops answering the Rig Manager heartbeat for 3 minutes (a reboot, a hypervisor fault) is a lost rig: the shard is re-queued to a rig of the same fingerprint class if the budget allows, else its checkpoints are `env_error (gate: rig_lost)`.

Chaos suite: RC runs, tier 2 flows owned by the connectivity flow owner, never in a session with census checkpoints, and `requires_window: all_quiet` because the assertions read quote staleness. clumsy over WinDivert shapes traffic by IP and port, not by process, so the controller runs inside the VM and the control channel addresses are excluded by rule; a Windows Firewall outbound block rule on the launcher executable gives the hard disconnect; an elevated helper service applies and removes rules because the harness runs as a standard user. Scenarios: 500 ms added latency, 5 percent loss, 256 kbit/s throttle, 30 second and 5 minute disconnects, reconnect after each. Assertions by Oracle and template: the connection indicator changes within the declared time; quote timestamps stop advancing and quotes are badged stale rather than silently frozen; a symbol change or chain load during the disconnect shows an explicit error state, not an empty grid; after reconnect quotes resume, Monitor and Working Orders reload without duplicate rows and no POP-10 appeared. There is no assertion about cancelling a staged order during the disconnect: a staged order exists only client-side and sending is forbidden, so nothing exists server-side to cancel. Each scenario ends with the rule removed and verified gone (a rule still present is `harness_error (reason: chaos_rule_stuck)` and the helper service removes all rules), a connectivity check and `verify_account_fixture`.

### 7.13 What invalidates calibration

Calibration (per checkpoint, five captures of the same build back to back on one rig plus one more on a second night; each checkpoint keeps to one rig while the library is sharded across the pool over a weekend `all_quiet` window, 7.10; procedure in 3.9 A/A calibration and threshold derivation) produces per-checkpoint, per-region noise floors tied to a rendering key, not to the whole `fingerprint_id`. The rendering key is the sha256 over the canonical JSON of the match fields that can change pixels: `windows_build`, `display` (DPI included), `cleartype`, `gpu`, `os_theme`, `app_theme` (scheme and font size), `jre_release`, `vmoptions_hash`, `java2d_pipeline`, `render_probe_hash`, and the capture library, settle parameters and Diff Engine parameters hashes of `harness`. It leaves out `build_id`, `data_epoch`, `workspace_hash` and the other match fields; the rows below scope their changes to a checkpoint or a region instead of to every floor. A floor is valid for a capture whose rendering key equals the floor's and whose checkpoint and region no row below has invalidated (each `calibration_floors` row records the hashes those rows compare, 8.3). A checkpoint or region with no valid floor is still diffed, at threshold zero: an identical region is `identical`, any changed region is `needs_human (reason: uncalibrated)` (4.12 Environment fingerprint, rule L-FPR-04), the Reporter shows the count and the Calibration Service queues the run (5.15 Canary Service and Calibration Service). This is never silent and never a tolerance: zero is the threshold until a floor exists.

| Change | Scope of invalidation | Detected by |
|---|---|---|
| New base-os generation (Windows Update, driver, hypervisor, hardening) | All checkpoints on the rig | Rig Manager at snapshot creation; `windows_build` and `gpu` in the rendering key |
| ClearType, display, DPI, OS or app theme, font size | All | Rendering key differs at run start |
| thinkorswim.vmoptions (pipeline, heap, anti-aliasing flags) | All | vmoptions hash (B3), in the rendering key |
| JRE (release file) or `render_probe_hash` | All, with a carry-over: the floors of the rendering key that differs from the new one only in `jre_release` or `render_probe_hash` carry over to the new key once the Nightly A/A drift check on the new main build passes (10.6 A/A drift on the Nightly run); until then its checkpoints run at threshold zero; more than 2 percent of checkpoints above floor, or the global-shift pre-pass, is `harness_error (reason: aa_drift_global)` and schedules a full calibration before any threshold is used | jre_release and render_probe_hash in the rendering key, plus the A/A drift check |
| Build alone | None by default (`build_id` is not in the rendering key) | The nightly A/A drift check decides, as above |
| Workspace Corpus file | Checkpoints in that workspace | The floor row's workspace hash against `workspace_hash` for that corpus id |
| Region Registry landmark or region, mask, crop, redaction version | That region | The floor row's regions file hash, mask versions and redaction version against the current ones |
| Settle rule parameters, capture library version, Diff Engine parameters | All | `harness` hashes in the rendering key |
| OCR engine or model version | Oracle tolerances and invariant floors, not pixel floors | Harness fingerprint field, outside the rendering key |
| Data mode or epoch definition for a checkpoint | That checkpoint | The floor row's epoch definition hash against the checkpoint declaration; `data_epoch` itself is outside the rendering key |
| Physical D3D rig added, a display configuration added, or a rig moved to another host type | That rig or configuration | Fingerprint gpu, display and rig fields |
| Golden re-seed or fixture file change | Golden `account_state` checkpoints: rule tolerances re-derived, no pixel floor change | Fixture file hash and `seeded_at` |

Time zone, keyboard layout and locale are outside the rendering key: they are pinned and read by R4 (7.1), so a different value ends in `env_error (gate: preflight.R4)` before any capture and no floor is ever used under it.

A non-zero floor on a frozen checkpoint after recalibration is a flow or environment bug with a fix list (brief 1.11, unknown 5, Branch B; DR-05 in 11.8), never a tolerance to raise.
