## 5. Architecture and components

This section gives, for every component in brief 1.6, its responsibility, inputs, outputs, failure outcomes and key internals. Outcome names are the closed set of 1.10 Outcome taxonomy (authoritative), held as enums in `taxonomy.yaml` (4.1 Conventions, repository layout and the lint); when several results apply to one checkpoint, the precedence rule of 1.10 decides the single outcome it keeps. A "finding" is a record attached to a checkpoint or run that is not itself an outcome (`locator_failure`, `unknown_popup`, `dependency_map_gap`, `app_crash`, and so on; kinds in 8.3 Schema): findings are reported, outcomes are counted. A "step event" is an audit row (8.3 `step_events`) and changes nothing by itself. Phase 0 unknowns are named by their decision record in 11.8 Phase 0 spike plan (DR-01 JAB exposure, DR-02 data fixture, DR-03 login and MFA, DR-04 pinned install, DR-05 A/A floor, DR-06 session rule, DR-07 computer use), each with Branch A and Branch B.

Process layout decisions:

- Three harness processes run on the rig: the Orchestrator (one process, several threads), the Gateway hook host (its own process so the hook callback never competes for the Orchestrator's interpreter lock or waits on OCR), and the Watchdog (its own process so it survives an Orchestrator crash). The thinkorswim tree is the fourth. 10.2 Watchdog and 7.12 Windows hardening checklist name the same three.
- Whatever needs the hypervisor runs on the control host in the Rig Manager; whatever needs the rig's desktop (input, capture, window enumeration) runs on the rig.
- Every harness process that touches the screen or input (Orchestrator, hook host, Watchdog, preflight, Recorder) declares `PER_MONITOR_AWARE_V2` before importing any screen or input library and logs `GetProcessDpiAwareness` at start; any other value ends the run `aborted_harness (reason: dpi_awareness)` before any capture, with every scoped checkpoint `harness_error (reason: dpi_awareness)` (the run's abort reason), as 3.4 Capture rules and 5.18 state. Coordinates everywhere in this section are physical pixels.
- The rig has a Run Store (SQLite WAL on local disk plus the `results.jsonl` ledger of 8.1, written only by the Orchestrator) and an artifact folder. Rows and redacted artifacts ship to the control host through the idempotent `POST /v1/runs/{run_id}/results` and `PUT /v1/artifacts/{sha256}` of 8.2 Single-writer rule as each checkpoint completes, and the run row closes at `reported`. The Central Store's only writer is one thread in the Reporter service on the control host (5.13), which also owns the local API that the report UI and the one-click actions call; the Watchdog writes neither store (it writes a JSONL journal the Orchestrator ingests, 5.14). 8. Storage and data model holds the DDL; this section fixes the writer rule and the hand-off points.
- Rig fleet and scheduling follow 11.1 Planning assumptions and 11.3 Sharding and parallelism: six rigs and six logins; rigs 1 to 4 are the pool for PR and merge runs, rig 5 runs the Nightly run and the soak, Calibration runs are sharded across the pool (rigs 1 to 4) in one weekend `all_quiet` window while the Nightly canaries and the fire drill stay on rig 5 (1.6), rig 6 is the Explorer rig and the spare; RC runs use all six. Base and candidate scheduling is by data mode: `frozen` checkpoints run base and candidate on the same rig back to back, reusing the base capture when its fingerprint and fixture epoch match the candidate's; `masked_live` checkpoints run on two identically fingerprinted rigs in lockstep (same minute), fingerprint equality asserted before capture; when only one rig is free, `masked_live` checkpoints are `not_run (reason: budget)` rather than captured minutes apart.
- Only the agent loop (when preflight enables it) and the Reviewer drainer talk to the model endpoint, and both send only artifacts that passed the redaction stage (5.7).

### 5.2 Orchestrator

- **Responsibility**: own one run from `provisioned` to `reported`; compute scope; drive flows, census visits and size sweeps through the Executor; assign exactly one outcome to every checkpoint in scope; write the heartbeat; honor budgets and the kill switch.
- **Inputs**: run request (run type, candidate and base build ids, change manifest for PR runs, budget, shard plan), the git checkout at the pinned commit, the rig fingerprint, the preflight result (including whether agent fallback is enabled and the review mode).
- **Outputs**: run record, the scope manifest (every scoped checkpoint id, uploaded on entry to `running`), checkpoint outcomes, step outcomes, step events (every gateway decision, retry, fallback, popup hit, focus correction), captures and extractions to the Stores, the run outcome, hand-off to the Reporter.
- **Failure outcomes**: a gate failure before `running` sets `env_error` (gate name, gate screenshot) on every checkpoint in scope; `paper_mode_asserted` or `settings_attested` failure sets the run `aborted_safety`; budget exhaustion sets remaining checkpoints `not_run (reason: budget)` and the run `aborted_budget` with the budget's reason (`wall_clock` when the run's wall budget less the report margin of 11.2 is reached, `app_restart_budget`, `dollar_cap`, `rate_cap` or `superseded`, 4.13); an unhandled exception or a hang is a Watchdog trigger (5.14): the in-progress checkpoint is `harness_error (reason: orchestrator_died)`, the run resumes at the next flow boundary, and exhaustion of the 2 Orchestrator restarts per shard ends the run `aborted_harness (reason: orchestrator_restart_budget)` with the remaining scoped checkpoints `harness_error (reason: orchestrator_restart_budget)` (unreached checkpoints carry the run's abort reason, 1.10). A checkpoint its flow never reached because an earlier step ended `failed` or `blocked_by_gateway` is `not_run (reason: step_failed:<step>)`; the checkpoint that step led to is `landmark_missing` when the locator failed on every rung, `assertion_failed` when an assertion failed, or `harness_error` with the reason when the gateway itself failed (5.4.4). An app crash or hang during a step is `assertion_failed (assertion: app_alive)` on the checkpoint being captured, `not_run (reason: app_crash)` for the rest of that flow, and a tier-1 `app_crash` finding (5.14); an app error dialog on screen at capture is `invariant_violation` INV-14 (5.9).
- **Key internals**: the state machine below; scope computation (2.11 Scope computation per run type); the shard plan and data-mode scheduling of 5.1; the popup sentinel loop (7.8 Popup catalog policy); targeted re-runs (3.10 Targeted re-run and flake logic, 10.5 Flake tracking); the heartbeat writer (the JSON of 10.2 at `C:\sentinel\run\<shard_id>\heartbeat.json`, the shard directory of 8.4, rewritten atomically at every step start and end, every gate, and at least every 10 s) and the reader of the Watchdog's reverse heartbeat `watchdog.json` at every gate and flow boundary (5.14); the kill-switch poll (file flag every 500 ms plus a named-pipe listener; the Watchdog also watches both, 6.6 Kill switch, recovery and post-run proof); one retry per step, never across a capture; the build id re-read from the window title after every relaunch and before each flow, where a change is `env_error (gate: launched, reason: version_changed_mid_run)` for the rest of the shard (a launcher update the Watchdog finds behind a `process_exit` is the same case, 5.14).

State machine. Every transition is guarded by an anchor check (template match, OCR read or window-title read against a declared expectation); the gate screenshot is stored whether it passes or fails. Preflight item ids are those of 12.7 Preflight checklist (groups R rig, B build, H harness self-test, N network, G gateway and registries).

### 5.3 Rig Manager

- **Responsibility**: deliver a rig in the pinned state with the right build and a recorded fingerprint before the Orchestrator starts; pair rigs for `masked_live` lockstep shards; watch rig liveness.
- **Inputs**: rig id, snapshot id (7.2 Snapshot lifecycle), build artifact id, install branch (DR-04 Branch A pipeline artifact with auto-update disabled, Branch B per-build snapshot, 7.3), pinned display and vmoptions settings, the shard plan.
- **Outputs**: `rig_ready` with the fingerprint record (the fields of 7.4 Environment fingerprint, `render_probe_hash` included; the build id is appended at `launched` from the window title), the preflight report, and for a lockstep pair the fingerprint-equality assertion.
- **Failure outcomes**: a failed R, B, N or G preflight item (ids from 12.7) records every scoped checkpoint as `env_error (gate: preflight.<item>)` and the run ends `complete_with_env_errors`; a failed H item (H1 input injection, H2 global hook, H3 capture, H4 gateway deny self-test, H5 kill-switch channel, H6 redaction, H7 stores, H8 watchdog, H9 OCR calibration, H10 crash plumbing) ends the run `aborted_harness (reason: preflight.<item>)` naming the item, before any product action; a G5 fingerprint pre-match failure makes every checkpoint `not_comparable (reason: fingerprint_mismatch)`; a lockstep pair whose fingerprints differ at capture time makes that shard's `masked_live` checkpoints `not_comparable (reason: fingerprint_mismatch)`; three minutes without a rig heartbeat is a lost rig, and the shard is re-queued to a rig of the same fingerprint class if the budget allows, else its checkpoints are `env_error (gate: rig_lost)` (10.7 Degraded modes). The spare is rig 6: it replaces a failed pool rig only by being re-snapshotted with the failed rig's login, because a login is never live on two rigs; the operator who did it is recorded in run health, and while rig 6 serves the pool no Explorer session runs (11.2).
- **Key internals**: hypervisor API client; DR-04 Branch A silent install from the artifact, auto-update setting written, vmoptions re-applied and verified by hash, or Branch B snapshot selection by build id; an in-VM preflight that asserts the console session (`OpenInputDesktop` name `Default`, autologon, no RDP session: R6), pins the display with `ChangeDisplaySettingsEx` and asserts `GetDpiForSystem() == 96` and `GetSystemMetrics(SM_CXSCREEN, SM_CYSCREEN) == (1920, 1080)` from a Per-Monitor-V2 aware process (R2), checks ClearType (R3), time zone, keyboard layout and toggle keys (R4: America/New_York, en-US, NumLock on, CapsLock off), rejects a uniform probe screenshot (H3), checks disk and clock (R7), and runs the network items (N1 login host; N2 model endpoint, `GET /v1/models/{pinned id}` plus a one-token message, whose failure sets `review_mode: deferred` and agent fallback off for the run so scripted failures end `failed`, never as a silent fallback; N3 market-data API; N4 data fixture; N5 a 2 MB POST to the approved model host, whose failure names the blocking control and sets the same degraded mode as N2, never `env_error` (review deferred, agent fallback and the Explorer disabled, the run continues; 7.11, 10.7); N6 the vault reachable and the rig's secret references resolving, values never read; N7 the PR host API and the artifact store reachable, whose failure lets the run proceed and publication retry under the dead-man deadline). The H items exercise the harness's own permissions once: a tokened click into a scratch window, a hook install, one received event and removal with callback latency under 20 ms, plus a check by psutil that no Recorder process is present on the rig (5.16), a capture with DWM bounds, the gateway deny self-test (set `flag_ticket`, inject Enter and an untokened click, expect two logged drops), both kill-switch channels, redaction of a synthetic account id, the single-writer store lock, the Watchdog heartbeat, and the crash plumbing (H10: the vmoptions hash carries the crash flags, the ErrorFile and heap-dump folders are writable, the WER LocalDumps key is present); a control that blocks any of them (EDR, AppLocker, DLP) is named in the `aborted_harness` reason (11.7 Prerequisites checklist). A rig heartbeat goes to the control host every 30 s.

### 5.4 Executor and the Input Gateway

- **Responsibility**: turn a flow step, an agent tool call or an Explorer tool call into OS input events, and make sure no other code path can.
- **Inputs**: step records with the types of 4.7 Flow file (`click_named`, `dblclick`, `rclick`, `drag`, `wheel`, `press`, `key_chord`, `type_fixture`, `secret`, `reset_input_state`, `wait_for`, `export`, `copy_grid`, plus the Capture-internal `park_mouse` and `focus_neutral`), the Window Watcher's window list, the fixture's typed values, the locator definitions stored with the flow and the Surface Registry's control entries, the deny profile (`scripted`, `agent`, `explorer`), `policy/send_policy.yaml`.
- **Outputs**: step outcomes (`passed`, `passed_after_retry`, `passed_via_agent_fallback`, `failed`, `blocked_by_gateway`), step events (one per emitted and per dropped event, with a 96x96 crop around every click point taken at action time), `locator_failure` findings, `gateway_integrity` findings.
- **Failure outcomes**: a step whose event the gateway refused or dropped is `blocked_by_gateway`; the flow ends and is `not_run (reason: quarantine)` on later runs until a human reviews it (1.10). A step whose ladder is exhausted is `failed`, the checkpoint it led to is `landmark_missing`, and the flow's later checkpoints are `not_run (reason: step_failed:<step>)`. A step whose emitted event never reached the hook is `failed` after its single retry, the checkpoint it led to is `harness_error (reason: hook_lost)`, and the run gets a `gateway_integrity` finding and an on-call alert. A step that meets an unexpected modal is `failed` with an `unknown_popup` finding and the popup sentinel takes over. Drops and refusals split by reason (5.4.4, 5.4.8). A safety-reason drop or refusal (a blocked key or a click on a deny rectangle while `order_stage` is set, a never-tokenize hit) is an attempted send: on a scripted flow, including an agent rescue inside it, one is enough to end the run `aborted_safety (reason: attempted_send)`, quarantine the flow and page on-call at P1; in an Explorer session it ends the session and counts toward the per-run trip. An integrity-reason drop (token mismatch, expired token, stale state) gets one retry; three in one flow or agent session end it `failed` and quarantine the flow; ten in one run trip the kill switch (run `aborted_safety (reason: kill_switch)`). A click requested on a label inside an order dialog that is neither allowlisted nor send-like is `aborted_safety (reason: unknown_dialog_in_order_stage)` when `order_stage` is set, else the flow is quarantined and the window is an `unknown_popup` finding. The nightly fire drill flow class is exempt from these counts (6.5).
- **Key internals**: the two halves below, the shared arm/deny state, the ticket-or-dialog flag, the locator ladder (5.5), the agent toolset (5.6).

#### 5.4.1 Single entry point

`gateway.emit(action)` is the only function in the codebase that calls `SendInput`; it wraps `pywinauto.mouse` and `pywinauto.keyboard` for event construction. Two enforcement layers:

1. Structural: a CI lint fails the build if any module outside `harness/gateway/` imports `pywinauto.mouse`, `pywinauto.keyboard`, `pyautogui`, `pynput`, `pydirectinput`, or references `SendInput`, `keybd_event` or `mouse_event` through ctypes. The agent loop and the Explorer loop are ordinary modules under this rule. The one exception is the fire drill injector, a separate signed executable under `harness/gateway/drill/`, allowlisted by path and by code-signing hash; its declared raw-injection phase is tagged `drill` by the drop-log drainer and matched against the drill's expected set instead of raising `gateway_integrity` (6.5).
2. Runtime: the fast half drops every input event that carries no token issued by the slow half (5.4.5). A direct `SendInput` from anywhere else is dropped and logged `untokened_injected`, which raises a `gateway_integrity` finding and an on-call alert. Console input from a human is dropped and logged `foreign_input`, with the same finding and alert; the operator's route to a running rig is the kill switch (6.6), after which the hook host exits and the console is free.

#### 5.4.2 Process layout and shared state

The slow half lives in the Orchestrator process as four threads: resolver (locator ladder), emitter (tokens plus `SendInput`), Window Watcher (enumeration and ticket detection), drop-log drainer. The fast half is the gateway hook host: a separate Python 3.12 process importing only `ctypes`, `mmap` and the standard library, which installs the two hooks on one thread running a `GetMessage` loop and does nothing else. It declares `PER_MONITOR_AWARE_V2` as its first statement so hook coordinates match the slow half's physical pixels.

The halves share one memory-mapped segment:

```
header       : magic, layout_version, seq (seqlock), armed, deny_all,
               flag_ticket (0 clear, 1 set, 2 unknown), watcher_mono_ts,
               orchestrator_pid, hook_host_pid, last_probe_mono_ts, hook_alive_mono_ts
tokens[16]   : id, kind, button_or_vk, x, y, tol_px, expires_mono_ts,
               flags (dialog_ok, secret, release, send_ok: gated branch only),
               state (armed, half_consumed,
               consumed, dropped, expired)
move_allow   : active, until_mono_ts, bbox
deny_rects[8]: inflated bounds of send-like controls currently visible
blocked_vk   : 256-bit map plus 16 chord entries (mods, vk)
drop_ring    : 4096 x 32-byte records: seq, mono_ts, event_type,
               vk_or_button, x, y, injected_flag, reason_code, token_id
```

The slow half writes everything except token `state`, `last_probe_mono_ts`, `hook_alive_mono_ts` and the ring, which only the hook writes. Writes use a seqlock (increment `seq` to odd, write, increment to even; the hook rereads on mismatch). The callback never takes a lock another process can hold, never allocates beyond the ring, never does I/O.

Staleness rules, so neither half ever acts on an old picture of the screen:

- The Window Watcher stamps `watcher_mono_ts` on every poll. The hook treats a stamp older than 500 ms as `flag_ticket = unknown`, which it handles as set (5.4.6). The slow half never tokenizes from the Watcher's cached list while the flag is set or unknown: stage 4 of 5.4.3 performs its own synchronous enumeration first.
- Tokens expire on monotonic time, so a stalled emitter cannot leave a live token behind (5.4.5). `deny_rects` and `blocked_vk` are rewritten on every Watcher poll and at `settings_attested`; between polls the inflation margin of 12 px covers control movement, and a dialog appearing between polls is covered by the flag's `unknown` handling and the synchronous re-check.
- A `magic` or `layout_version` mismatch (the two halves built from different harness commits) makes the hook host set `deny_all` and exit with a distinct code; the slow half sees the dead hook host (below) and the run ends `aborted_harness (reason: hook_lost)` without a relaunch, since a relaunch would reproduce it.

Fail-closed rules:

- The hook host polls `orchestrator_pid` every 500 ms, switches to `deny_all` if the process is gone, and exits once the Watchdog has killed the thinkorswim tree (the Watchdog signals it through a named event; it also exits on its own after 60 s in `deny_all` with no Orchestrator, so a stale hook host never outlives a run).
- The hook host stamps `hook_alive_mono_ts` every 250 ms from its message loop. Before every emission the slow half checks that `hook_host_pid` is alive and the stamp is under 1 s old; otherwise it emits nothing, the step is `blocked_by_gateway` with reason `hook_host_dead`, the checkpoint the step led to is `harness_error (reason: hook_lost)`, the flow's later checkpoints are `not_run (reason: step_failed:<step>)`, and the Orchestrator asks the Watchdog to kill the thinkorswim tree and restart the hook host, because a run without the hook has no safety layer. The run then re-enters the state machine at `launched` and resumes at the next flow boundary. A hook-host restart has its own budget of one per shard and does not consume one of the 3 app relaunches (5.14); the second hook-host restart in one shard ends the run `aborted_harness (reason: hook_lost)`. The run never continues with the app alive and the hook dead.
- Hook removal by Windows (callback over the hook timeout) is detected by the probe of 5.4.4 and handled the same way, with a reinstall attempt first.

#### 5.4.3 Slow half: before an event is emitted

The emitter runs this pipeline for every action and records each stage as a step event:

1. Foreground: `GetForegroundWindow` must belong to the process tree; otherwise one pywinauto `set_focus()` on the target window (it implements `AttachThreadInput` plus `SetForegroundWindow`), re-check, and fail the step with reason `foreground_lost` if it still fails. Each correction is a `focus_correction` event; a rising count is a popup-sentinel signal, and a foreign foreground process is also a `foreign_window` event for the hardening finding of 7.8.
2. Modal: `IsWindowEnabled(main_hwnd)` false means a modal owns the frame. If the step targets that dialog by title regex, continue; otherwise the popup sentinel handles it (catalog match: dismiss, wait or abort per the entry; no match: agent with the dismiss-only toolset when enabled, else `WM_CLOSE`, and an `unknown_popup` finding either way, 7.8) and the step fails.
3. Resolution: the locator ladder (5.5) yields physical screen coordinates and the resolved control name; for key actions, the key is checked against the step's declaration. The slow half also OCRs the 96x96 crop under the click point, so the label under the pointer is known even when the resolver used an offset from an anchor.
4. Safety, in this order, each a refusal that ends the step `blocked_by_gateway` before anything reaches the hook:
   - Never-tokenize: the resolved name or the under-point OCR text matches the never-tokenize regex `/^(send|auto send|flatten|blast all|replace|submit)$/i` or any label matching `/send|submit|replace|flatten|blast|auto/i` outside the Order Confirmation dialog. `Confirm and Send` is not on this list: it opens the dialog and is clickable only from a scripted step (never profile `agent` or `explorer`) in a flow with `order_stage: true` and only after attestation passed this session. Under the OPEN gated branch of 6.7 Send policy, the single-use send token that branch defines carries `send_ok`, which lifts the dialog allowlist in the slow half and the Send deny rectangle in the hook for exactly one button down; with `policy/send_policy.yaml` disabled the slow half never sets `send_ok`, so no such token exists.
   - Dialog allowlist: while an order dialog (the Order Confirmation dialog or any order dialog of the popup catalog) is in front, the only clickable controls are those whose resolved and under-point labels are both exactly in the pinned dismiss allowlist (expected `Delete` and `Edit`; pinned in Phase 0, 6.2 Never-send guard). Any other click in the dialog is refused. `dialog_ok` is the slow half's statement that this check ran synchronously: it is set on a click token only after the flag re-check below, when either no order dialog is present and the point lies outside every deny rectangle, or the dialog is present and the click is on an allowlisted label. The hook requires it on every button down while `flag_ticket` is set or unknown (5.4.4), so a click tokened from a stale picture of the screen is dropped.
   - Deny profile: under `explorer`, the deny list of 6.8 Explorer boundary and deny list (window titles, labels, landmark-anchored geometry); under `agent`, the same list in full, since a locator rescue never needs a denied surface. Under `explorer`, `drag_named` resolves only splitters and detach handles; a drag whose start point is an order bubble on a chart or an order cell on the ladder is an order path and is refused (5.4.10, 6.8).
   - Flag re-check: if `flag_ticket` is set or unknown, the flag is re-read from a fresh synchronous enumeration and ticket-detector pass (not the 100 ms poll); guarded keys are refused, and the click point must lie outside every deny rectangle inflated by 12 px.
   A refusal whose cause is an attempted send (never-tokenize hit, a non-allowlisted click inside the dialog whose under-point label matches the send regex or lies in a deny rectangle, a guarded key requested while the flag is set) ends the flow or agent session and, on a scripted flow, ends the run `aborted_safety` through `teardown` (a flow that asks for Send is a flow bug or a violation attempt and is reviewed as an incident, 6.12). A click requested on a label inside an order dialog that is neither in the dismiss allowlist nor send-like is an unknown dialog label: with `order_stage` set the run ends `aborted_safety (reason: unknown_dialog_in_order_stage)`, because a dialog the flow cannot name while an order is staged is not a screen the harness may act on; otherwise the flow is quarantined and the window is an `unknown_popup` finding (7.8). A refusal with any other cause (deny profile, ambiguous name) ends the flow or session, counts toward the three-per-flow and ten-per-run thresholds of 5.4.8, and is reviewed as a flow bug.
5. Token write: one token per OS event (a click is `mouse_down` plus `mouse_up`; a drag is `mouse_down`, a `move_allow` window over the path bounding box, `mouse_up`; one `wheel` token per notch; a key is `key_down` plus `key_up`). Tolerance 2 px; expiry 500 ms, drags `hold_ms + 1000`.
6. Emission: hook-host liveness check (5.4.2), then `SendInput` with an absolute move first, then the button or key events. Drags interpolate at least 10 moves over `hold_ms` (a single jump does not start a Swing drag gesture). Typing is one key pair per character from the fixture value or the flow literal; no typing action accepts text from a model.
7. Consumption: wait up to 200 ms for every token to reach `consumed`. A token in state `dropped` carries the hook's reason code; a safety reason (5.4.4) makes the step `blocked_by_gateway` and the consequences of stage 4 apply by reason. An integrity reason (`token_expired` or `token_mismatch_coords` on the gateway's own event, or a token that expired unconsumed, meaning the event never reached the hook: `SendInput` refused, hook removed, endpoint control interfering) is a harness fault: the probe of 5.4.4 runs at once; if the hook answers, the step's single retry re-resolves, re-tokenizes and re-emits (success is `passed_after_retry` with a `gateway_integrity` finding); if the hook does not answer or the retry drops again, the step is `blocked_by_gateway` with the reason, the checkpoint it led to is `harness_error (reason: hook_lost)`, and the fail-closed sequence of 5.4.2 runs. Integrity drops count toward the three-per-flow and ten-per-run thresholds of 5.4.8 after the retry; they never end the run `aborted_safety` on their own, because nothing reached the app.
8. Post-condition: the step's declared effect (anchor appears, title changes, field text changes) is evaluated by the settle logic within the step timeout; failure is `failed` with reason `postcondition`.

Stage 3 takes up to hundreds of milliseconds (OCR, template search). Nothing in stages 1 to 5 touches the hook, so the callback never waits on them.

#### 5.4.4 Fast half: the hooks

The hook host installs `SetWindowsHookEx(WH_MOUSE_LL, ...)` and `SetWindowsHookEx(WH_KEYBOARD_LL, ...)` from a message-loop thread at one priority step above normal. Windows applies a timeout to low-level hook callbacks and silently removes a hook whose callback repeatedly exceeds it, after which events flow unfiltered. The callback therefore returns in well under one millisecond: read the seqlock state, classify, decide, write at most one ring record, return `CallNextHookEx` (allow) or nonzero (drop). Both hooks see injected events (`LLKHF_INJECTED`, `LLMHF_INJECTED` are set on the gateway's own events) and console input alike.

| Event | Allowed when | Otherwise dropped with reason | 6.2 rule |
|---|---|---|---|
| Any | `deny_all` clear and `armed` set | `deny_all`, `not_armed` | 1 |
| Mouse move | `move_allow.active` and inside its bbox, or `armed` with no token pending | `move_outside_allow` | 3 |
| Button down | A token with the same button, abs(dx) and abs(dy) <= tol_px, unexpired, state `armed`; the point outside every `deny_rects` entry (a `send_ok` token, gated branch only, passes the Send rectangle once); if `flag_ticket != 0`, the token has `dialog_ok` and Shift is not held | `no_token`, `token_mismatch_coords`, `token_expired`, `deny_rect`, `shift_click_dialog`, `dialog_not_ok` | 3, 2 |
| Button up | Matching token in state `half_consumed`, expired or not (a release never activates a Swing control whose press it did not receive, and dropping it would leave a button logically held) | `no_token` | 3 |
| Wheel | A `wheel` token at the point with matching delta sign | `no_token`, `token_mismatch_coords` | 3 |
| Key down | A `key_down` token with the same vk, unexpired; if `flag_ticket != 0`, the vk not in `blocked_vk` and the live chord not in the chord list | `no_token`, `token_expired`, `blocked_key_dialog`, `blocked_chord_dialog` | 3, 2 |
| Key up | Matching `key_down` token in state `half_consumed`, expired or not; or a `release` token from `reset_input_state` | `no_token` | 3 |
| Hardware (not injected) input | Never during a run | `foreign_input` | 4 |

Reason codes split into safety reasons (`deny_all`, `not_armed`, `deny_rect`, `shift_click_dialog`, `dialog_not_ok`, `blocked_key_dialog`, `blocked_chord_dialog`, `foreign_input`, and `no_token` on an event the slow half did not issue, including `untokened_injected`) and integrity reasons (`token_expired`, `token_mismatch_coords`, `move_outside_allow`, and `no_token` on an event the slow half believes it tokened). Each code is stored verbatim as the `gate_reason` of its 8.3 `step_events` row, with `gate_decision` `dropped` (hook) or `refused` (slow half), `emitted` for an allowed event and `late_up` for a release accepted after expiry, and the class (`safety` or `integrity`) in `gate_class`; this is the `gateway_event` of 4.13's step outcome record, so the audit trail of 6.2 carries the code, not a coarse class.

Every drop writes a ring record, which the drainer turns into a `gateway_drop` step event; every consumed token writes a compact record so the audit trail (6.10, 8.3) also has the allowed events.

Hook liveness: the slow half emits a tokened probe move to the parking coordinate every 5 s while idle and before every step batch, then reads `last_probe_mono_ts`. A probe the hook did not see within 100 ms means the hook was removed (Windows timeout, an endpoint control, or a hook host fault). The hook host reinstalls both hooks once and logs `hook_reinstalled`, the run gets a `gateway_integrity` finding and an on-call alert, and the next probe must succeed; a failed reinstall or a second removal in one shard is a dead hook host and follows the fail-closed sequence of 5.4.2 (kill the tree, restart the hook host, relaunch; the second restart in a shard ends the run `aborted_harness (reason: hook_lost)`). Preflight H2 requires callback latency under 20 ms on the rig; Phase 0 adds a ten-minute soak with OCR and template search at full load, and if callback latency at p99.9 exceeds 1 ms the hook host is rewritten as a small native executable with the same shared-memory contract (5.19).

#### 5.4.5 One-shot click tokens

A token authorizes one OS event at an expected place within an expiry. Coordinates are physical screen pixels from the slow half's resolution, compared at a 2 px tolerance (`SendInput` rounding on absolute moves). A control that moves between resolution and emission cannot redirect a click: the click lands where the token said and the post-condition fails instead. A token is `half_consumed` on button down (or key down) and `consumed` on the matching up, so a second down on it is dropped. Expiry is monotonic time, so a stalled emitter cannot leave a live token behind.

Expiry mid-click: a token whose down was consumed accepts its up after expiry (table above), so the app never sees a press without a release; the record is marked `late_up` and the step event carries the delay. A token whose down arrives after expiry is dropped `token_expired` and handled as an integrity drop (5.4.3 stage 7). A `half_consumed` token with no up after 2 s makes the slow half emit `reset_input_state`, whose `release` tokens are allowed at any coordinate because a release alone activates nothing. For a drag, `move_allow` expires at `hold_ms + 1000`; later moves are dropped `move_outside_allow`, the up is still allowed, and the step fails on its post-condition. Sixteen slots suffice: a step holds at most a drag's two tokens plus modifier pairs, and typing emits one character at a time.

#### 5.4.6 The ticket-or-dialog-visible flag

`flag_ticket` is the gateway's knowledge that an order could be sent from the current screen; it is the order-stage flag of 6.2. The Window Watcher maintains it as the OR of three sources, set fast and cleared slowly:

1. Window enumeration every 100 ms: `EnumWindows`, filter by `GetWindowThreadProcessId` to the PID set, `IsWindowVisible`, class in `SunAwtFrame`, `SunAwtDialog`, `SunAwtWindow`; a visible window whose `GetWindowText` matches the order-dialog regex set from the popup catalog (the Order Confirmation dialog entry, the detached Order Entry window; exact titles are a Phase 0 read, 5.19) sets the flag. For each such window the Watcher locates the send-like controls of the never-tokenize set by template (Send in the dialog, Auto Send, Flatten, Blast All, Replace) and writes their inflated bounds into `deny_rects`. `Confirm and Send` is never a deny rectangle: it opens the dialog rather than sending, and the slow half guards it (5.4.3).
2. Ticket detector at 2 Hz: template match of the send-control templates (per theme) on a half-scale capture of the foreground window, floor 0.90. This covers the Order Entry panel docked inside the main frame, which enumeration cannot see. The matched send-like controls and the Active Trader ladder's order columns also enter `deny_rects`.
3. Flow declaration: a step with `order_stage: true` sets the flag sticky until a later `close_dialog` or `clear_ticket` teardown action (4.7) completes and an `absent` assertion on the dialog title or ticket template passes; the flow lint rejects a flow that clicks `Confirm and Send` without both.

The flag clears only after two consecutive clear polls (200 ms) from sources 1 and 2 and no sticky declaration. If enumeration or capture fails, or `watcher_mono_ts` is stale (5.4.2), the flag is `unknown`, which the hook treats as set. The Orchestrator aborts any agent or Explorer session the moment the flag becomes set or unknown (step `failed`, reason `ticket_visible_in_agent_mode`). In an Explorer session the hook also drops all input from that moment, the gateway's recovery path closes the window with a tokened Escape, and the session ends with the finding `explorer_order_stage` (S1, paged and notified by the safety routing of 9.10, the Explorer owner told), counted toward the per-run trip of ten (5.4.8); the run continues (6.8). The 30-second open-dialog kill-switch trigger of 6.6 applies to scripted flows and agent rescue only.

Residual race: a dialog appearing between the synchronous re-check at stage 4 and delivery of a guarded key a few milliseconds later. It is covered by the attestation (confirmation dialog on, so a stray Enter on the ticket opens the dialog rather than sending) and by the rule that agent and Explorer tools never emit guarded keys at all. It is listed as a known residual in 6.2 and exercised by the nightly fire drill (6.5).

#### 5.4.7 The blocked key set

While `flag_ticket` is set or unknown the hook drops, regardless of token (6.2 rule 2): `VK_RETURN` (main and numpad), `VK_SPACE`, every F-key, every chord carrying Ctrl, Alt or Win (Ctrl+Enter, Alt+letter Swing mnemonics on dialog buttons included), any mouse event while Shift is held (the opt-in Shift+click send path), and every chord in the loaded order-hotkey list. That list is loaded at `settings_attested` from two sources: every binding the attestation flow read from the Hot Keys tab (A6 requires that list to be empty, so normally nothing), and the pinned build's default order-action chords, read once in Phase 0 and checked into `gateway/default_order_hotkeys.yaml` (6.2), so a default binding that is neither an F-key nor a Ctrl, Alt or Win chord is still blocked, drill item 3 of 6.5 has a fixed set to inject, and a binding added in-session has no effect. Attestation requires the Hot Keys list to be empty and the Active Trader hotkeys disabled (A5, A6); both lists are loaded anyway. Tab, Shift+Tab, Escape, arrows, digits, letters, period, minus, Backspace and Delete pass under the flag, with tokens. Outside the flag, `VK_RETURN` and `VK_SPACE` are guarded keys: a scripted step must request them explicitly (`press: enter`, or `type_fixture` with `commit: enter`), the slow half emits them only after the synchronous re-check, and the agent `press` tool does not offer them.

#### 5.4.8 Logging of dropped events and the thresholds

Every refusal and every dropped event becomes a `gateway_drop` step event with run id, flow id, step id, mode (`scripted`, `agent`, `explorer`, `system`), monotonic and wall time, event type, vk or button, screen point, the `injected` flag, the reason code, the token id if any, the 96x96 click crop and the hash of the latest capture.

Consequences, in precedence order:

1. Safety reasons, which are attempted sends: a refusal or drop with reason `deny_rect`, `blocked_key_dialog`, `blocked_chord_dialog`, `shift_click_dialog`, `dialog_not_ok`, or a never-tokenize hit, outside the fire drill. On a scripted flow, including an agent rescue running inside it (5.6), one is enough: the step is `blocked_by_gateway`, the flow ends, the run ends `aborted_safety (reason: attempted_send)` (process tree killed, fresh scripted login, verified Cancel All, Working and Filled diffed against the start snapshot, 6.6), on-call is paged at P1 and the flow is quarantined until reviewed (6.12 incident S2 or S1 by what the proof shows). In a standalone Explorer session the same reasons end the session with the step `failed`, open an S3 ticket to the Explorer owner and count toward rule 3; the run continues, because the Explorer's toolset cannot emit a guarded key and is denied every ticket-opening control (6.2, 6.8); a ticket or dialog flag set in an Explorer session anyway follows 5.4.6 (`explorer_order_stage`). A click requested inside an order dialog on a label that is neither allowlisted nor send-like is `aborted_safety (reason: unknown_dialog_in_order_stage)` while `order_stage` is set; otherwise the flow is quarantined and the window is an `unknown_popup` finding (5.4.3).
2. Integrity: `untokened_injected` and `foreign_input` raise a `gateway_integrity` finding and an on-call alert and count toward rule 3; the run continues because nothing reached the app.
3. Counts, for integrity reasons (`token_expired`, `token_mismatch_coords`, `move_outside_allow`, `no_token` on an event the slow half believes it tokened, `untokened_injected`, `foreign_input`) and for non-send refusals in the slow half (deny profile, ambiguous name): the first integrity drop of a step gets the single retry of 5.4.3 stage 7; three refusals or drops in one flow or one agent session end it `failed`, and the flow is `not_run (reason: quarantine)` on later runs until the flow owner reviews it; ten in one run trip the kill switch and the run ends `aborted_safety (reason: kill_switch)` (6.6 lists this trigger). Explorer attempted sends under rule 1 count toward the ten as well. Drill flows and the H4 self-test are exempt.
4. A drop of the step's own token with an integrity reason follows 5.4.3 stage 7.

Run health prints drops by reason and mode; the fire drill flow class expects exactly the drop set 6.5 enumerates (each item attempted through the gateway API and by raw `SendInput` from the drill process) and passes only on that set.

#### 5.4.9 How agent mode and the Explorer are forced through the gateway

The agent loop exposes to the model only the tools in 5.6; every tool result carries the next redacted screenshot. There is no `computer` tool with coordinate actions in the tool list, and the dispatcher rejects any tool name it does not define (5.6 states the consequences). Each handler is a call into the gateway slow half with profile `agent` or `explorer`; handlers have no access to the emitter module (lint) and the hook drops anything untokened (runtime). The Explorer shares the hook host and the handlers, with the deny list of 6.8, its own login and snapshot (7.2), and the budgets of 2.9 enforced by the Orchestrator. Screenshots sent to the model are taken through Capture and pass redaction first (5.7).

### 5.5 Locator ladder

A locator turns a named target into physical screen coordinates. Each target carries up to three scripted definitions plus an agent permission:

```yaml
target:
  name: trade.order-entry.stock.qty-field
  window: main                         # or a title regex for dialogs
  jab:   { role: text, name: Qty, path: OrderEntryPanel/.../Qty }     # DR-01 Branch A only
  image: { template: anchors/order_entry_qty_label.png, offset: [64, 0], region: order-entry-panel, floor: 0.92 }
  ocr:   { text: Qty, region: order-entry-panel, offset: [64, 0], fuzzy: 0.9 }
  agent_fallback: true                 # false for login, secret and teardown steps
```

| Rung | Mechanism | Accept when | Failure code | Recorded as |
|---|---|---|---|---|
| 1. JAB (DR-01 Branch A only) | pyjab or a ctypes client over `WindowsAccessBridge-64.dll`: find the accessible context by role, name and path under the target window; read its bounds | Found, unique, visible, bounds inside the window | `locator_failed(jab)`: not found, ambiguous, stale, bridge unavailable | Step event with rung and reason; Branch B flows record `rung1_skipped` |
| 2. Image anchor | OpenCV `matchTemplate` (`TM_CCOEFF_NORMED`) on the target window's capture within the declared region; template stored beside the flow and versioned with it; one template set per theme and display tier, no multi-scale | Best score >= floor (default 0.92) and the second peak at least 0.05 below it | `locator_failed(image)` below floor; `locator_ambiguous(image)` | Step event with score, peaks, 40x20 crop at the match |
| 3. OCR text anchor | Tesseract (or PaddleOCR, Phase 0 picks) on the region upscaled 3x and inverted (the Oracle's OCR settings, 2.8.1 Sources); the word box whose normalized text matches exactly or at fuzzy ratio >= 0.9; apply the offset | Exactly one matching word box | `locator_failed(ocr)`; `locator_ambiguous(ocr)` | Step event with the word boxes considered |
| 4. Agent | Session with the goal "click the control named X in window W" and the 5.6 toolset; only if `agent_fallback: true`, preflight enabled it, the per-run rescue cap is not spent, and `flag_ticket` is clear | The step's post-condition passes within the rescue cap of 25 actions and 90 s wall clock (5.6) | `agent_failed` (`cap`, `refusal`, `vocabulary`, `abort_flag`, `disabled`) | Step `passed_via_agent_fallback` with a `locator_failure` finding |

Ladder rules:

- Within one attempt the order is rung 1, 2, 3. If all fail, the Executor runs `reset_input_state`, re-enumerates, re-captures and tries the scripted rungs once more; success is `passed_after_retry` and the first attempt's screenshot is kept. There is no third scripted attempt and no retry across a capture.
- Only then does rung 4 run, and its success is `passed_via_agent_fallback`, never `passed`. The `locator_failure` finding (8.3 kind `locator_failure`) records the step id, every rung's result and score, the pre-attempt screenshot hash, the agent action trace with rationale, the final target in physical coordinates and a 40x20 crop around it. The Reporter shows it in the Unexpected section as "scripted locator broke at step X" beside the checkpoint's diff (9.2 PR comment template), because a moved or missing control is a regression signal, not a recovered error; the crop and coordinates also become the proposed anchor patch of 9.6 One-click actions and 11.5 Maintenance model.
- A checkpoint reached after a fallback is captured after the flow's declared normalize steps (reset scroll, reselect sub-tab, park, focus) and is flagged `rescued`. Its outcome is `needs_human (reason: rescued_capture)`, even when the diff is clean, unless a higher-precedence outcome applies (an `invariant_violation`, for example); the diff still runs and the Reviewer receives the finding as input, so the human sees the diff and the broken locator together (3.11 Classification decision table). A rescued checkpoint never inherits a `noise` or `intended` decision: the signature lookup of 8.3 is skipped for it (`rescued = 1`), so a broken locator is never hidden by an earlier human verdict.
- Rung 4 is skipped with `agent_failed(disabled)` when preflight found the endpoint unreachable (`agent_available: false`), when the step or flow forbids it, during login, secret and teardown steps, when the per-run rescue cap (default 25 rescued steps) is spent, and whenever `flag_ticket` is set or unknown; the step is then `failed`, the checkpoint it led to `landmark_missing`, and the flow's later checkpoints `not_run (reason: step_failed:<step>)`. A spent rescue cap is a run-health line ("agent rescue cap reached after N steps; later locator failures are `failed`") and a maintenance item for every tier owner with a failed flow.
- The resolved rung is recorded for every step, so flows drifting from rung 1 to rung 2 or 3 between builds show up as a maintenance metric before they fail (11.5).

### 5.6 Agent-mode toolset

The agent is Claude on the security-approved endpoint (DR-07 Branch A; under Branch B this subsection is not built and every ladder ends at rung 3). It is implemented with ordinary tool definitions and image inputs, not the computer-use beta tool, because the model never receives a coordinate action; whether the data agreement covers the activity is DR-07 regardless of the API feature used (6.11). There is therefore no computer-use tool type to pin: the pinned items are the model id and the harness toolset schema version (the JSON schema of the tools below, hashed), both stamped on every agent step and checked by preflight N2 (10.7). Agent mode never runs in flows of class `login`, `fixture_reset`, `teardown`, `canary` or `paper_send_ok` (4.7, 6.11), which covers attestation and recovery. It receives a one-sentence goal, the current redacted screenshot and exactly these tools; it never receives a raw coordinate action or a free-text typing action.

| Tool | Arguments | Resolution and refusal |
|---|---|---|
| `click_named(target, window?)` | A control name from the name catalog: the Surface Registry's control ids for the current surface (4.5), the flow's declared targets, and the OCR word boxes visible on screen | Resolved by rungs 1 to 3 only. A name on the never-tokenize list (a send label) is an attempted send: in a rescue inside a scripted flow it ends the run `aborted_safety (reason: attempted_send)` (6.2); in an Explorer session it ends the session, opens an S3 ticket and counts toward the ten-per-run trip (5.4.8). A name on the active deny profile returns a tool error `blocked_by_gateway`, the step is `blocked_by_gateway`, the session continues and the attempt counts toward the three-per-session and ten-per-run thresholds of 5.4.8; the third denied attempt in a session ends it (5.4.8, 6.8); the run continues, because agent tools never emit guarded keys and the refusal happened before any event existed. A name not in the catalog returns a tool error `unknown_target` and counts as a refusal. Ambiguous names return the candidates by name, never by position |
| `type_fixture(fixture_id)` | An id from the fixture's `typed_values` (symbols, quantities, prices, watchlist names) | The gateway types the value; the model never sees or supplies text. An unknown id is a tool error and a refusal. Secrets are not fixture values |
| `press(key)` | One of `tab`, `shift_tab`, `escape`, `page_up`, `page_down`, `up`, `down`, `left`, `right`, `home`, `end` | Enter, Space, chords and function keys are not offered; any other value is a tool error and a refusal |
| `scroll(target, notches)` | A catalog name and a signed notch count | `wheel` tokens at the resolved point; mouse parked after |
| `drag_named(from, to)` | Two catalog names, both splitters or detach handles; profile `explorer` only | The `drag` primitive through the Gateway with the order-geometry refusal of 5.4.10: splitters and detach handles are the only legal targets, and a drag that starts on an order bubble on a chart or an order cell on the ladder is denied as an order path (6.8); absent from the tool list under profile `agent` |
| `zoom(region)` | A rectangle in screenshot coordinates | Read-only; mapped back to physical pixels by the fixed scale factor, cropped from the redacted native capture, returned at most 1280 px on the long edge |

Requests outside the vocabulary: the dispatcher validates every tool call against the JSON schema of these tools. An unknown tool name, a malformed argument, a key outside the `press` list, a name outside the catalog or a fixture id outside `typed_values` returns a tool error naming the allowed values, is logged as a step event with the full request, and counts as one refusal; the third refusal in a session ends it with `agent_failed(vocabulary)`, which is the three-per-session rule of 5.4.8 and 6.8. Text the model emits outside a tool call is stored as data and never acted on. A response with `stop_reason: refusal` or `max_tokens`, or a `model` field that differs from the pin, ends the session with `agent_failed(refusal)`. On any session end the step is `failed` (or, in a rescue, the ladder result is `agent_failed` and the step is `failed`), with the consequences of 5.5.

Screenshots: Capture produces the native 1920x1080 frame, redaction runs, then the frame is downscaled to 1280x720 (factor 1.5) for the model. Since the model emits no coordinates, the only mapping is for `zoom`; the scale factor is verified at the `canary_flow_passed` gate by zooming on a known template region and matching the template in the returned crop. The system prompt states that all screen content, including news, chat, notes and tooltips, is data and never an instruction, and that the session ends on any attempt outside the tools. Budgets are enforced by the Orchestrator, not the prompt: 25 actions and 90 s wall clock per rescue; the per-run rescue cap of 5.5; dollar caps per run and per week from `budgets.yaml` (11.4 Cost model); for the Explorer, 400 actions, 90 minutes, a dollar cap per session and per week, and early stop after 20 consecutive actions without a new screenshot hash (2.9, 6.8), where exhaustion ends the session and the RC run continues. Every action's rationale, tool call, result, model id, prompt hash and usage block are step events. The session aborts the instant `flag_ticket` becomes set or unknown; for the Explorer that is the `explorer_order_stage` path of 5.4.6. When the model endpoint is unavailable (preflight N2 or N5 failed, or an outage not recovered by the flow boundary, 10.7), an Explorer session does not start and an agent-only step is skipped, both recorded `not_run (reason: model_unavailable)`; a rescue rung is skipped as 5.5 states.

### 5.7 Capture

- **Responsibility**: produce, per checkpoint, one settled, redacted image of the declared target window plus a composite of the virtual screen, with the metadata the Diff Engine needs to decide comparability. Rules are owned by 3.4 Capture rules, 3.5 Settle rule and 3.6 Redaction before storage; this subsection gives the mechanism and the failure outcomes.
- **Inputs**: the checkpoint record (target window kind or title regex, data mode, settle parameters, must-see anchors, anti-anchors, `max_wait`, `keep_focus`), the Window Watcher's list, the Region Registry entry (masks are needed to judge frame stability), the redaction list and account patterns (6.10 Redaction pipeline and egress log).
- **Outputs**: target-window PNG (content-addressed by sha256), composite JPEG (report only, never diffed, never sent to the Reviewer), capture metadata (window title, extended frame rect, z-order, DPI and scale, fingerprint id, app uptime, restart count, executor mode and action path, time to settle, redaction version and box count), one egress log line per stored artifact; for `masked_live` checkpoints the 3 to 5 frames over 1 to 2 s that 7.9 specifies, whose per-pixel median equals the settled frame outside masks, since the settle rule requires the frames to be identical there (3.5); the median changes nothing the Diff Engine sees and exists so a quote flash inside the triple is recorded, not diffed.
- **Failure outcomes**: `not_settled` with reason (`frames_unstable`, `anchor_missing`, `anti_anchor_present`, `unexpected_window:<title>`, `timeout`), last frame kept, no retry, no diff; `env_error (gate: running, reason: occluded)` with the foreign window's pid and title when a foreign process's window covers any sample point of the target rect, plus a `foreign_window` event for the hardening finding of 7.8 and one on-call alert per run per foreign image name; `not_comparable (reason: window_mismatch)` when the target window cannot be found by title or its rect does not intersect the virtual screen, and `not_comparable (reason: surface_mismatch)` when the active tab or panel headers do not match the expected screen id; `landmark_missing (reason: redaction_landmark:<id>)` when a redaction landmark cannot be located (6.10), in which case nothing is stored and nothing leaves the rig for that checkpoint; a redaction hit found only by the OCR sweep releases the frame and files the redaction-miss finding of 6.10 for the flow owner.
- **Key internals**:
  - Window enumeration: `EnumWindows` plus `GetWindowThreadProcessId`; the PID set is the launcher PID, the PID owning the main frame, and every descendant tracked by psutil (whether the JVM is in-process or a child of the install4j launcher is a Phase 0 read, 5.19; the code starts from the main frame's PID either way). Visible windows of class `SunAwtFrame`, `SunAwtDialog`, `SunAwtWindow` are captured; other classes from the same PIDs are captured and logged `unknown_window_class`.
  - Bounds: `DwmGetWindowAttribute(hwnd, DWMWA_EXTENDED_FRAME_BOUNDS)` gives the visible frame in physical pixels without invisible resize borders; the process is Per-Monitor-V2 aware, so these are the pixels mss returns.
  - Grab: one `mss` grab of the virtual screen (`monitors[0]`) per frame; each window image is a crop at its extended bounds; the composite is the full frame with window rects drawn and titled. One frame for all windows means crops and composite show the same instant.
  - Pre-capture routine (3.5): `park_mouse` at the declared dead-area coordinate and wait 1 s (tooltip delay); `focus_neutral` by a tokened click on the declared neutral control, never Escape, skipped when `keep_focus: true` (the caret mask then applies); occlusion check (`WindowFromPoint` on an 8 by 8 grid inside the target rect must return windows of the process tree; a foreign process's window is the `occluded` outcome above; an unexpected thinkorswim window still present at `max_wait` after the popup sentinel ran is `not_settled (reason: unexpected_window:<title>)`); then the settle loop.
  - Settle loop: frames at 250 ms; must-see anchors present by template at 0.92 or OCR; anti-anchors (`Loading`, `Reconnecting`, `Disconnected`, spinner templates, empty-grid placeholder) absent anywhere in the target window; three consecutive frames identical outside the checkpoint's masks, redactions and a small rectangle at the parking coordinate; all within `max_wait` (default 15 s; charts and scans 30 s). The third frame of the triple is the capture (3.5). Time to settle is stored; a p50 above 2x the calibration p50 is the `settle_regression` finding of 3.5.
  - Redaction (6.10): stage 1 anchored boxes from the redaction list (offsets from landmarks such as the account selector and the Account Info header, located by template each capture) filled with the theme background color; stage 2 an OCR sweep of the whole image for the `D-` pattern, the eight-digit SCHW pattern and the test user's name tokens, filling any hit; the union of boxes from both sides is applied to both (3.6). Redaction runs in memory; the unredacted frame is never written to disk. Stores, the Diff Engine, the Reviewer and the agent receive only the redacted image, and every upload carries the redaction version (8.4).
  - Comparability metadata: window title via `GetWindowText`; active tab and panel headers by template or OCR against the checkpoint's expected screen id; executor mode and action path (scripted, retried, rescued).

### 5.8 Diff Engine

- **Responsibility**: compare candidate and base captures of one checkpoint at three granularities and produce a terminal outcome or a diff record for classification. Algorithms and parameters are owned by 3.7 Three-granularity diff, 3.8 Region Registry semantics, 3.9 A/A calibration and threshold derivation and 3.11 Classification decision table; nothing in this subsection overrides them.
- **Inputs**: both redacted captures with metadata, the Region Registry entry, A/A floors and thresholds keyed by fingerprint, the noise-signature library and decisions from the Central Store, `diff_engine.yaml`.
- **Outputs**: diff record (per-region metrics, connected components, heatmap, translation estimate, diff signature as the perceptual hash of the anchored crop with Hamming tolerance 8, 6 for tier 1), the outcome or the classification input, the `layout_shift`, `landmark_moved` and `color_shift` findings of 3.7, and the run-level global-shift signal.
- **Failure outcomes**: fingerprint mismatch is `not_comparable (reason: fingerprint_mismatch)` with the differing field, refused before any pixel is read; screen-id mismatch is `not_comparable (reason: surface_mismatch)`; a region landmark not found at its floor is `landmark_missing` for a tier-1 panel and a skipped-region finding otherwise, never a blind diff; no base capture for the checkpoint id is `needs_baseline`; a landmark move or geometry change that pushes a panel's masked plus non-identity redacted share over its budget, or any mask or redaction box onto a money cell, is `harness_error (reason: mask_budget_exceeded)` with the `mask_budget_exceeded` finding (3.8, 4.8); a threshold for a region with no calibration row is 0 and its above-zero diffs end `needs_human (reason: uncalibrated)` (3.9). The global-shift pre-pass runs once per run before any Reviewer call (fraction of checkpoints above epsilon, share of differing pixels on text edges, 10.6 A/A drift on the Nightly run): over the limits, the run finding `global_rendering_shift` stops the Reviewer queue for the run, the above-threshold checkpoints stay `needs_human (reason: global_shift)` with `review_state: pending` under that one finding, and the on-call channel gets one post instead of hundreds of findings.
- **Key internals**: exact hash equality short-circuits to `identical`; otherwise the order of 3.7 (landmarks and alignment, whole-window translation, per-region YIQ diff with pixelmatch anti-aliasing detection and SSIM, connected components over a 5x3 dilation kernel; `edge_tolerance_px` is off by default and allowed only on a region with a human-approved `floor_exception`) and the rule list of 3.11. The decision lookup of 8.3 returns every active decision within tolerance for the signature: one verdict inherits, conflicting verdicts inherit nothing and are listed as conflicting (9.7), and a rescued checkpoint never consults it (5.5). Captures produced under a harness, environment or app failure never enter it (10.1 Failure classes and the diff-engine rule).

### 5.9 Invariant Checker

- **Responsibility**: evaluate the baseline-free layout invariants (catalog in 2.7 Layout invariants) on every capture, independent of the base build.
- **Inputs**: the capture, a bounds source, the Surface Registry's required labels, required controls and minimum font height, the per-surface overlap allowlist. Masks do not apply: a clipped label inside a masked region is still a violation.
- **Outputs**: `invariant_violation` with rule id, offending bounds, native-resolution crop and tier severity; or a pass record per rule; a pre-existing violation (on both builds) reported once at one severity lower, keyed by diff signature (2.7).
- **Failure outcomes**: a bounds source that fails at run start (JAB bridge down under DR-01 Branch A; OCR calibration item H9 under Branch B) ends the run `aborted_harness` at preflight; a bridge that dies mid-run makes every later checkpoint `harness_error (reason: bounds_source_unavailable)` until the Watchdog's relaunch restores it, and a bridge still down after the relaunch ends the run `aborted_harness` with the same reason; a single element whose bounds cannot be read is recorded per rule, and the checkpoint ends `needs_human (reason: bounds_unreadable)` unless a higher-precedence outcome applies; a violation that does not persist across the three settled frames is discarded and counted in flake statistics (2.7). Invariants run on every candidate capture, including one whose outcome will be `not_run (reason: base_step_failed)` because the base build could not reach the checkpoint; their findings are reported beside that outcome (3.1).
- **Key internals**: bounds from the JAB tree under Branch A (custom-painted containers exposing no children are marked opaque and fall to Branch B rules inside); from OCR word boxes on the 3x upscaled capture plus template-located controls and projection-profile grid lines under Branch B. The rules are INV-01 to INV-15 of 2.7, each with its detection method per branch, false-positive controls and severity as that table states. INV-14 is how an app error or exception dialog on screen at capture becomes an outcome; the popup sentinel routes such dialogs here, not to the dismiss list, and the Watchdog attaches the log slice and any crash file to the finding (5.14). Results are never reclassified by the Reviewer and never inherit decisions; a wrong invariant for a surface is a registry exception with owner, reason and expiry (9.6).

### 5.10 Oracle

- **Responsibility**: read numbers and text as typed values and check them against declared expectations, arithmetic invariants and the market-data API (sources in 2.8.1, tolerances in 2.8.2, arithmetic invariants in 2.8.3, assertion kinds in 2.6.2).
- **Inputs**: captures and regions typed `rule`, the outputs of `export` and `copy_grid` steps, JAB values under DR-01 Branch A, flow assertions, fixture expectations, API quotes with the paperMoney delay model (20 minutes by default; the fixture records whether the login is real-time, 7.9).
- **Outputs**: typed extractions stored beside the capture (field, value, source, confidence), assertion results, `assertion_failed` with field, expected and observed, text diffs of exports.
- **Failure outcomes**: a false assertion is `assertion_failed`; a field unreadable above its confidence floor (70 for text, 85 for money, price, integer and percent fields; a read whose two passes at 3x and 2x upscale disagree on digit count is unreadable too) is tried on the alternate source the checkpoint declares in the order of 2.8.1 (JAB value under DR-01 Branch A, then grid copy or export where the surface has one) and, when no source reads above the floor, is `needs_human (reason: oracle_unreadable)` with the crop, the field name and both reads; an export that produced nothing within the timeout is a step `failed` with reason `export_timeout` and the checkpoint's export assertions are `needs_human (reason: oracle_unreadable)`; a failed OCR calibration panel at preflight (H9) ends the run `aborted_harness`, and a miss on the re-check at `canary_flow_passed` makes every checkpoint with an OCR assertion `harness_error (reason: ocr_calibration)`, never `assertion_failed`, as 2.8 states; a market-data API failure (N3, or a mid-run timeout) makes the API cross-checks `env_error (gate: preflight.N3)` for the checkpoints that declare them and leaves the other assertions of those checkpoints in force.
- **Key internals**: OCR on 3x upscaled, inverted crops with a per-field character whitelist (2.8.1); a calibration panel (fixture region with known digits) read at the `canary_flow_passed` gate; export through the ladder-located Actions menu with a typed absolute path (the Swing file chooser accepts a path and Enter; that Enter is a guarded key the step requests explicitly, emitted only with `flag_ticket` clear); clipboard read after `copy_grid`, then cleared; API cross-check against the quote as of capture time minus the delay, exact only for symbols whose last session closed more than the delay earlier and that are not on the 24-hour trading list (2.8.2); extractions must pass before any capture can be approved as a baseline (9.8 Baseline lifecycle).

### 5.11 Reviewer

- **Responsibility**: answer the narrow classification question of 3.12 for a diff above threshold (`matches_manifest`, `partially_matches_manifest`, `does_not_match_manifest`, `no_visible_difference`, `cannot_judge`, plus the collateral description and manifest-visibility tasks); the answer is the R input of 3.11 Classification decision table, which the Orchestrator maps to `intended` or `needs_human` at the 0.80 routing threshold. The Reviewer never decides `collateral`: that outcome follows from the surface declaration alone (3.11 rows 17 to 19), and the Reviewer only supplies the description and pointer shown beside it. Prompt contract, output schema, eval set, change control and degraded modes are owned by 3.12 to 3.16 and 10.4 and 10.7.
- **Inputs**: the item of 3.12 (header, manifest entry or dependency edge, flow context, Oracle values, diff metrics, base and candidate crops at 1:1, heatmap, optional mock, optional 2x copies), the `locator_failure` finding for rescued checkpoints; every image the redacted copy from the artifact store.
- **Outputs**: structured verdict (3.13), confidence, plain-English description, region pointer; `model` from the response, prompt hash, few-shot version, redaction and mask versions and usage per verdict (8.3 `reviews`).
- **Failure outcomes**: an item not answered by the report deadline stays `needs_human` with `review_state: pending` and the report publishes `unreviewed` for it, re-rendered when the verdict lands (10.7): the outcome then becomes what 3.11's table gives (`intended`, `collateral`, `noise` only through A/A, or `needs_human` with reason `reviewer_no_match` or `reviewer_uncertain`; a declared removed surface the Reviewer does not confirm is `needs_human (reason: reviewer_no_match)`, 3.11 row 25a) and `review_state` goes from `pending` to `done`, and if a human decision already exists on the item the verdict is attached as an annotation only and changes neither the outcome nor the decision; an item still pending when the per-run spend ceiling ends the run becomes `needs_human (reason: reviewer_cap)` with `cause: dollar_cap`, and one the Reviewer job gives up on stays `needs_human (reason: reviewer_unavailable)`, both with `review_state: done` (4.13); an endpoint unreachable at preflight (N2 or N5) sets `review_mode: deferred` for the run with the same effect; a response with `stop_reason: refusal` or `max_tokens`, a schema violation after one retry, a non-rate-limit 4xx, or a `model` that differs from the pin leaves the item `needs_human (reason: reviewer_unavailable)` and counts in run health, alerting above 2 percent of items (3.15); items beyond the per-run cap (PR 60, merge 200, RC 500) are `needs_human (reason: reviewer_cap)`; a pinned model id no longer served is a `harness_error` on the daily model check and a deprecation alarm (10.7). No run ever waits on the model.
- **Key internals**: a queue in the Central Store keyed by run id, checkpoint id, region, diff hash, mask version and prompt hash (asynchronous, idempotent); the drainer submits through Message Batches with the shared system prompt cached, one call per Reviewer cluster with its member count, and a synchronous path (concurrency 4) for every PR run item and for tier-1 items of other runs near the deadline (3.15); Reviewer clusters per run: an `invariant_violation` or `assertion_failed` never goes to the Reviewer (3.16); the sweep and split checkpoints of one surface and one region form one cluster, sent as one call carrying the crops of the smallest and the largest affected step; census and flow checkpoints cluster by 9.7's rule (equal category, primitive and region, pHash within 6, component boxes equal within 4 px relative to the region's anchored bounds), one call per cluster; schema validation before any field reaches the report; the deterministic settings of 3.12, which is what the brief's "temperature 0" means in practice (no sampling parameters on models that reject them, pinned effort, byte-stable prompt, majority vote at borderline); pinned model id. The Reviewer never promotes a baseline, never creates a mask, never changes an outcome from the Invariant Checker or the Oracle, has no tools and no access to the rig, and its text is rendered as data (3.16).

### 5.12 Stores

- **Responsibility**: persist every record and artifact with one writer per database and content addressing for images. DDL, artifact layout, git contents, retention, backup and failure modes are owned by 8.1 to 8.9; this subsection fixes the rig-side store and the hand-off.
- **Inputs**: records from every component on the rig; redacted artifacts only; the Watchdog's journal.
- **Outputs**: the Run Store on the rig (SQLite WAL plus `results.jsonl`), the Central Store on the control host, the artifact tree of 8.4 (`objects\<aa>\<sha256>` under `runs\<run_id>` and `baselines\<lineage>\<build_id>`), git-tracked registries at a pinned commit (8.5).
- **Failure outcomes**: a Run Store write that fails after the busy timeout and 3 retries ends the shard and the run `aborted_harness (reason: store_write_failed)` with the ledger intact for replay (8.9); an artifact write or read-back on the rig that fails after one retry is the checkpoint outcome `harness_error (reason: artifact_persist_failed)`, never a finding, and the run cannot end `complete` (8.4, 8.9); low free space at preflight is `env_error (gate: preflight.R7)`; an upload hash mismatch is re-requested up to 3 times, then the shard is `import_failed` and the run `aborted_harness (reason: artifact_persist_failed)` (8.9); an upload without a redaction version is refused and the checkpoint is `harness_error (reason: redaction_version_missing)`; a Central Store unreachable at `reported` keeps the run retrying with backoff until the deadline, when the dead-man timer closes it (5.14); a secret found by the post-run scan quarantines the objects and ends the run `aborted_harness (reason: secret_leaked)` with the report withheld (6.9, 8.9).
- **Key internals**: SQLite in WAL mode on a fixed local volume, never a share (8.2). The Run Store's writer is the Orchestrator; the hook host writes only its shared-memory ring, which the drainer turns into `gateway_drops.jsonl` and step events; the Watchdog writes only `watchdog_events.jsonl`, ingested into `step_events` by the Orchestrator on resume (10.2), so no second writer ever exists. The scope manifest uploaded at `running` entry lets the control host fill outcomes for a dead rig. The Central Store's only writer is one thread in the Reporter service, fed by the idempotent endpoints of 8.2; the report UI reads through read-only connections and submits decisions to that service. Git holds the Surface Registry, Dependency Map, Workspace Corpus, flows with anchor templates, Region Registry and mask records, popup catalog, mutant catalog, fixtures and the config files of 4.1 (`taxonomy.yaml`, the single source of the outcome enums; `phase0/branches.yaml`, the chosen branch per unknown, which the Executor reads to decide whether rung 1 exists; `policy/send_policy.yaml`, the OPEN `paper_send_ok` switch the gateway reads), pinned per run by the commit hash in the run row.

### 5.13 Reporter and Integrations

- **Responsibility**: turn outcomes and findings into the PR comment (9.2), merge and RC reports (9.4), report UI pages (9.5), Jira tickets and Slack posts (9.9) and alerts (9.10); apply decision inheritance (9.7); print the coverage matrix (2.12) and run health; host the dead-man timer and the Central Store writer. Templates, rules and SLAs are owned by 9. Reporting, triage and integrations.
- **Inputs**: the Central Store (outcomes, findings, diffs, reviews, decisions, baselines, flake statistics, canary results, egress log), the run's artifacts, the change manifest, the Dependency Map, run-started and run-completed events, rig heartbeat summaries.
- **Outputs**: the PR comment with Intended and Unexpected sections and the `sentinel/pr-run` commit status (`pending`, `success`, `failure`, and `error` for `aborted_safety`, `aborted_harness` and unreported runs, 9.2); the coverage matrix with every cell covered, `not_run` with reason, or `not_registered`; run health (gateway drops by reason and mode, focus corrections, popups, time to settle, agent spend, hook reinstalls, rescue cap state); deduplicated Jira and Slack posts; alerts (dead-man, `env_error`, `harness_error`, `aborted_safety`, new high-confidence `collateral`, daily `needs_human` digest, canary failure, reviewer backlog); decision records written by human actions only (9.6); the detector-blind and generation-failed banner of 10.3 while it applies.

- **Key internals**: FastAPI service on the control host behind SSO hosting the report UI, the Central Store writer and the local API every write goes through (8.2, 8.7); GitHub or Bitbucket API client posting one comment per run, edited in place on re-runs and when verdicts land; decision inheritance by diff signature rendered as "suppressed by decision #id"; `not_run` is never rendered as passed; Reviewer text is escaped as data.

### 5.14 Watchdog

- **Responsibility**: watch the Orchestrator and the thinkorswim tree from outside both; collect crash artifacts; kill, relaunch and trigger resume; own the kill switch's second half; feed the control host's dead-man timer. Design detail (heartbeat fields, sampling, reaction sequence, budgets, JVM flags) is owned by 10.2 Watchdog.
- **Inputs**: the heartbeat file of 10.2, the kill-switch file flag and named pipe, the process tree (launcher PID; main-frame PID from `GetWindowThreadProcessId` on the window matching the main-window regex; every process descended from either or running from the pinned install folder, via psutil), the run deadline, the hook host PID, crash artifact locations (`hs_err_pid*.log` at `-XX:ErrorFile`, WER LocalDumps, the app log directory pinned in config after a Phase 0 read, Application Event Log IDs 1000 and 1002).
- **Outputs**: for an app crash or hang, `assertion_failed (assertion: app_alive)` on the checkpoint being captured with the cause of 10.1 (`jvm_crash`, `hang`, `oom`, `process_exit`) in `detail` (4.13), `not_run (reason: app_crash)` for the rest of that flow, and a tier-1 `app_crash` finding with the artifacts attached (an exception dialog with the app alive is INV-14, not this path); before a `process_exit` is classified, the Watchdog checks the launcher log for an update in the failure window and compares the build manifest and the relaunch's build-id read (7.3) with the values read before the failure, and if either changed the event is `env_error (gate: launched, reason: version_changed_mid_run)` for the checkpoint in progress and the rest of the shard, with no `app_crash` finding and no relaunch consumed (10.2); `watchdog_events.jsonl` (never SQLite); relaunch and resume events; the kill-switch execution record.
- **Failure outcomes**: if the Watchdog dies, the Orchestrator notices its missing reverse heartbeat (`C:\sentinel\run\<shard_id>\watchdog.json`, written every 2 s with pid, monotonic time and last trigger; the Orchestrator reads it at every gate and flow boundary, and an age over 30 s or a dead PID is the trigger) and ends the run `aborted_harness (reason: watchdog_dead)` at the next flow boundary with the remaining checkpoints `harness_error (reason: watchdog_dead)`, since a run without a watchdog has no dead-man coverage on the rig (10.2; a Watchdog absent at preflight is H8, `aborted_harness (reason: preflight.H8)`); if the Watchdog cannot find a main frame (no window matches the regex for 30 s while the heartbeat says `running`), it tracks the tree by the install-folder rule and reports `main_frame_missing` in its journal, and the Orchestrator's next gate or step fails on its own anchor check (`env_error (gate: launched)` on relaunch, or the step's `foreground_lost`); an empty tree is the `process_exit` app failure above; if the `run_completed` event has not reached the control host by the deadline (PR budget plus 15 minutes, merge plus 30, RC plus 60, Nightly by 06:00 America/New_York), the Reporter service writes `aborted_harness (reason: dead_man)`, fills `harness_error` for every scoped checkpoint without an outcome from the scope manifest, and pages on-call (9.10). `dead_man` applies only to a run that reached `running` (scope manifest uploaded) and then stopped reporting; a run still queued at its start deadline takes the start-deadline outcome of 11.2 instead (PR run `aborted_budget (reason: pool_saturated)`, merge run coalesced into the next merge run, RC run decided by the release manager, 9.12, Nightly or Calibration run `aborted_harness (reason: start_failed)`). That is the central layer of the two-layer dead-man of 10.2; the local layer is the Watchdog itself, which at the same deadline kills the Orchestrator and the tree and runs `orchestrator --resume <run_id> --finalize`, which writes the same outcome and ships the rows.
- **Key internals**: a Windows scheduled task under the harness user, started at logon before the Orchestrator, in the same interactive session, sampling every 2 s (10.2): heartbeat age over 60 s in `running` or 5 minutes in `provisioned` and `launched`; Orchestrator PID; tree presence and working set against 1.5 x `-Xmx` plus 1 GB; screenshot staleness as the primary hang detector (hash of the main window unchanged since `expect_screen_change_since` for max(2 x `max_wait_s`, 60 s) with no anti-anchor on screen, skipped while `capture_suspended`), with `IsHungAppWindow` and `SendMessageTimeout(WM_NULL)` only as a secondary check because a blocked Swing event dispatch thread still answers Windows; new crash files. On any trigger: screenshot to a restricted folder (redacted before storage, never sent to the Reviewer); best-effort `jcmd Thread.print` from a same-major JDK under a 15 s timeout; collect the log slice since the last checkpoint, hs_err_pid files, dumps, Event Log entries, the heartbeat and the last 20 gateway events; `reset_input_state` through a fresh gateway instance (stuck modifiers survive the injecting process); kill the tree, children first, and the hook host last only when the Orchestrator is dead (otherwise the hook host stays up under the Orchestrator's deny state); signal the Orchestrator to record the outcome and relaunch, or start `orchestrator --resume <run_id>` when it is dead; a heartbeat write that fails twice is the Orchestrator's own fault, so it signals the Watchdog over the named event with code `self_abort` (the stale heartbeat is then not treated as a hang), runs teardown with capture disabled and ends the run `aborted_harness (reason: heartbeat_unwritable)` (10.2); the relaunch re-enters at `launched` and passes every gate again, `paper_mode_asserted` included, and resumes at the next flow boundary. Budgets per shard: 3 app relaunches (the first three app failures in a shard are each relaunched; a fourth, a failure during the gate sequence of the shard's first launch or of a relaunch included, marks the remaining checkpoints `not_run (reason: budget)` and ends the run `aborted_budget (reason: app_restart_budget)`, 10.2), 2 Orchestrator restarts (exhaustion: run `aborted_harness (reason: orchestrator_restart_budget)`); a hook-host restart has its own budget of one per shard and consumes no app relaunch, and the second ends the run `aborted_harness (reason: hook_lost)` (5.4.2). A proactive relaunch after 40 flows or 90 minutes of app uptime is a step event, not a failure. Kill switch: on the flag, the pipe or the operator chord it sets `deny_all` if the Orchestrator has not, kills the tree, records the time, and hands the recovery login and verified Cancel All to the Orchestrator's recovery flow class (6.6). The Rig Manager sets `-XX:ErrorFile`, `-XX:+HeapDumpOnOutOfMemoryError`, `-XX:HeapDumpPath` and `-XX:+CreateCoredumpOnCrash` in vmoptions (the same list as 7.3 and 10.2) (validity against the bundled JDK major is a Phase 0 check); whether the launcher rewrites vmoptions is unverified (7.14 item 3), so the fingerprint's vmoptions hash is what catches it.

### 5.15 Canary Service and Calibration Service

Canary Service (design, scoring and governance in 10.3 Canary Service and the mutant catalog; starter catalog in 12.5):

- **Responsibility**: prove nightly that the deployed detector path (Region Registry masks, thresholds, redaction, downscaling, Diff Engine, Invariant Checker, Oracle, Reviewer prompt and pinned model) still sees each defect class it claims to see.
- **Inputs**: the mutant catalog M01 to M33 in the one catalog file `sentinel-config/canaries/mutants.yaml` (12.5 is authoritative for ids and transformations; classes in the snake_case names of 10.3; `money_cell` flag; seed 20260101; M25 is the identical control), the approved captures of the current main build, current masks, thresholds, prompt and model id, three behavioral mutants driven through the Executor by `class: canary` flows (12.5 M26, M27, M30) and one gateway mutant (M28).
- **Outputs**: `canary_results` rows (mutant id, class, detected, outcome produced, reviewer category, the mask, decision or threshold that absorbed a miss, catalog version, base hash), detection rate per class, the canary result state per mutant (`detected`, `missed`, `detector_blind`, `detector_degraded`, `generation_failed`), the nightly path-equivalence check.
- **Failure outcomes**: the Nightly run's outcome stays `complete` whatever the canaries find; what changes is the canary state. A missed money-cell mutant sets its row `detector_blind` (its checkpoint record is `harness_error (reason: detector_blind)`), sets `system_state.detector_state`, pages P1 and stamps the banner of 10.3 on every report and PR comment until the next green canary, with the RC gate blocked; a class below its rolling floor sets `detector_degraded` (`harness_error (reason: detector_degraded)` on the missed rows) and alerts; a mutant whose landmark cannot be located is `harness_error (reason: canary_generation_failed)` for that mutant with state `generation_failed`, never skipped, and `generation_failed` pages and banners exactly as `detector_blind` does; only when no canary could run at all is the Nightly run itself `aborted_harness (reason: canary_generation_failed)`. A path-equivalence failure (below) is `harness_error (reason: canary_path_divergence)` on the re-evaluated pair's canary row, with the same banner, because a detector proven on a different path proves nothing.
- **Key internals**: mutants enter through the same `evaluate_checkpoint` entry point the Orchestrator calls for a real pair, in the same harness build (the harness commit of the Nightly run equals the day's merge run's), with `synthetic: true` set only on the record, which the Stores enforce downstream (never a baseline, decision, Jira post or product metric). Two proofs that the injection path is the real path: M25 (the unchanged base injected as candidate) must end `identical`, and every night one real checkpoint pair from the day's merge run, chosen by seed, is re-evaluated through the canary entry point and its outcome, per-region metrics and component list must equal the stored product rows exactly. Behavioral mutants (M26, M27, M30) drive the real app through the Executor so Capture, the Oracle and INV-09 are covered; M28 swaps the Send template for one step so the gateway's `blocked_by_gateway` path is covered. The catalog re-runs as a CI gate whenever masks, thresholds, the Region Registry, the prompt or few-shots, the pinned model id, the redaction stage or the downscale path change (10.3). The nightly fire drill (6.5) and the other safety canaries are flow classes owned by 6. Safety, identity and data protection and scheduled by the Nightly run beside the mutants; their results are `canary_results` rows with `money_cell = 1`, so a miss is `detector_blind` with the blind detector named, and a drill item not blocked is in addition `harness_error (reason: drill_failed:<item>)` on the drill checkpoint.

Calibration Service (procedure in 3.9 A/A calibration and threshold derivation; what invalidates calibration in 7.13):

- **Responsibility**: measure the A/A noise floor per checkpoint and per region before any threshold is used, and again whenever the fingerprint, a flow, a region, a mask, a crop or the redaction version changes.
- **Inputs**: a Calibration run (per checkpoint, five captures of the same build back to back on one rig plus one more on a second night; the library is scheduled over a weekend `all_quiet` window across the pool with each checkpoint keeping to one rig, 3.9, 7.13), the Region Registry, the Diff Engine with thresholds disabled.
- **Outputs**: `calibration_floors` rows keyed by fingerprint (changed pixels, components, SSIM, color shift, translation, time to settle per region and pair), the fix list of 3.9 with a cause class per non-zero floor on a frozen checkpoint, proposed masks from the dilated union of A/A-changing pixels (human acceptance only), derived thresholds, time-to-settle p50 per checkpoint.
- **Failure outcomes**: a non-zero floor on a `diff` or `freeze` region of a frozen checkpoint is a fix-list item with an owner, never a tolerance; until fixed or covered by a human-approved `floor_exception` the region runs at threshold 0 and its above-zero diffs end `needs_human (reason: uncalibrated)`; a fingerprint change without a new Calibration run has the same effect on every threshold-dependent checkpoint and the Nightly A/A check is `not_comparable (reason: fingerprint_mismatch)` against the old fingerprint (10.6); a fix-list item open for 5 business days quarantines the checkpoint (10.5).
- **Key internals**: the 15 pairwise diffs of 3.9 through the Diff Engine with thresholds disabled; statistics in the Central Store keyed by fingerprint id; threshold derivation by the mechanical rules of 3.9; the nightly A/A pass of 10.6 on the current main build (every tier-1 checkpoint plus a rotating 20 percent of the rest, captured twice in one session) for drift.

### 5.16 Recorder

- **Responsibility**: let a flow owner author an anchored YAML flow by performing it once on an authoring rig, and lint anchors before runs. Maintenance roles and budgets are in 11.5 Maintenance model.
- **Inputs**: the live app on an authoring rig (never a run rig), the owner's actions, the theme and display tier, the Surface Registry's control ids.
- **Outputs**: a flow file in the schema of 4.7 whose targets carry image anchors (a template of about 40x20 px around a stable icon or label chosen from the recorder's suggestions, an offset to the click point, the window title, a search region), an OCR text anchor as the next rung and a JAB path first under DR-01 Branch A, one screenshot per action, templates stored beside the flow; secret steps as `secret: vault_ref` placeholders; the pre-run anchor lint report.
- **Failure outcomes**: a recorded step whose template is not unique on its own screenshot is rejected at save time; a recording in which any keystroke was captured while the pause was active, or in which the save-time scan finds the plaintext of a secret the session used, is deleted unsaved and handled as an S1 secret incident (6.12: credential rotated, security paged); an anchor that no longer matches the latest approved base capture is a maintenance item in run health for the flow owner (11.5), never an app bug, and the flow still runs through the ladder with its `locator_failure` findings pre-labeled maintenance; a Recorder process found on a run rig at preflight fails H2 and ends the run `aborted_harness`.
- **Key internals**: global `WH_MOUSE_LL` and `WH_KEYBOARD_LL` hooks in observe mode (never blocking) plus a screenshot per action; the Recorder binary is excluded from the rig image by packaging and refuses to start on a host whose name matches the rig pattern. Secret handling: the hook pauses automatically when the focused window is the login dialog by title regex or template, or when the focused control is a password field by JAB role under Branch A, and the owner presses the pause hotkey before typing any other secret; while paused the Recorder writes no keystrokes and takes no screenshots, and on resume it asserts that its keystroke log did not grow. At save time it fetches each secret the session referenced under a short-lived lease, scans the keystroke log and OCRs every screenshot for it in memory, and refuses the save on a hit as above. Per-theme and per-tier anchor sets rather than multi-scale matching; an `order_stage` prompt when a recorded title matches the order-dialog regex set, so the flag declaration of 5.4.6 is never forgotten; re-anchor mode showing each broken anchor beside the agent's final click target for acceptance or re-recording; health fields per flow (`owner`, `last_repaired`, `agent_fallback_rate`, `flake_rate`) feeding 9.11 metrics and 11.5 budgets.

### 5.18 Technology choices

| Concern | Choice | Notes and exclusions |
|---|---|---|
| Language and runtime | Python 3.12 on every harness process; the hook host uses the standard library only | The hook host is its own process so the Orchestrator's interpreter lock never delays a callback |
| DPI awareness | `PER_MONITOR_AWARE_V2` declared first in every harness process; `GetProcessDpiAwareness` logged | Any other value at run start ends the run `aborted_harness (reason: dpi_awareness)` before any capture (3.4); all coordinates are physical pixels |

| Screen capture | mss (virtual-screen grab, crop per window) | BitBlt-based, excludes the cursor, one frame for all windows |
| Image processing | OpenCV (`matchTemplate`, binarize, dilate, connected components, phase correlation) and scikit-image (SSIM, labeling) | Deterministic and calibratable; no learned models in the detector path |
| OCR | Tesseract through pytesseract by default; PaddleOCR as the alternative, chosen in Phase 0 by accuracy on the calibration panel at the pinned 3x upscale | Runs only in the slow half and in Capture, never in the hook |

| Process tracking | psutil | Process tree from the launcher and main-frame PIDs plus the install-folder rule; working-set ceiling; Recorder-absent check |
| Storage | SQLite in WAL mode, one writer per database; content-addressed files for artifacts; git for registries, flows, masks, corpus | Never on a network share (8.2) |
| Report UI and Central Store service | FastAPI with uvicorn | Read-only connections for pages; writes through the service |
| PR comments | GitHub REST API or Bitbucket REST API client, selected by config | One comment per run, edited in place |
| Model access | Anthropic SDK: Messages with ordinary tool definitions and image inputs for the agent, Message Batches for the Reviewer, pinned model ids per component, schema-validated structured output | Security-approved endpoint with zero-data-retention terms only (6.11); agent mode absent under DR-07 Branch B; no computer-use beta tool, so the pinned items are the model id and the harness toolset schema version (5.6) |

| Hooks and shared state | ctypes `SetWindowsHookEx` with `WH_MOUSE_LL` and `WH_KEYBOARD_LL`; `multiprocessing.shared_memory` with a seqlock layout | Native rewrite of the hook host if the Phase 0 latency soak fails |

| Optional recording | ffmpeg gdigrab ring buffer at 2 to 5 fps during agent and Explorer sessions, 3 fps full length for RC runs and the fire drill (8.4) | Off for scripted PR and merge flows; paused while `capture_suspended`; frames pass redaction before storage |
| Packaging | PyInstaller plus signtool with a corporate certificate | So endpoint security can allow-list the harness by publisher and hash (11.7) |
